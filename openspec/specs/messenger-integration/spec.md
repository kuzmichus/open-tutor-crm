## Requirements

### Requirement: Отправка сообщения в мессенджер
Система SHALL предоставлять функцию `send_message(db, tutor_id, messenger, recipient, text)`, принимающую имя мессенджера из закрытого списка `MESSENGERS`, получателя и текст, и возвращающую список ошибок (пустой список — отправка успешна). Отправка SHALL выполняться только если у репетитора сохранён токен этого мессенджера и заполнены получатель и текст.

#### Scenario: Отправка в подключённый мессенджер
- **WHEN** `send_message` вызывается у репетитора с сохранённым токеном Telegram
- **THEN** сообщение доставлено через Bot API (`sendMessage`: chat_id + text), функция возвращает пустой список ошибок

#### Scenario: Отправка в MAX
- **WHEN** `send_message` вызывается у репетитора с сохранённым токеном MAX
- **THEN** сообщение доставлено через `POST platform-api2.max.ru/messages?chat_id=…` с телом `{"text": …}` и токеном сырой строкой в заголовке `Authorization`, функция возвращает пустой список ошибок

#### Scenario: Отправка в неподключённый мессенджер
- **WHEN** `send_message` вызывается для мессенджера без сохранённого токена
- **THEN** возвращается список с ошибкой «не подключён», HTTP-запрос к API не выполняется

#### Scenario: Неизвестный мессенджер
- **WHEN** `send_message` вызывается с именем вне `MESSENGERS`
- **THEN** возвращается список с ошибкой, ни один отправитель не вызывается

#### Scenario: Ошибка доставки
- **WHEN** API отвечает ошибкой (`ok: false`, HTTP 4xx/5xx) или сеть недоступна
- **THEN** отправитель повторяет попытки, после исчерпания возвращается список с описанием ошибки от мессенджера

#### Scenario: Пустой получатель или текст
- **WHEN** `send_message` вызывается с пустым получателем или пустым текстом
- **THEN** возвращается список с ошибкой, HTTP-запрос не выполняется

### Requirement: Реестр отправителей и декораторы-обёртки
Конкретные отправители SHALL регистрироваться в реестре декоратором `@register_sender("<мессенджер>")`, а `send_message` SHALL диспетчеризовать вызов по имени мессенджера. Сквозное поведение (журналирование, повтор при сбое) SHALL реализовываться классами-декораторами, оборачивающими базовый отправитель с интерфейсом `Sender.send(config, recipient, text)`; ошибка доставки SHALL передаваться исключением `SendError`.

#### Scenario: Новый мессенджер без правки отправки
- **WHEN** добавляется класс отправителя с декоратором `@register_sender("max")`
- **THEN** `send_message(…, "max", …)` вызывает его через реестр без изменений в коде диспетчера

#### Scenario: Повтор при сбое
- **WHEN** первая попытка отправки падает с `SendError`, вторая проходит
- **THEN** отправка завершается успехом, суммарно выполнено две попытки

### Requirement: Статусы подключения мессенджеров
Система SHALL предоставлять `is_messenger_connected(db, tutor_id, messenger) -> bool` и `connected_messengers(db, tutor_id) -> list[str]`. Подключённым мессенджер SHALL считаться при непустом сохранённом токене; список SHALL ограничиваться `MESSENGERS`.

#### Scenario: Список подключённых
- **WHEN** у репетитора сохранён токен Telegram и не сохранены MAX/VK
- **THEN** `connected_messengers` возвращает `["telegram"]`, `is_messenger_connected("telegram")` — `True`, для остальных — `False`

#### Scenario: Изоляция по репетитору
- **WHEN** токен сохранён у репетитора A
- **THEN** функции статусов репетитора B его не видят

### Requirement: KV-таблица параметров репетитора
Параметры репетитора (токены мессенджеров и будущие настройки) SHALL храниться в таблице `tutor_params` — одна строка на пару «репетитор + ключ»: `tutor_id` (FK на `tutors`, CASCADE) + `key` + `value`. Сервис SHALL предоставлять `get_param`, `set_param` (upsert), `delete_param`, `all_params`.

#### Scenario: Запись и чтение параметра
- **WHEN** `set_param(db, tutor_id, "telegram_token", token)` вызывается дважды с разными значениями
- **THEN** `get_param` возвращает последнее, в таблице одна строка для этой пары

#### Scenario: Изоляция параметров
- **WHEN** параметр записан репетитору A
- **THEN** чтение по id репетитора B возвращает `None`

### Requirement: Страница настройки мессенджеров
Страница `/tutor/settings` SHALL быть доступна только с сессией и содержать вкладку «Мессенджеры» с секциями поддерживаемых мессенджеров (Telegram, MAX — поле токена и статус подключения) и секциями неподдерживаемых пока мессенджеров («Скоро», без поля ввода). POST `/tutor/settings/messengers` SHALL сохранять токены по формату каждого мессенджера (Telegram — «id:секрет», принимая и ссылку вида `https://api.telegram.org/bot<token>`; MAX — длинная строка из латиницы и цифр), ре-рендерить вкладку с ошибками при неверном формате любого токена (не сохраняя ничего) и удалять параметр при пустом значении. Пункт сайдбара «Настройки» SHALL вести на `/tutor/settings`.

#### Scenario: Доступ
- **WHEN** неавторизованный запрос GET `/tutor/settings` или POST `/tutor/settings/messengers`
- **THEN** ответ 303 на `/tutor/login`

#### Scenario: Сохранение токена
- **WHEN** POST валидного токена
- **THEN** токен сохранён как параметр `telegram_token`, страница возвращается с плашкой «Изменения сохранены» и статусом «Подключён»

#### Scenario: Ошибка формата токена
- **WHEN** POST значения, не похожего на токен (у любого из мессенджеров)
- **THEN** вкладка ре-рендерится с ошибкой по этому мессенджеру, ни один токен не сохраняется

#### Scenario: Сброс подключения
- **WHEN** POST пустого поля токена при сохранённом ранее токене
- **THEN** параметр удаляется, статус — «Не подключён»

#### Scenario: Независимость статусов мессенджеров
- **WHEN** токен MAX сохранён, а токен Telegram — нет
- **THEN** секция MAX показывает «Подключён», секция Telegram — «Не подключён»

### Requirement: Журнал исходящих сообщений бота
Диспетчер `send_message` SHALL сохранять строку журнала в таблицу `sent_messages` для каждой реальной попытки доставки (вызван конкретный отправитель после валидации): репетитор, мессенджер, получатель (chat_id), текст, статус `SENT_MESSAGE_STATUSES = ("sent", "error")` и текст ошибки (`SendError` после ретраев). Ученик SHALL опознаваться одним запросом по `(tutor_id, messenger, chat_id)` в `student_messenger_invites`; не найден — `student_id` остаётся пустым. Ошибки валидации до попытки (неизвестный/неподдержанный мессенджер, пустой получатель или текст, не подключённый канал) SHALL не попадать в журнал. Запись SHALL добавляться без самостоятельного commit — транзакцию завершает вызывающий код.

#### Scenario: Успешная доставка пишется в журнал
- **WHEN** `send_message` доставил сообщение (пустой список ошибок)
- **THEN** в `sent_messages` появилась строка со статусом «sent», ученик опознан по chat_id

#### Scenario: Ошибка после ретраев пишется в журнал
- **WHEN** отправитель исчерпал попытки и вернул `SendError`
- **THEN** строка журнала имеет статус «error» и текст ошибки, включая описание от Bot API

#### Scenario: Валидация не пишет журнал
- **WHEN** `send_message` вернул ошибку до вызова отправителя (не подключён, пустой текст)
- **THEN** новых строк в журнале нет

### Requirement: Привязка канала уведомлений через диплинк бота
Система SHALL позволять репетитору привязать мессенджер к своему аккаунту по диплинку бота: действие «Подключить» SHALL генерировать одноразовый код и глубокую ссылку (`https://t.me/<бот>?start=<код>` для Telegram, `https://max.ru/<бот>?start=<код>` для MAX) при сохранённом токене этого мессенджера. Состояния привязки и подпись чата SHALL храниться в KV-параметрах репетитора (`<m>_chat_id`, `<m>_chat_label`, `<m>_bind_code`, `<m>_bind_link`). Действие «Отвязать» SHALL удалять привязку чата, не трогая токен бота.

#### Scenario: Генерация ссылки при сохранённом токене
- **WHEN** репетитор с сохранённым токеном Telegram нажимает «Подключить»
- **THEN** сохраняются одноразовый код и ссылка вида `https://t.me/<ник бота из getMe>?start=<код>`, карточка канала показывает ссылку и статус «в процессе»

#### Scenario: Подключение без токена
- **WHEN** репетитор нажимает «Подключить» без сохранённого токена мессенджера
- **THEN** блок показывает ошибку с указанием на вкладку «Мессенджеры», код и ссылка не создаются, сеть не вызывается

#### Scenario: Автоматическая привязка по коду
- **WHEN** репетитор перешёл по ссылке и нажал «Запустить» (Telegram прислал `/start <код>`, MAX — `bot_started` с payload `<код>`)
- **THEN** при проверке блока chat_id чата и подпись (`@username` или имя) сохраняются, код и ссылка удаляются, карточка показывает «<Мессенджер> подключен»

#### Scenario: Старт без кода не привязывает
- **WHEN** бот получает `/start` без кода или с чужим кодом
- **THEN** привязка не меняется, канал остаётся «в процессе»

#### Scenario: Отвязка
- **WHEN** репетитор нажимает «Отвязать» у подключённого канала
- **THEN** привязка чата и незавершённая привязка удаляются, токен бота остаётся, карточка возвращается в состояние «не подключён»

#### Scenario: Повторное подключение
- **WHEN** «Подключить» нажато повторно до завершения привязки
- **THEN** код и ссылка пересоздаются, старая ссылка работать перестаёт

#### Scenario: Приветственное сообщение после привязки
- **WHEN** привязка канала подтверждена (код найден в апдейтах)
- **THEN** бот отправляет в привязанный чат приветственное сообщение (общий `send_message`: журнал и ретрай); сбой отправки не отменяет привязку — ошибка показывается в блоке каналов

### Requirement: Блок «Каналы уведомлений» на вкладке «Уведомления»
Страница `/tutor/profile?tab=notifications` SHALL содержать блок «Каналы уведомлений» с карточкой на каждый мессенджер из списка поддерживаемых (`SUPPORTED`): «не подключён» с кнопкой «Подключить», «в процессе» со ссылкой на бота, «подключен» с подписью чата и кнопкой «Отвязать». Рендер блока SHALL быть сетенезависимым (только чтение параметров); сеть SHALL вызываться только действием «Подключить» и проверкой привязки. Пока есть незавершённая привязка, блок SHALL опрашивать сам себя по htmx, и проверка SHALL подтверждать привязку по апдейтам бота. Действия блока SHALL работать и без JS (303-редирект на вкладку).

#### Scenario: Блок на вкладке
- **WHEN** репетитор открывает вкладку «Уведомления»
- **THEN** блок показывает карточки Telegram и MAX в текущих состояниях; сетевые вызовы при рендере не выполняются

#### Scenario: Проверка привязки опросом
- **WHEN** привязка «в процессе» и бот получил старт с кодом
- **THEN** очередной опрос блока возвращает карточку «подключен» без действий со стороны репетитора

#### Scenario: Работа без JS
- **WHEN** POST «Подключить»/«Отвязать» отправлен без заголовка `HX-Request`
- **THEN** ответ — 303 на `/tutor/profile?tab=notifications`; при ошибке подключения вкладка показывает общую подсказку

#### Scenario: Неизвестный мессенджер
- **WHEN** POST-действие блока вызвано для имени вне `SUPPORTED`
- **THEN** ответ 404

### Requirement: Изоляция каналов по репетитору
Привязка канала SHALL принадлежать репетитору: чтение, подтверждение и отвязка SHALL идти по `tutor_id` из сессии, ключи привязки SHALL жить в `tutor_params` с составным PK (репетитор, ключ). Код привязки одного репетитора SHALL не подтверждать канал другого.

#### Scenario: Каналы не пересекаются
- **WHEN** у репетитора A привязан Telegram, репетитор B открывает вкладку «Уведомления»
- **THEN** карточки B показывают «не подключён»; параметры A остаются без изменений

#### Scenario: Доступ без сессии
- **WHEN** запрос GET/POST действий блока без сессии
- **THEN** ответ 303 на `/tutor/login`

### Requirement: Проверка TLS-сертификатов Bot API
Вызовы Bot API мессенджеров (клиенты привязки и отправители) SHALL выполнять проверку сертификата сервера по умолчанию. Настройка `MESSENGER_TLS_VERIFY=false` SHALL отключать проверку подлинности сервера для вызовов Bot API (шифрование сохраняется) — для сред, где сертификат API подписан корнем, отсутствующим в системных хранилищах (например, корень Минцифры для `platform-api2.max.ru`).

#### Scenario: Проверка включена по умолчанию
- **WHEN** любой вызов Bot API без переопределения настройки
- **THEN** сертификат сервера проверяется штатным SSL-контекстом

#### Scenario: Проверка отключена настройкой
- **WHEN** окружение задало `MESSENGER_TLS_VERIFY=false` и выполняется вызов Bot API
- **THEN** TLS-соединение устанавливается без проверки подлинности сервера, вызов проходит с сертификатом, которому нет доверия в системе

### Requirement: Приглашение ученика в канал через диплинк бота
Система SHALL позволять репетитору пригласить ученика в свой бот по диплинку: действие «Пригласить» в карточке ученика SHALL генерировать одноразовый код и глубокую ссылку (`https://t.me/<бот>?start=<код>` для Telegram, `https://max.ru/<бот>?start=<код>` для MAX) при сохранённом токене этого мессенджера. Приглашение SHALL храниться в таблице `student_messenger_invites` (уникально по паре ученик–мессенджер): код и ссылка — состояние «в процессе», chat_id и подпись чата — «подключён». Повторное «Пригласить» до подключения SHALL пересоздавать код и ссылку. Действие «Отвязать» SHALL удалять приглашение вместе с привязкой чата, не трогая токен бота.

#### Scenario: Генерация ссылки из карточки ученика
- **WHEN** репетитор с сохранённым токеном Telegram нажимает «Пригласить» в карточке ученика
- **THEN** ссылка копируется в буфер обмена, блок показывает инструкцию с той же ссылкой целиком и статус «в процессе», приглашение сохранено

#### Scenario: Приглашение без токена
- **WHEN** репетитор нажимает «Пригласить» без сохранённого токена мессенджера
- **THEN** блок показывает ошибку с указанием на вкладку «Мессенджеры», код и ссылка не создаются, сеть не вызывается

#### Scenario: Повторное приглашение
- **WHEN** «Пригласить» нажато повторно до подключения ученика
- **THEN** код и ссылка пересоздаются, старая ссылка работать перестаёт

#### Scenario: Отвязка ученика
- **WHEN** репетитор нажимает «Отвязать» у подключённого ученика
- **THEN** приглашение и привязка чата удаляются, токен бота остаётся, карточка возвращается в состояние «не приглашён»

### Requirement: Автоподключение чата ученика по «Запуску» бота
Проверка апдейтов бота SHALL находить за одно чтение потока и код привязки канала репетитора, и все непогашенные коды приглашений учеников его аккаунта. Найденный код приглашения SHALL сохранять chat_id чата и подпись (`@username` или имя) в приглашении, гасить код и ссылку. Старт без известного кода SHALL ничего не менять. Для MAX чтение SHALL идти по одному общему маркеру потока, двигая его только когда просмотрено всё до него.

#### Scenario: Ученик нажал «Запустить»
- **WHEN** ученик перешёл по ссылке и нажал «Запустить» (Telegram прислал `/start <код>`, MAX — `bot_started` с payload `<код>`)
- **THEN** при очередной проверке chat_id и подпись сохраняются в приглашении, код гасится, блок показывает «Ученик подключён» с подписью чата

#### Scenario: Старты ученика и репетитора в одной пачке
- **WHEN** в очереди апдейтов есть старты и с кодом канала, и с кодом приглашения
- **THEN** одно чтение привязывает и канал репетитора, и чат ученика; маркер MAX двигается один раз

#### Scenario: Старт без известного кода
- **WHEN** бот получает `/start` без кода или с чужим кодом
- **THEN** приглашения и привязка канала не меняются, приглашение остаётся «в процессе»

#### Scenario: Приветствие после подключения
- **WHEN** приглашение погашено (код найден в апдейтах)
- **THEN** бот отправляет в чат ученика приветственное сообщение; сбой отправки не отменяет подключение — ошибка показывается в блоке

### Requirement: Блок «Приглашение в мессенджеры» на вкладке «Настройки»
Форма редактирования существующего ученика SHALL содержать на вкладке «Настройки» блок «Приглашение в мессенджеры» с карточкой на каждый поддерживаемый мессенджер (`SUPPORTED`): «не приглашён» с кнопкой «Пригласить», «в процессе» с полной ссылкой на бота, кнопкой «Скопировать ссылку» и статусом ожидания, «подключён» с подписью чата и кнопкой «Отвязать». Рендер блока SHALL быть сетенезависимым; сеть SHALL вызываться только действиями и проверкой. Пока есть непогашенное приглашение, блок SHALL опрашивать сам себя по htmx. Действия SHALL работать и без JS (303-редирект на страницу ученика). У формы нового ученика блока SHALL не быть.

#### Scenario: Блок на вкладке «Настройки»
- **WHEN** репетитор открывает карточку существующего ученика на вкладке «Настройки»
- **THEN** блок показывает карточки Telegram и MAX в текущих состояниях; сетевые вызовы при рендере не выполняются

#### Scenario: У нового ученика блока нет
- **WHEN** открывается форма создания ученика
- **THEN** блока «Приглашение в мессенджеры» в разметке нет — приглашать некого, пока ученик не сохранён

#### Scenario: Проверка подключения опросом
- **WHEN** приглашение «в процессе» и ученик нажал «Запустить»
- **THEN** очередной опрос блока возвращает карточку «подключён» без действий со стороны репетитора

#### Scenario: Работа без JS
- **WHEN** POST-действие блока отправлено без заголовка `HX-Request`
- **THEN** ответ — 303 на страницу карточки ученика

#### Scenario: Неизвестный мессенджер
- **WHEN** POST-действие блока вызвано для имени вне `SUPPORTED`
- **THEN** ответ 404

### Requirement: Изоляция приглашений по репетитору
Приглашение SHALL принадлежать репетитору-владельцу ученика: доступ к фрагменту и действиям SHALL идти через владельца ученика (`get_owned_student`), чужой ученик и несуществующий SHALL быть неразличимы — 404.

#### Scenario: Чужой ученик
- **WHEN** репетитор B обращается к фрагменту или действиям приглашения ученика репетитора A
- **THEN** ответ 404; приглашение A остаётся без изменений

#### Scenario: Доступ без сессии
- **WHEN** запрос GET/POST действий блока без сессии
- **THEN** ответ 303 на `/tutor/login`
