## Requirements

### Requirement: Отправка сообщения в мессенджер
Система SHALL предоставлять функцию `send_message(db, tutor_id, messenger, recipient, text)`, принимающую имя мессенджера из закрытого списка `MESSENGERS`, получателя и текст, и возвращающую список ошибок (пустой список — отправка успешна). Отправка SHALL выполняться только если у репетитора сохранён токен этого мессенджера и заполнены получатель и текст.

#### Scenario: Отправка в подключённый мессенджер
- **WHEN** `send_message` вызывается у репетитора с сохранённым токеном Telegram
- **THEN** сообщение доставлено через Bot API (`sendMessage`: chat_id + text), функция возвращает пустой список ошибок

#### Scenario: Отправка в MAX
- **WHEN** `send_message` вызывается у репетитора с сохранённым токеном MAX
- **THEN** сообщение доставлено через `POST platform-api2.max.ru/messages?chat_id=…` с телом `{"text": …}` и токеном сырой строкой в заголовке `Authorization`, функция возвращает пустой список ошибок

#### Scenario: Отправка в неподключённый мессенджер
- **WHEN** `send_message` вызывается для мессенджера без сохранённого токена
- **THEN** возвращается список с ошибкой «не подключён», HTTP-запрос к API не выполняется

#### Scenario: Неизвестный мессенджер
- **WHEN** `send_message` вызывается с именем вне `MESSENGERS`
- **THEN** возвращается список с ошибкой, ни один отправитель не вызывается

#### Scenario: Ошибка доставки
- **WHEN** API отвечает ошибкой (`ok: false`, HTTP 4xx/5xx) или сеть недоступна
- **THEN** отправитель повторяет попытки, после исчерпания возвращается список с описанием ошибки от мессенджера

#### Scenario: Пустой получатель или текст
- **WHEN** `send_message` вызывается с пустым получателем или пустым текстом
- **THEN** возвращается список с ошибкой, HTTP-запрос не выполняется

### Requirement: Реестр отправителей и декораторы-обёртки
Конкретные отправители SHALL регистрироваться в реестре декоратором `@register_sender("<мессенджер>")`, а `send_message` SHALL диспетчеризовать вызов по имени мессенджера. Сквозное поведение (журналирование, повтор при сбое) SHALL реализовываться классами-декораторами, оборачивающими базовый отправитель с интерфейсом `Sender.send(config, recipient, text)`; ошибка доставки SHALL передаваться исключением `SendError`.

#### Scenario: Новый мессенджер без правки отправки
- **WHEN** добавляется класс отправителя с декоратором `@register_sender("max")`
- **THEN** `send_message(…, "max", …)` вызывает его через реестр без изменений в коде диспетчера

#### Scenario: Повтор при сбое
- **WHEN** первая попытка отправки падает с `SendError`, вторая проходит
- **THEN** отправка завершается успехом, суммарно выполнено две попытки

### Requirement: Статусы подключения мессенджеров
Система SHALL предоставлять `is_messenger_connected(db, tutor_id, messenger) -> bool` и `connected_messengers(db, tutor_id) -> list[str]`. Подключённым мессенджер SHALL считаться при непустом сохранённом токене; список SHALL ограничиваться `MESSENGERS`.

#### Scenario: Список подключённых
- **WHEN** у репетитора сохранён токен Telegram и не сохранены MAX/VK
- **THEN** `connected_messengers` возвращает `["telegram"]`, `is_messenger_connected("telegram")` — `True`, для остальных — `False`

#### Scenario: Изоляция по репетитору
- **WHEN** токен сохранён у репетитора A
- **THEN** функции статусов репетитора B его не видят

### Requirement: KV-таблица параметров репетитора
Параметры репетитора (токены мессенджеров и будущие настройки) SHALL храниться в таблице `tutor_params` — одна строка на пару «репетитор + ключ»: `tutor_id` (FK на `tutors`, CASCADE) + `key` + `value`. Сервис SHALL предоставлять `get_param`, `set_param` (upsert), `delete_param`, `all_params`.

#### Scenario: Запись и чтение параметра
- **WHEN** `set_param(db, tutor_id, "telegram_token", token)` вызывается дважды с разными значениями
- **THEN** `get_param` возвращает последнее, в таблице одна строка для этой пары

#### Scenario: Изоляция параметров
- **WHEN** параметр записан репетитору A
- **THEN** чтение по id репетитора B возвращает `None`

### Requirement: Страница настройки мессенджеров
Страница `/tutor/settings` SHALL быть доступна только с сессией и содержать вкладку «Мессенджеры» с секциями поддерживаемых мессенджеров (Telegram, MAX — поле токена и статус подключения) и секциями неподдерживаемых пока мессенджеров («Скоро», без поля ввода). POST `/tutor/settings/messengers` SHALL сохранять токены по формату каждого мессенджера (Telegram — «id:секрет», принимая и ссылку вида `https://api.telegram.org/bot<token>`; MAX — длинная строка из латиницы и цифр), ре-рендерить вкладку с ошибками при неверном формате любого токена (не сохраняя ничего) и удалять параметр при пустом значении. Пункт сайдбара «Настройки» SHALL вести на `/tutor/settings`.

#### Scenario: Доступ
- **WHEN** неавторизованный запрос GET `/tutor/settings` или POST `/tutor/settings/messengers`
- **THEN** ответ 303 на `/tutor/login`

#### Scenario: Сохранение токена
- **WHEN** POST валидного токена
- **THEN** токен сохранён как параметр `telegram_token`, страница возвращается с плашкой «Изменения сохранены» и статусом «Подключён»

#### Scenario: Ошибка формата токена
- **WHEN** POST значения, не похожего на токен (у любого из мессенджеров)
- **THEN** вкладка ре-рендерится с ошибкой по этому мессенджеру, ни один токен не сохраняется

#### Scenario: Сброс подключения
- **WHEN** POST пустого поля токена при сохранённом ранее токене
- **THEN** параметр удаляется, статус — «Не подключён»

#### Scenario: Независимость статусов мессенджеров
- **WHEN** токен MAX сохранён, а токен Telegram — нет
- **THEN** секция MAX показывает «Подключён», секция Telegram — «Не подключён»
