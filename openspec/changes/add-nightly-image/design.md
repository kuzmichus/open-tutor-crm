# Design

## Context

В `.github/workflows/` два файла: `ci.yml` — переиспользуемый workflow проверок
(`workflow_call`) и триггеры на `push`/`pull_request`; `release.yml` — ручная
публикация с обязательной версией, которая вызывает проверки через
`uses: ./.github/workflows/ci.yml` и публикует четыре тега. Секреты
`DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` настроены. Мотивация — в proposal.md.

Спецификация `ci-cd-pipeline` пока существует только как дельта работающего
change `add-ci-cd-pipeline` (в `openspec/specs/` её нет) и содержит требование
«Публикация запускается только вручную... MUST NOT... по расписанию». Ночной
канал прямо с ним соприкасается — согласование описано в решении 6.

## Goals / Non-Goals

**Goals:**

- Раз в сутки автоматически собирать HEAD `main` и публиковать его как
  `kuzmichus/open-tutor-crm:night`, но только при зелёных проверках.
- Ночной канал не пересекается с релизным: те же секреты, другие теги, никакой
  связи с версией.

**Non-Goals:**

- Дополнительные теги ночи (`night-YYYYMMDD`, `sha-*`) — при потребности в
  откатах добавляется отдельным change.
- Мультиархитектурность, авто-релизы, чистка релизных тегов.
- Изменение `release.yml` и логики `ci.yml`.

## Decisions

1. **Отдельный файл `.github/workflows/nightly.yml`, а не триггер в release.yml.**
   `release.yml` — «только вручную, только с явной версией»: у его
   `workflow_dispatch` есть обязательный input, который расписание передать не
   может, а комментарии файла фиксируют философию «публикация — осознанное
   действие» именно для релизного канала. Ночной канал — другое поведение с
   другим контрактом, поэтому отдельный workflow с собственными `schedule` и
   `workflow_dispatch`. Альтернатива (schedule в release.yml) отклонена: он
   заставил бы либо сделать input необязательным, либо ветвить логику по
   `github.event_name`.

2. **Гейт на проверках: job `checks` c `uses: ./.github/workflows/ci.yml`,
   публикация — `needs: [checks]`.** Тот же паттерн, что в release.yml. Красный
   `main` не должен уезжать в реестр: тег `night` по умолчанию воспринимают как
   «последнее рабочее состояние». Альтернатива «публиковать снапшот любой
   ценой» отклонена — она превращает `night` в лотерею.

3. **Один тег `night`.** Прямое требование владельца и следствие философии
   «не засорять теги» (шапка release.yml): тег перезаписывается ежедневно, сам
   себя чистит. Альтернативы с датированными тегами отклонены (см. Non-Goals).

4. **Расписание: cron `17 0 * * *` UTC = 03:17 МСК.** Ночь по московскому
   времени для владельца, при этом не ровный час — GitHub сдвигает и отбрасывает
   часть запусков на пиковых `:00`, поэтому минуты сдвинуты. Допущение, записанное
   в план: время легко поменять одной строкой, если владелец захочет другое окно.

5. **Триггер `workflow_dispatch` вместе с `schedule`.** Даёт проверить workflow
   сразу после merge, не дожидаясь первого ночного окна, и закреплён сценарием
   в спецификации.

6. **Согласование с дельтой `ci-cd-pipeline`: правка формулировки в самом
   change `add-ci-cd-pipeline`.** Требование «Публикация... MUST NOT... по
   расписанию» уточняется до смысла «запрет касается релизной публикации» —
   заголовок и сценарии остаются про релизный канал, расхождение исчезает к
   моменту архивации обоих change. Оформить это как MODIFIED-дельту в текущем
   change нельзя: спецификации `ci-cd-pipeline` ещё нет в `openspec/specs/`.
   Оставить противоречие «до архивации» тоже нельзя — в main-спеках остались бы
   два взаимоисключающих требования.

7. **Конкурентность: `concurrency.group: nightly`, `cancel-in-progress: false`.**
   Если вчерашний прогон ещё выполняется (завис на push), новый не должен рвать
   его посреди отправки в реестр — по аналогии с `release-${{ inputs.version }}`.
   Одновременные ночные публикации дрались бы за один тег.

8. **Сборка и кэш — как в release.yml:** `docker/setup-buildx-action@v4`,
   `docker/build-push-action@v7`, `linux/amd64` без QEMU, `cache-from/to:
   type=gha`. Двойная сборка (в проверках и в publish) существует и в релизе;
   gha-кэш делает вторую быстрой, поэтому выделять её в переиспользуемый
   workflow ради ночи не нужно.

## Risks / Trade-offs

- [GitHub отключает `schedule` после 60 дней без активности в репозитории] →
  платформенное ограничение; обычный ритм коммитов и релизов его не
  достигает. Признак — пропавшие ночные прогоны; лечится ручным запуском и
  повторным пушом в ветку.
- [Запуски по расписанию задерживаются, иногда заметно] → для ночного канала
  точное время не критично; точное время не даёт и сам GitHub.
- [Долгий красный `main` → тег `night` устаревает] → осознанный отказ от
  публикации красного: свежесть ночи не должна winning над «в реестре только
  рабочий код». Красный статус workflow сигнализирует о проблеме.
- [Правка дельты чужого change] → минимальная: одна формулировка, без правки
  сценариев; задачи этого change фиксируют границу правки.

## Migration Plan

Merge в `main` → расписание активно со следующего ночного окна; сразу после
merge триггер проверяется ручным запуском `workflow_dispatch`. Откат — удалить
файл `nightly.yml` (и вернуть формулировку в дельте `ci-cd-pipeline`), тег
`night` в реестре можно удалить руками.

## Open Questions

Нет: время запуска и состав тегов — записанные допущения, меняются одной строкой.
