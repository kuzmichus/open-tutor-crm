# Design

## Context

См. proposal.md — Why. Ключевые вводные из кодовой базы:

- Модели занятий нет; данные календаря — детерминированная демо-заглушка (решение зафиксировано в proposal).
- Стек: FastAPI + Jinja2 + HTMX + Alpine (все локальные ассеты в `app/static/`, запрет CDN — AGENTS.md п.7), дизайн-система в `styles.css` с готовыми статус-чипами `chip--regular/cancelled/unplanned/rescheduled` и тёмной темой на CSS-переменных.
- Доступ по сессии (`require_tutor_id`, `LoginRequired`) сейчас живёт в `app/student/services/access.py` и уже переиспользуется вне модуля student — для нового модуля это кросс-модульная зависимость.
- Роутинг: каждый доменный модуль сам собирает свой `router` в `views/__init__.py`, подключается в `main.py`; шаблоны модулей неймспейсятся подкаталогом (`tutor/…`, `student/…`).
- `/` — демо-страница «Hello world» (`app/common/views/index.py` + `app/templates/index.html`); `/tutor/` — кабинет с профилем.

## Goals / Non-Goals

**Goals:**

- Недельный календарь, который выглядит и ощущается живым: листание без перезагрузки, hover слотов, drag занятий — без задержек (никаких сетевых запросов на pointermove).
- Тестируемость в pytest: сетка, demo-занятия, навигация и заглушки проверяются текстом SSR-ответа; JS-слой — проверками наличия точки монтирования и подключённых ассетов.
- Ноль новых зависимостей и ноль миграций БД.
- Переиспользование доступа по сессии без зависимости нового модуля на student.

**Non-Goals:**

- Модель Lesson, миграции, персистентность изменений — всё, что меняется drag'ом и формой, живёт до перезагрузки/листания.
- Мобильный вид «День» (отложено — следующий change).
- Месячный/дневной режимы, ресурсы, таймзона-логика демо-данных.
- Функциональная реализация кнопок «Ссылка на окна» и «Цвет: ученик» (заглушки).

## Decisions

### D1. Гибридная архитектура: SSR + HTMX-листание + Pointer Events drag

- **Принято:** сетка, шапка дней и карточки занятий рендерятся Jinja; недели листаются HTMX-запросом `?start=` с подменой области календаря; hover/клик по четвертям — Alpine; drag — pointer-события в `app/static/calendar.js`.
- **Альтернативы:**
  - *FullCalendar (vendored):* MIT и drag входят в free, но ~400 КБ вендора, собственный скелет DOM, который придётся перевоспитывать под Geist/тёмную тему/чипы, и расхождение с философией «сервер рендерит HTML». Выигрывает только при месяце/ресурсах — это Non-Goals.
  - *Чисто клиентский рендер (JSON + JS):* мгновенное листание, но pytest не видит содержимое в `response.text`, ломается домашний стиль SSR.
  - *HTMX на drag:* невозможно — drag непрерывная интеракция; HTMX умеет request/response, не pointermove. Даже в «HTMX-варианте» drag писался бы на JS.
- **Задержки:** листание = 1 локальный запрос (~10–30 мс, незаметно); drag = 0 сети; drop в демо = 0 сети.

### D2. Новый доменный модуль `app/calendar/`

Структура по правилам AGENTS.md:

```
app/calendar/
├── __init__.py
├── services/
│   ├── access.py        # (нет — доступ в common, см. D3)
│   └── demo_schedule.py # генератор demo-недели: чистые функции
├── views/
│   ├── index.py         # GET /tutor/calendar (страница)
│   └── __init__.py
└── templates/calendar/index.html
```

- **Альтернатива:** календарь внутрь модуля tutor — отвергнута: календарь обещан сайдбаром как отдельный раздел и будет расти (модель занятий, отпуск, окна), модуль tutor сейчас про аутентификацию/профиль.
- `demo_schedule.py` — чистые функции `(week_start: date) -> Day[]`: детерминированы, не трогают БД, покрываются unit-тестами без HTTP.

### D3. Доступ по сессии — в `app/common/`

`require_tutor_id` и `LoginRequired` переезжают в `app/common/access.py`; `app/student/services/access.py` становится тонким ри-экспортом (обратная совместимость импортов) либо импорты обновляются точечно — выбирается вариант с ри-экспортом, чтобы не трогать много файлов. Вьюхи календаря берут доступ только оттуда.

- **Альтернатива:** копия доступа в модуле calendar — отвергнута (дублирование логики сессии).
- Правило «общий код в `common/`» подтверждено пользователем.

### D4. Контракт навигации недели

- `GET /tutor/calendar` — полная страница; `GET /tutor/calendar?start=YYYY-MM-DD` — **то же приложение вьюхи**, но с `HX-Request` заголовком отдаёт фрагмент (область `#calendar-swap`), без — полную страницу. Кнопки недель — `hx-get` с `hx-target="#calendar-swap"`.
- `start` нормализуется к понедельнику; некорректное значение → текущая неделя (без 4xx: календарь не должен падать на кривой ссылке).
- **Альтернатива:** отдельный `/tutor/calendar/week` — отвергнут: лишний маршрут, оба варианта покрыты одним вьюхом с веткой по заголовку.
- Демо-данные детерминированы по `week_start` → один и тот же ответ на повторный запрос (важно для тестов и HTMX-подмены).

### D5. Drag: Pointer Events + снап 15 мин, изменения только в DOM

- `pointerdown` на карточке → порог 5 px (отличие клика от драга) → `setPointerCapture` → на `pointermove` — `transform` (без ре-рендера Alpine на каждый пиксель) + подсветка целевой четверти через `elementFromPoint`/геометрию колонок → на `pointerup` — снап к 15 мин, перенос блока в колонку нового дня, фиксация в локальном состоянии.
- `touch-action: none` на карточках; на узких экранах drag конкурирует со скроллом — принимаем (net-вид «День» отложен, там конфликт пересмотрим).
- Изменения переживают только до `htmx:afterSwap` (листание перерисовывает область из SSR) — осознанный компромисс демо-режима, зафиксирован в спеке.
- Drop в демо **не** шлёт запрос; в будущем здесь же — оптимистичный `hx-post` (см. Open Questions).

### D6. Модалка «Новый урок» — Alpine-компонент в шаблоне, один в обеих точках входа

Форма входит в `calendar/index.html` (и в фрагмент, и в полную страницу). Открытие по клику четверти — из `data-*` ячейки (дата/время); по кнопке «Добавить» и по FAB — без предзаполнения времени (сегодня/ближайшая четверть — решение реализации). «Сохранить» добавляет карточку в DOM тем же кодом, что и рендер demo-занятий (единый рендерер-шаблон карточки), — чтобы позиционирование не расходилось.

### D7. Стилизация — в общем `styles.css`, не отдельный файл

Календарные классы `.cal-*` добавляются в `styles.css` (там уже вся дизайн-система и тёмная тема на переменных). `calendar.js` подключается только на странице календаря через `{% block head %}` с `defer`, как `students.js` — до `alpine.min.js` (паттерн `alpine:init` из base.html).

- **Альтернатива:** `calendar.css` — отвергнут: тёмная тема хранит переменные в одном месте, второй файл плодит дублирование переменных.

### D8. `/` → редирект, заглушка на `/tutor/`

`index.py` отдаёт `RedirectResponse("/tutor/", 303)`; `index.html` удаляется, карточка «Hello world» + часы переносится в `tutor/home.html` как «Заглушка дашборда» (секция над профилем с пояснением). `/tutor/` уже требует сессию — неавторизованный по цепочке уходит на логин. Ссылка «Главная» сайдбара — `/tutor/`.

- **Почему 303, а не 200:** это навигация GET-перехода, как в остальных редиректах проекта (`/tutor/` → login).

### D9. Ссылки навигации — косметический перевод на `/tutor/*`

Все локальные пункты `sidebar.html`, `bottom-bar` в `home.html` и `student/index.html` получают префикс `/tutor/` (`/calendar`→`/tutor/calendar`, `/students` и т.д.). Пункты без роутов (`/tutor/bookings`, `/tutor/tasks`, …) остаются заглушками 404 — как и сейчас, но в едином неймспейсе. Внешняя ссылка (feedback) не трогается.

## Risks / Trade-offs

- [**Тесты «Hello world» на `/` сломаются**] → `tests/test_index.py` переписывается на ожидание 303 → `/tutor/` (и цепочку на логин); содержимое проверяется в `test_home.py`.
- [**Слепой перевод ссылок создаёт больше 404 в неймспейсе `/tutor/`**] → осознанно: 404 и сейчас, меняем только префикс; проверка «нет битых ссылок на *несуществующие маршруты календаря*» остаётся в тестах календаря для его собственных кнопок.
- [**Drag на тач-устройствах конфликтует со скроллом**] → `touch-action: none` только на карточках занятий; принимаем до появления вида «День».
- [**Demo-данные и будущая модель: двойная логика**] → генератор изолирован в `services/demo_schedule.py` с чистым контрактом «неделя → события»; при появлении Lesson заменяется источником из БД без изменения рендеринга/JS.
- [**HTMX-фрагмент и полная страница могут разойтись**] → оба варианта рендерятся одним шаблоном с веткой на `is_fragment`; тесты покрывают оба (`HX-Request` и без).
- [**Склонения «урок/урока/уроков» в шапке**] → вынести в функцию demo-сервиса и покрыть unit-тестом (в проекте уже есть прецедент проверки склонений в тестах UI).

## Migration Plan

Миграций БД нет. Деплой — обычный: `uv run pytest` → `alembic upgrade head` (без изменений) → рестарт. Откат — revert коммита; обратная совместимость ссылок не требуется (404 был и до нас).

## Open Questions

- Будущая персистентность drag/form (POST-контракт модели Lesson) — зависит от дизайна модели, вне этого change; точка интеграции обозначена в D5.
- Точное наполнение demo-расписания (имена, цены, цвета, даты отпуска) — подбирается при реализации под эстетику, спеку не меняет.
