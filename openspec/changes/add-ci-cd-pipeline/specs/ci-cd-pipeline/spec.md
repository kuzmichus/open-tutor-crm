# Spec Delta

## Purpose

Описывает контракт автоматических проверок на push и pull_request и ручной
публикации Docker-образа: какие проверки обязательны, при каких условиях
публикация разрешена, какие теги получает образ и как версия приложения связана
с версией релиза.

## ADDED Requirements

### Requirement: Проверки запускаются на push и pull_request

Система SHALL запускать набор проверок автоматически при каждом push в любую
ветку и при каждом pull_request, без ручного вмешательства. Набор проверок MUST
быть одним и тем же для push и для pull_request.

#### Scenario: Push в ветку

- **WHEN** в ветку `ci_cd` отправлен коммит
- **THEN** запускается workflow проверок, и его итоговый статус доступен в интерфейсе GitHub

#### Scenario: Открытие pull request

- **WHEN** открыт pull request из ветки `feature-x` в `main`
- **THEN** запускается тот же набор проверок, и его статус привязан к pull request

### Requirement: Обязательный набор проверок

Набор проверок MUST включать прогон тестов, проверку соответствия `uv.lock`
манифесту, проверку отсутствия дрейфа схемы миграций, линт и сборку
Docker-образа со смоук-проверкой живости. Все проверки MUST выполняться без
внешней сети, кроме загрузки зависимостей.

#### Scenario: Тесты проходят

- **WHEN** запущены проверки для коммита, где `uv run pytest -n auto` зелёный
- **THEN** проверка тестов завершается успешно

#### Scenario: Тест падает

- **WHEN** в коммите есть регрессия и хотя бы один тест падает
- **THEN** проверка тестов завершается неуспешно, и итоговый статус workflow красный

#### Scenario: Lock-файл рассинхронизирован

- **WHEN** `pyproject.toml` изменён, а `uv.lock` не обновлён
- **THEN** проверка lock-файла завершается неуспешно

#### Scenario: Модель изменена без миграции

- **WHEN** в модели добавлено поле, но миграция не создана
- **THEN** проверка схемы на чистой базе обнаруживает расхождение и завершается неуспешно

#### Scenario: Синтаксическая ошибка или неопределённое имя

- **WHEN** в коде есть синтаксическая ошибка или ссылка на неопределённое имя
- **THEN** линт завершается неуспешно

#### Scenario: Сборка образа и смоук-проверка

- **WHEN** проверки запущены для коммита
- **THEN** образ собирается, контейнер стартует, и `GET /health` отвечает `{"status": "ok"}`

#### Scenario: Новый файл не попал в образ

- **WHEN** в корне проекта появился каталог, который не перечислен в `COPY` Dockerfile
- **THEN** сборка или смоук-проверка обнаруживают проблему до merge

### Requirement: Публикация запускается только вручную с указанием версии

Публикация образа MUST NOT запускаться на push, pull request или по расписанию.
Она SHALL запускаться только вручную и MUST требовать явного указания версии
публикуемого релиза.

#### Scenario: Пуш не публикует образ

- **WHEN** в `main` отправлен коммит или создан тег
- **THEN** workflow публикации не запускается

#### Scenario: Ручной запуск с версией

- **WHEN** пользователь запускает workflow публикации вручную и указывает версию `0.2.0`
- **THEN** запускается сборка и публикация образа версии `0.2.0`

#### Scenario: Ручной запуск без версии

- **WHEN** пользователь запускает workflow публикации, не указав версию
- **THEN** запуск отклоняется на этапе валидации входных параметров

### Requirement: Публикация не выполняется при красных проверках

Перед сборкой и публикацией образа MUST выполняться тот же набор проверок, что
и на push. Если любая проверка неуспешна, образ MUST NOT собираться для
публикации, MUST NOT отправляться в реестр, а тег MUST NOT создаваться.

#### Scenario: Тесты красные при ручном запуске

- **WHEN** пользователь запускает публикацию версии `0.2.0`, а тесты падают
- **THEN** образ не публикуется, git-тег не создаётся, workflow завершается неуспешно

#### Scenario: Версия не совпадает с проектом

- **WHEN** указана версия `0.2.0`, а в `pyproject.toml` записана другая версия
- **THEN** публикация прерывается до сборки с сообщением о расхождении версий

### Requirement: Образ публикуется в Docker Hub с набором тегов

Образ SHALL публиковаться в Docker Hub под именем `kuzmichus/open-tutor-crm`
исключительно для архитектуры `linux/amd64`. Публикация MUST давать образу четыре
тега: точную версию, минорную версию, `latest` и тег с коротким SHA коммита.

#### Scenario: Теги после успешной публикации

- **WHEN** опубликована версия `0.2.0` из коммита `abc1234`
- **THEN** в реестре доступны теги `0.2.0`, `0.2`, `latest` и `sha-abc1234`

#### Scenario: Архитектура образа

- **WHEN** образ скачан на машине с архитектурой `linux/amd64`
- **THEN** образ запускается, а манифест не содержит других архитектур

### Requirement: Тег релиза создаётся после успешной публикации

Git-тег с версией релиза MUST создаваться только после успешной отправки образа
в реестр. Если публикация не удалась, тег в репозитории MUST NOT появляться.

#### Scenario: Успешная публикация создаёт тег

- **WHEN** образ версии `0.2.0` успешно опубликован
- **THEN** в репозитории появляется тег `v0.2.0`

#### Scenario: Ошибка реестра

- **WHEN** отправка образа в Docker Hub завершилась ошибкой авторизации
- **THEN** git-тег не создаётся, а workflow сообщает об ошибке публикации

### Requirement: Версия приложения берётся из манифеста проекта

Версия, которую приложение сообщает о себе, MUST совпадать с версией в
`pyproject.toml`. Отдельного источника версии в коде быть не должно, поэтому
версия приложения и версия опубликованного образа MUST NOT расходиться.

#### Scenario: Версия в метаданных приложения

- **WHEN** в `pyproject.toml` записана версия `0.2.0` и запрошен `GET /openapi.json`
- **THEN** поле `info.version` равно `0.2.0`

#### Scenario: Версия меняется в одном месте

- **WHEN** версия в `pyproject.toml` изменена на `0.3.0`
- **THEN** приложение сообщает `0.3.0` без правок в исходниках

### Requirement: Секреты реестра недоступны для pull request

Учётные данные Docker Hub MUST быть доступны только workflow публикации.
Pull request, в том числе из форка, MUST NOT получать доступа к секретам и
MUST NOT иметь возможности опубликовать образ.

#### Scenario: Pull request из форка

- **WHEN** pull request пришёл из форка и запустил проверки
- **THEN** секреты Docker Hub недоступны, а публикация не выполняется

#### Scenario: Права токена workflow

- **WHEN** выполняется workflow проверок
- **THEN** он не имеет права записи в репозиторий и не может создать тег
