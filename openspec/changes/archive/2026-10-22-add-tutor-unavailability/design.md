# Design

## Context

Календарь уже наполняется реальными уроками (`week_days.build_week_days` → `week.week_lessons`), но недоступность репетитора осталась в демо-слое: `demo_schedule` красит август заглушкой «Отпуск», а диалог «Новый отпуск» (`calendar.js:createVacation`) добавляет блоки только в текущий DOM и теряет их при листании. См. `proposal.md` — Why.

Ограничения, которые формируют подход:

- Один репетитор — один аккаунт: `tutor_id` берётся только из сессии (`app/common/access.py`), второго педагога в модели нет.
- У `lessons` нет `tutor_id`: владелец выводится из цели (ученик или группа) через JOIN. Отметка недоступности — корневая сущность репетитора, поэтому у неё `tutor_id` есть.
- Время уроков хранится наивно (`starts_at` без конвертации), даты отметок — чистые `date`. Часовой пояс в этом change не участвует, расхождения не возникает.
- Закрытые списки значений объявляются кортежем в файле модели и дублируются `CheckConstraint` (AGENTS.md, п. 10).
- Панель в `#modal` — единственный контейнер, который переживает подмену `#calendar-swap` (`calendar/index.html`), поэтому управление отметками живёт там.
- Создание урока идёт двумя путями: форма (`POST /tutor/lessons`) и drag (`POST /tutor/lessons/{id}/move`). В форме может быть серия, даты которой считает только Python (`series_generator.generate_occurrences`).

## Goals / Non-Goals

**Goals:**

- Отметки недоступности как данные: переживают перезагрузку, листание недель и любую неделю в своём сроке.
- Один источник истины для «день отмечен»: серверный сервис, который используют и рендер календаря, и проверки урока.
- Предупреждение при постановке урока — без дублирования календарной математики в JavaScript.
- Удаление демо-слоя календаря без потери живых функций (`week_start`, `lessons_word`).

**Non-Goals:**

- Мобильная лента дня и компактный режим недели — отдельный change.
- Замещающий педагог, роли, шаринг учеников между репетиторами.
- Связь недоступности с бронированием окон (`slot-booking` остаётся демо) и с «Ссылкой на окна».
- Часовой пояс репетитора при расчёте дат отметок.
- Уведомления ученикам и напоминания о недоступности.

## Decisions

### D1. Одна таблица, два режима, CHECK по режимам

```
TutorUnavailability  (app/unavailability/models/unavailability.py)
  id          String(36) uuid4
  tutor_id    FK tutors.id ondelete=CASCADE, index, nullable=False
  mode        String(8)   'period' | 'weekday'
  reason      String(12)  'vacation' | 'sick' | 'unavailable' | 'dayoff'
  start_date  Date|NULL   period
  end_date    Date|NULL   period, NULL = бессрочно
  weekday     Integer|NULL weekday, 0..6
  until_date  Date|NULL   weekday, NULL = бессрочно
  created_at / updated_at  DateTime(timezone=True)
```

Кортежи-константы в файле модели (как `LESSON_TYPES`): `UNAVAILABILITY_MODES`, `PERIOD_REASONS`, `DAYOFF_REASON`, `REASON_LABELS`, `WEEKDAY_LABELS`.

CHECK-ограничения (`ck_unavailability_period`, `ck_unavailability_weekday`):

```
period:  mode='period' AND start_date IS NOT NULL AND weekday IS NULL
         AND until_date IS NULL AND reason IN ('vacation','sick','unavailable')
         AND (end_date IS NULL OR end_date >= start_date)
weekday: mode='weekday' AND weekday BETWEEN 0 AND 6
         AND start_date IS NULL AND end_date IS NULL AND reason='dayoff'
```

*Альтернативы.* Две таблицы (`unavailability_period`, `unavailability_weekday`) — чище по CHECK, но список «Уже отмечено» и правка срока стали бы двумя наборами сервисов и вьюх при одинаковом поведении. Одна таблица с «мягким» nullable-набором и валидацией только в форме — нарушает AGENTS.md (инвариант держится и в БД). Выбрана одна таблица с двумя CHECK.

Отдельная колонка `tutor_id` (а не вывод из цели) — потому что у отметки цели нет вовсе; это корневая сущность репетитора, как `students` и `groups`.

### D2. Отдельный доменный модуль `app/unavailability/`

```
app/unavailability/
├── models/unavailability.py
├── services/
│   ├── access.py        get_owned_unavailability + ри-экспорт require_tutor_id
│   ├── marks.py         отметки недели, покрытие дат, приоритет
│   ├── unavailability_form.py   разбор формы, контекст панели
│   ├── unavailability_writer.py создание, изменение срока, снятие
│   └── presentation.py  подписи причин и сроков
├── views/               panel.py, create.py, update_end.py, delete.py
└── templates/unavailability/_panel.html
```

*Почему не внутрь `calendar/`.* Календарь по AGENTS.md — модуль без моделей; недоступность нужна и модулю `lesson` (проверка при создании/переносе). Положить модель в `calendar` значило бы, что `lesson` зависит от `calendar`, а `calendar` уже зависит от `lesson` — цикл. Отдельный модуль разрывает его: оба зависят от `unavailability`, как `homework` зависит от `lesson`.

### D3. Выборка отметок недели — один запрос, сервис `marks.py`

```python
def marks_for_week(db, tutor_id, monday) -> list[Unavailability]  # сырые строки
def coverage_for_week(db, tutor_id, monday) -> dict[date, DayMark] # 7 дней
```

Один `SELECT` с `OR` двух форм:

```
mode='period'  AND start_date <= sunday AND (end_date IS NULL OR end_date >= monday)
mode='weekday' AND weekday IN (7 дней недели) AND (until_date IS NULL OR until_date >= monday)
```

`DayMark` — frozen dataclass: `reason`, `reason_label`, `extra_reasons` (для `title`). Покрытие разворачивается в Python по семи датам: развернуть `weekday`-отметку в даты проще, чем писать `BETWEEN` на каждую.

*Альтернатива.* Считать покрытие в шаблоне — запрещено (шаблон не форматирует бизнес-данные).

### D4. Приоритет отметок: `period` важнее `weekday`

Когда на день приходится и отметка периода, и постоянный выходной, в шапке дня показывается причина периода; причины выходного уходят в `title`. Отметка периода важнее, потому что она временная и конкретная («болею»), а выходной — фон.

**Единственный источник выходных — таблица `tutor_unavailability`.** Автоматической разметки субботы и воскресенья в сетке нет: флаг `is_weekend` и стили `.cal-day--weekend` / `.cal-dayhead--weekend` удалены. Раньше сб/вс всегда рисовались плашкой «Выходной» и штриховкой по номеру дня недели — это противоречило правилу «выходной задаёт пользователь»: день выглядел нерабочим, хотя записи в таблице не было.

*Риск путаницы с уже существующей штриховкой выходных снят вместе с самой штриховкой.* Осталось одно визуальное состояние нерабочего дня:

```
недоступность (единственный источник)
45deg, --cal-off + подпись причины в шапке
«Отпуск» / «Больничный» / «Недоступен» / «Выходной»
```

Токен `--cal-off` (тон причины) и плотный шаг штриха остаются: день читается как «выключен», а не как «просто день».

*Следствие для формы урока.* Предупреждение при постановке урока срабатывает только на отметки — в выходные по календарю урок ставится без вопросов, если репетитор их не отметил.

### D5. Предупреждение: клиент читает, сервер считает

Два канала — потому что в форме может быть серия, даты которой знает только Python:

```
ЖЕСТ (клик по четверти, drag)
  сервер отрендерил день с data-unavailable="Отпуск"
  → JS читает атрибут → confirm() → запрос с ack_unavailable=1
  (математики в JS нет)

ФОРМА (создание урока, правка даты)
  сервер считает покрытие: generate_occurrences() × marks_for_week()
  → находит пересечения → возвращает форму с баннером
  «День отмечен как недоступный: Отпуск. Всё равно поставить урок?»
  → пользователь подтверждает → повторный POST с ack_unavailable=1
```

Правила:

1. **Сервер проверяет всегда**, даже при `ack_unavailable=1`. Флаг означает «пользователь видел предупреждение», а не «можно не проверять»: он защищает только от повторного показа. Иначе устаревший `ack` (форма открыта до создания отметки) молча создал бы урок.
2. **`ack_unavailable` — hidden-поле формы** и параметр запроса переноса, а не cookie и не состояние сессии: подтверждение относится к конкретной отправке, следующая постановка в тот же день предупреждает снова.
3. **Предупреждение — не ошибка валидации.** Форма рендерится с отдельным ключом контекста (`unavailable_warning`), без `errors`: список ошибок означает «не сохранено и не сохранится», а здесь «сохранится, если подтвердите».
4. **Клиент не дублирует confirm после серверного баннера.** Клик по четверти ставит `ack_unavailable=1` в адресе формы (`?ack_unavailable=1` вместе с `starts_at`), форма несёт его скрытым полем. Один жест — одно подтверждение.

*Альтернативы.* Только клиентский `confirm()` — не работает для серии и для запроса без JS. Только серверный preflight `GET /check?starts_at=...` — лишний раунд и всё равно нужен confirm; отклонено.

### D6. Серия: одно предупреждение с числом затронутых занятий

`create_series` считает `generate_occurrences()`, поэтому проверка идёт **до** записи: `unavailability_warning(db, tutor_id, occurrences)` возвращает `(reason_label, count)` первого совпадения. При неподтверждённой отправке уроки не создаются, форма возвращается с баннером и всеми присланными значениями (панель расписания уже заполнена).

Счёт «затронуто N занятий» берётся из пересечения фактических дат серии с покрытием — то, что пользователь видит в баннере, совпадает с тем, что реально создастся.

*Риск.* `MAX_SERIES_OCCURRENCES = 520` — проверка идёт по списку дат, не по дням календаря; 520 сравнений с множеством дат покрытия тривиальны.

### D7. Демо-слой удаляется, живые функции переезжают

`demo_schedule.py` распиливается:

```
удаляется:  _LESSONS_BY_WEEKDAY, is_vacation_week, is_between_terms,
            build_week, _day_events
переезжает: week_start()      → app/calendar/services/week.py (рядом с week_bounds)
            lessons_word()    → app/calendar/services/presentation.py
```

`schedule_event.py`: убираются `kind`, `VACATION`, `is_lesson`; `ScheduleEvent.from_lesson` остаётся. `ScheduleDay.lessons` заменяется на `events` (фильтровать больше нечего).

`calendar.js`: удаляются `vacationForm`, `openVacationDialog`, `closeVacation`, `createVacation`; guard в `openSlot` (`day.querySelector(".cal-vacation") → return`) заменяется проверкой `data-unavailable` с `confirm()`.

`presentation.py`: `has_vacation`/`is_vacation` уходят, приходит `unavailable` (причина или пусто) и `is_empty` считается по урокам и отметкам (см. требование «Пустая неделя»).

### D8. Панель управления — паттерн домашнего задания

`GET /tutor/unavailability` → `_panel.html` в `#modal`. Форма и список — **одна форма** с `hx-target` на саму себя и `hx-swap="outerHTML"` (как `homework/_panel.html`): сохранение возвращает панель, ошибка — панель с ошибками и присланными значениями. Плюс `HX-Trigger: unavailability-saved`, на который подписан корень `#calendar-swap` — неделя перерисовывается с сервера.

*Почему не пустой ответ + событие, как у уроков.* Панель содержит список «Уже отмечено», который обязан обновиться после каждого действия; пустой ответ его бы не обновил, а отдельный запрос списка — лишний раунд.

### D9. «Изменить срок» — отдельный эндпоинт

`POST /tutor/unavailability/{id}/end` меняет только `end_date` (или `until_date` для выходного). Полная форма правки не нужна: причина и первый день у отметки не меняются, а «снять и поставить заново» — это ровно то, чего просили избежать.

Правило валидации: новый срок не раньше первого дня (для периода) и не раньше сегодняшнего дня не требуется — можно сократить прошедшую отметку. Пустое значение = бессрочно (для периода) / без ограничения (для выходного).

### D10. Снятие — двухшаговое, как удаление группы

Кнопка «Снять» → состояние «Точно снять?» → `POST /tutor/unavailability/{id}/delete`. Паттерн уже есть в `group/_manage.html`; отмены (undo) в проекте нет, а бессрочная отметка без подтверждения необратима одним кликом.

### D11. Список «Уже отмечено»: активные сверху, прошедшие свёрнуты

Сортировка: активные (срок не истёк) по возрастанию первого дня, затем прошедшие — под `<details>` «Показать прошедшие». Причина деления — список растёт монотонно, и без свёртки через год он вытеснит форму.

## Risks / Trade-offs

- **[Два подтверждения подряд]** клик по четверти даёт `confirm()`, затем форма может дать серверный баннер → смягчение: `ack_unavailable` передаётся из адреса формы в скрытое поле (D5, п. 4); без этого флага сервер предупреждает всегда.
- **[Устаревший DOM]** отметку создали в другой вкладке — `data-unavailable` в открытой неделе отсутствует → смягчение: сервер проверяет всегда, даже с `ack`; предупреждение придёт из формы, а не из `confirm()`.
- **[Отметка не влияет на существующие уроки]** создали отпуск поверх стоящих занятий — уроки остаются, календарь показывает их поверх штриховки → осознанно: change не удаляет и не переносит уроки, только предупреждает при постановке. Отдельный сценарий «что делать с уже стоящими» — вне объёма.
- **[Путаница штриховок]** выходной, недоступность и (до удаления) заглушка похожи → смягчение: собственный токен `--cal-off`, плотнее шаг, подпись причины в шапке; тест на различие классов.
- **[Бессрочная отметка «забыта»]** отпуск без последнего дня действует годами → смягчение: в списке срок показан как «с 26.10 — бессрочно», кнопка «Снять» на виду.
- **[Подсчёт серии расходится с фактическим созданием]** считаем по `generate_occurrences`, а создаём по тем же датам — расхождение возможно только при изменении генератора → смягчение: одна функция-источник дат на оба шага, тест «число в баннере = числу затронутых уроков после создания».
- **[Удаление демо ломает существующие тесты]** 4 демо-теста и 3 теста DOM-отпуска в `tests/test_calendar.py` → смягчение: удаляются вместе с кодом, новые тесты отметок покрывают те же сценарии на реальных данных.

## Migration Plan

1. `uv run alembic revision --autogenerate -m "add tutor unavailability"` → таблица `tutor_unavailability` с FK и CHECK; `uv run alembic upgrade head`.
2. Данные не мигрируются: демо-отпуск существовал только в коде, отметок в базе нет.
3. Порядок выката внутри одной ветки: модель и миграция → сервисы и панель → рендер календаря → предупреждения в уроках → удаление демо-слоя → тесты. Промежуточное состояние (отметки есть, демо ещё не удалено) рабочее: демо-отпуск и отметки сосуществуют один коммит.
4. Откат — `alembic downgrade -1` и revert коммита; данные пользователя (уроки) не затрагиваются.
5. При архивации change'а capability `vacation-creation` теряет все требования и удаляется из `openspec/specs/` (штатное поведение `openspec archive`).

## Open Questions

- Нужен ли фильтр «показывать только активные» в списке, если отметок станет много — решается после первых реальных данных, спеки не меняет.
- Стоит ли подсвечивать целевую четверть красным во время перетаскивания в отмеченный день (сейчас — только `confirm()` при отпускании). UX-улучшение, не влияет на требования.
