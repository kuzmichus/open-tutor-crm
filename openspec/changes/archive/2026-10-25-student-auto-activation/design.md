# Design

## Context

Статус ученика — ручное поле (`new` / `active` / `archived`, CHECK в БД). Списание за проведённый урок создаётся автоматически в двух путях записи: `charges.sync_lesson_charge` (обычная работа с уроками) и `recalculate` (кнопка «Пересчитать баланс», backfill старых занятий). Оба пути живут без коммита внутри себя — коммит делает вызывающая сторона, поэтому хук активации может участвовать в той же транзакции.

## Goals / Non-Goals

- Goals: «новый» ученик сам становится «активным» после первого платного проведённого урока; правило одним местом; атомарность с уроком и списанием.
- Non-Goals: обратные переходы, активация платежами/возвратами, уведомления, ретроактивная активация при миграции (старые ученики активируются кнопкой «Пересчитать баланс» на их карточке).

## Decisions

### D1. Триггер — строка списания, а не статус урока
«Проведён не бесплатно» в системе выражено ровно одной вещью: строкой `account_operations` с `kind='lesson'`. Статус урока «Проведён» не подходит (бесплатный урок проведён, а платного занятия не было), цена на уроке — тоже (у группового урока цена участника берётся из группы и может появиться в любой момент). Списание объединяет всё: урок проведён, цена определима, операция создана. Бонус: CHECK `amount > 0` на списании исключает «активацию нулём».

### D2. Правило перехода — только `new` → `active`, без коммита
Активация — одно присваивание с защитой: ученик существует, его статус «новый». Архив остаётся архивом: возвращение ученика в работу — решение репетитора, а не побочный эффект списания (у архивного ученика не должно быть новых уроков, а если списание появилось из старых данных — статус менять молча опасно). Функция без коммита, как `sync_lesson_charge`: урок, списания и статус едут одним коммитом вызывающей стороны, откат отменяет всё вместе.

### D3. Правило живёт в модуле `student`, вызывается из `finance`
Перевод статуса — жизненный цикл ученика, поэтому функция в `app/student/services/activation.py`; пути создания списаний (`finance`) её вызывают. Зависимость `finance → student` уже существует по моделям (все операции джойнят ученика), сервис-импорт ничего нового не добавляет; вмонтировать правило в `charges.py` значило бы оставить знание о статусах ученика в чужом домене.

### D4. Хук — в момент создания строки, не после коммита
В `sync_lesson_charge` активация вызывается в ветке `operation is None` (upsert обновил сумму — ученик уже был активирован раньше), в `recalculate` — при добавлении backfill-строки. Повторные вызовы идемпотентны (защита по статусу), поэтому серия из нескольких уроков или пересчёт по 20 занятиям безопасны без запоминания «кого уже активировали».

## Risks / Trade-offs

- Репетитор, специально держащий ученика «новым» при идущих занятиях, получит автоперевод. Осознанный компромисс: статус и так надо переводить руками, автоматика делает ровно то же действие.
- Групповой урок активирует всех участников с ценой — включая тех, кто попал в группу случайно. Цена участника (`price_override`) и выведение из группы остаются ручными инструментами.
