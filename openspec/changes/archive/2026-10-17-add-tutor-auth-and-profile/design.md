# Design

## Context

См. proposal.md — Why. Ключевые факты из кодовой базы:

- `app/tutor/models/tutor.py` — модель `Tutor` (id INTEGER PK, name, email, created_at); таблица уже создана и имеет миграции `d94901fbc8b7` → `eb86f21210aa`.
- До этого изменения модуль содержал одну вьюа — страницу-список `GET /tutors`; она (вместе с `index.py` и `tutor/index.html`) удаляется по решению пользователя, поэтому на момент реализации views модуля создаются с нуля.
- Шаблоны модуля неймспейсятся подкаталогом (`tutor/home.html`); каталог уже зарегистрирован в `app/templating.py`.
- В окружении НЕ установлены `passlib`, `bcrypt`, `argon2`, `pwdlib`, `itsdangerous` — хеширование и сессии делаются на стандартной библиотеке, новых зависимостей не добавляем.
- Тесты `tests/test_pages.py` создают `Tutor(name=..., email=...)` напрямую — после смены схемы их надо обновить.

## Goals / Non-Goals

**Goals:**

- Надёжная (пере)схема таблицы `tutors` с переносом существующих строк.
- Работающие регистрация, вход, сессия, личный кабинет, выход, восстановление пароля по ссылке.
- Соответствие AGENTS.md: один класс — один файл, по одному эндпоинту на файл views, миграция через Alembic, зелёные тесты.

**Non-Goals:**

- Отправка писем по email (ссылка восстановления показывается на странице — по решению пользователя).
- Роли, права доступа, панель администратора, редактирование карточки (CRUD-форма профиля).
- CSRF-токены, «запомнить меня», OAuth, подтверждение email.
- Новые зависимости, кроме `python-multipart` (обязателен для `Form()` в FastAPI — подтверждено пользователем). passlib/bcrypt/pwdlib/itsdangerous не используются: хеширование и сессии — на стандартной библиотеке.

## Decisions

### D1. Хеширование пароля: стандартная библиотека, PBKDF2-HMAC-SHA256

Формат хранения: `pbkdf2_sha256$<итерации>$<соль_hex>$<хеш_hex>` (соль 16 байт на пользователя, генерация через `secrets`; итерации — константа модуля, ~600 000).

- Почему не `pwdlib[argon2]`/`bcrypt`: в проекте нет ни одного хеш-пакета, зависимости в `pyproject.toml` минимальны; PBKDF2 доступен «из коробки» и полностью покрывает требование «пароль хранится захешированным».
- Верификация и хеш-формат инкапсулируются в классе `PasswordHasher` (`app/tutor/services/password_hasher.py`), поэтому алгоритм позже меняется в одном месте.
- Альтернатива (открытый пароль) отвергнута прямо пользователем; формат с префиксом и итерациями позволяет мигрировать на другой алгоритм без ломки данных.

### D2. Сессии: серверные, таблица `tutor_sessions` + httpOnly-cookie

- Модель `TutorSession` (`app/tutor/models/tutor_session.py`): id, `tutor_id` FK, `token` (уникальный, `secrets.token_urlsafe(32)`), `expires_at`, `created_at`. Срок жизни — 7 дней.
- Cookie `tutor_session`: `httponly=True`, `samesite="lax"`, `path="/"`, `secure=False` (локальная разработка по HTTP).
- Почему не подписанный cookie (HMAC/itsdangerous): нужен секрет конфигурации и нет серверного отзыва — а spec требует, чтобы после logout кабинет снова закрывался; удаление строки делает это тривиально. `itsdangerous` в окружении отсутствует.
- Проверка на каждый запрос кабинета: по cookie ищется живая сессия (token + `expires_at > now`); иначе — редирект на `/tutor/login`. Подделанный/неизвестный token просто не находится в базе.

### D3. Ключи восстановления: таблица `tutor_password_reset_tokens`

Модель `PasswordResetToken` (`app/tutor/models/password_reset_token.py`): id, `tutor_id` FK, `token` (уникальный, `secrets.token_urlsafe(32)`), `created_at`, `expires_at` (TTL 24 часа — закреплено в spec), `used_at` (NULL = не использован).

- Почему не колонки `reset_token`/`reset_token_expires_at` на `tutors`: колонки «протухли бы» вместе с историей, а таблица даёт одноразовость (`used_at`) и возможность иметь несколько активных ключей (например, повторный запрос) без потери предыдущих.
- Использование: при POST формы нового пароля ключ помечается использованным в той же транзакции, что и смена пароля.
- Компромисс: токены лежат в БД открытыми (как и сессии) — приемлемо для локальной CRM; хранение хешей токенов отложено.

### D4. Миграция `tutors`: пересоздание таблицы вручную

SQLite не позволяет сменить PK и тип `id` через ALTER. Autogenerate не обнаружит смену типа PK, поэтому миграция пишется вручную (revision с `down_revision='eb86f21210aa'`):

1. `op.create_table('tutors_new', ...)`: id `sa.String(36)` PK, name, email (unique index), `password_hash` (nullable — для перенесённых строк), телефон, «о себе», предмет, опыт, стоимость в час (Numeric, nullable), часовой пояс (nullable), created_at.
2. Копирование данных: `INSERT INTO tutors_new (id, name, email, created_at) SELECT lower(hex(randomblob(4)))||'-'||... , name, email, created_at FROM tutors` — генерация uuid4 через SQL-выражения SQLite (или `op.get_bind().execute` с `uuid.uuid4()` в python-цикле; выбираем python-цикл для гарантии формата uuid4).
3. `drop_table('tutors')`, `rename` new → `tutors`, восстановление unique-индекса на email.
4. `downgrade()` — обратное пересоздание INTEGER PK (id теряет uuid4; имя/иные колонки не восстанавливаются — осознанный компромисс демо-миграции, фиксируем в миграции комментарием).

`created_at` переносится как есть. Новые необязательные колонки — nullable, `password_hash` — nullable только для мигрированных строк: форма регистрации всегда требует пароль, поэтому в приложении он обязателен (соответствует spec: миграция создаёт новые колонки с допустимыми пустыми значениями).

### D5. Раскладка кода (правила AGENTS.md)

Views, по одному эндпоинту на файл, все в `app/tutor/views/`, собираются в `views/__init__.py`:

| Файл | Эндпоинты |
|---|---|
| `home.py` | `GET /tutor/` |
| `login.py` | `GET+POST /tutor/login` |
| `register.py` | `GET+POST /tutor/register` |
| `logout.py` | `POST /tutor/logout` |
| `remember_password.py` | `GET+POST /tutor/remember-password` |
| `reset_password.py` | `GET+POST /tutor/reset-password?key=...` |

Сервисная логика, не относящаяся к вьюам и не являющаяся ORM-моделью, — в новом каталоге модуля `app/tutor/services/` (по одному классу на файл):

- `password_hasher.py` — `PasswordHasher` (hash/verify).
- `sessions.py` — работа с сессиями: создание, проверка cookie, удаление.
- `password_reset.py` — создание/проверка/погашение ключей.

Шаблоны (`app/tutor/templates/tutor/`): `home.html`, `login.html`, `register.html`, `remember_password.html`, `reset_password.html` — все наследуют `base.html`. `index.html` (страница-список `/tutors`) удаляется вместе с ручкой.

### D6. Поведение форм и редиректов

- Регистрация принимает **только четыре поля**: имя, email, пароль и подтверждение пароля (решение пользователя). Лишние поля в POST **игнорируются**; необязательные поля карточки (телефон, «о себе», предмет, опыт, стоимость/час, часовой пояс) при регистрации не заполняются — они остаются частью карточки и выводятся в кабинете, когда заданы. Проверка «стоимость часа — число» убрана из регистрации вместе с самим полем; заполнение профиля после регистрации — вне объёма (см. Non-Goals).
- Пароль и подтверждение должны совпадать; несовпадение — ошибка валидации без создания аккаунта, проверка идёт после пустого пароля и до проверки дубликата email.
- GET-страницы форм — `200`; ошибки валидации — повторный рендер формы с сообщением (status 200, как у HTMX-сайтов без JS-раутинга).
- Успех регистрации → `303` на `/tutor/login` с сообщением «Аккаунт создан, войдите» (аутологин не делаем — по спеке пользователь направляется на вход).
- Успех входа → `303` на `/tutor/`; logout → `303` на `/tutor/login`; успех сброса → `303` на `/tutor/login` с сообщением.
- Ошибки входа — единое сообщение «Неверный email или пароль» (spec).
- Email-валидация — простая проверка присутствия `@` и домена регулярным выражением (без `EmailStr`: пакет `email-validator` не установлен).
- Ссылка восстановления формируется как `/tutor/reset-password?key=<token>` и выводится на странице результата.

### D7. Тесты

- Обновить `tests/test_pages.py`: фабрика создания репетитора в `tests/conftest.py` (например, фикстура `tutor_factory`), передающая обязательные поля + `password_hash`.
- Новые тесты (по одному-несколько на каждый сценарий спек): рендер каждой страницы; успешная регистрация (и что пароль в базе != открытому); дубликат email; невалидные данные; успешный вход и редирект; неверный пароль/неизвестный email; кабинет закрыт без сессии; кабинет показывает только свои данные; logout закрывает сессию; восстановление: существующий email → ссылка с ключом, неизвестный → нейтральное сообщение; успешный сброс (старый пароль не входит, новый входит); повторное использование ключа; истёкший/несуществующий ключ; пустой новый пароль.
- Тест миграции данных не пишем (in-memory `create_all` в тестах не проходит через Alembic); перенос проверяется вручную по шагам Migration Plan.

## Risks / Trade-offs

- [Смена PK int → uuid4 в SQLite может сломать миграцию на реальных данных] → миграция пишется вручную с python-циклом копирования; перед применением — бэкап файла БД; `downgrade()` восстанавливает работоспособную схему (без uuid4).
- [Dev-база `tutor.db`, созданная через `init_db()` (create_all), имеет старую схему] → create_all не мигрирует существующие таблицы; в шагах миграции: либо `alembic upgrade head` с предварительным `alembic stamp`, либо удалить `tutor.db` в локальной разработке (таблица с демо-данными переносится миграцией).
- [Ссылка восстановления показывается на экране, а не отправляется письмом] → осознанный демо-компромисс по решению пользователя; реальная доставка — вне объёма.
- [Нет CSRF-защиты у POST-форм] → `SameSite=lax` у cookie снижает риск; CSRF-токены — вне объёма (Non-Goals).
- [Хранение сессий и ключей восстановления открытыми токенами в БД] → для локальной CRM приемлемо; при переходе в прод — хранить хеш токенов (не меняет спеки, только D3/D2).
- [Существующие тесты и любые внешние обращения к `Tutor(name=..., email=...)` сломаются] → фабрика в conftest; сломанные обращения — только в `tests/` (поиском подтверждается при apply).

## Migration Plan

1. Бэкап dev-базы (`cp tutor.db tutor.db.bak`), если она есть.
2. `uv run alembic revision` уже создан вручную; применить: `uv run alembic upgrade head`.
3. Проверка: строки старой таблицы перенесены (SELECT name, email — без потерь, у каждой uuid4), `alembic downgrade -1`/`upgrade head` проходят без ошибок; страница `/tutors` уже удалена, поэтому перенос проверяется по данным и через кабинет `/tutor/`.
4. Откат: `uv run alembic downgrade eb86f21210aa` (id возвращается к INTEGER, uuid4 теряются) либо восстановление бэкапа.
