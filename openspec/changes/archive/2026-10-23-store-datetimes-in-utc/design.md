# Design

## Context

См. `proposal.md` — Why. Состояние кода, которое формирует подход:

- `lessons.starts_at` и `homework.due_at` объявлены `DateTime(timezone=True)`, но получают **наивные** значения из `datetime-local`: `lesson_form._parse_datetime` делает `datetime.fromisoformat`, `homework_form._parse_due_at` — то же. Колонка не спасает: тип в SQLite не влияет на то, что кладёт приложение.
- `created_at`/`expires_at` уже пишутся через `utcnow()` (`app/tutor/services/clock.py`), то есть **в одной таблице две системы координат**: `lessons.starts_at` — местное время, `lessons.created_at` — UTC.
- SQLite теряет `tzinfo`: `DateTime(timezone=True)` возвращает наивное значение. Проверено: и `14:00+00:00`, и `14:00+03:00` читаются как `14:00` без зоны. Значит aware-значение существует только внутри Python, и каждое чтение из БД нужно нормализовать.
- «Сейчас» и «сегодня» берутся локально: `datetime.now()` в `calendar/views/index.py` и `tutor/views/home.py`, `date.today()` в `lesson/services/lessons.py`, `unavailability/services/unavailability_form.py`, `group/views/create_student.py`.
- `tutor.timezone` есть в модели и в `tutor-records`, но **не заполняется нигде**: регистрация пишет только имя/email/пароль, страницы профиля нет. У всех 7 репетиторов в рабочей базе значение `NULL`, поэтому бейдж зоны в календаре всегда скрыт.
- `zoneinfo` уже используется в `app/common/services/timezones.py` для списка зон — новую зависимость вводить не нужно.
- `presentation.py` принимает `now` параметром и не читает часы сам — это готовая точка для подстановки зонального «сейчас».
- Клиентская математика: `calendar.js:todayIso()` и `prefillMoment()` читают `new Date()`, то есть часы устройства.

## Goals / Non-Goals

**Goals:**

- Один кадр хранения (UTC) и одно место перевода в зону педагога — чтобы окна и бронь следующего change'а могли сравнивать времена без специальных знаний.
- Инвариант миграции, проверяемый тестом: после перевода существующих строк отображение не меняется ни на минуту.
- Минимальный диф: `layout_events`, шаблоны карточек и CSS не переписываются.

**Non-Goals:**

- UI профиля для смены зоны и любая валидация ввода зоны пользователем.
- Зона ученика при показе (публичная страница следующего change'а показывает зону педагога и подпись).
- Перевод времени в напоминаниях, письмах и экспорте — их пока нет.
- Смена типа колонок в БД: `DateTime(timezone=True)` остаётся, меняется только то, что в неё кладут.

## Decisions

### D1. Один модуль перевода: `app/common/services/tutor_time.py`

Правило «всё время переводится здесь» вместо разбросанных `.astimezone()`:

```python
tutor_zone(tutor) -> ZoneInfo        # fallback: системная зона -> UTC
to_utc(local_naive, tutor) -> datetime   # aware UTC
to_local(utc_value, tutor) -> datetime   # aware в зоне педагога
now_utc() -> datetime                    # aware UTC
now_local(tutor) -> datetime
today_local(tutor) -> date
local_day_bounds(day, tutor) -> (utc_start, utc_end)
local_week_bounds(monday, tutor) -> (utc_start, utc_end)
```

*Почему в `common/`, а не в `calendar/`*: модуль нужен уроком, ДЗ, календарю и недоступности; AGENTS.md требует общий код держать в `common/`. `clock.py` (`utcnow`/`as_utc`) остаётся и используется внутри — дублировать нормализацию нельзя.

*Альтернатива*: положить перевод в `calendar/` и импортировать из `lesson/` — создало бы зависимость урока на календарь, которой сейчас нет (зависимость идёт в обратную сторону: календарь читает уроки).

### D2. Зона педагога с детерминированным fallback

```
tutor.timezone пусто / неизвестное имя  ->  системная зона сервера
системная зона недоступна               ->  UTC
```

`ZoneInfo(name)` бросает `ZoneInfoNotFoundError` на неизвестное имя — это не 500, а переход к следующему уровню. Отсутствие зоны не должно ломать страницу: репетитор с `NULL` (после миграции таких не будет, но строки могут появиться из старых бэкапов) видит время в зоне сервера.

*Почему не «требовать зону и падать»*: `tutor-records` объявляет поле необязательным, и менять это в данном change'е — лишний BREAKING.

### D3. Границы операций — в зоне педагога, результат — в UTC

Ключевое правило: **любая граница вычисляется как настенное время, потом переводится**. Не наоборот.

```
неделя:   monday 00:00 local --to_utc--> start
          monday+7 00:00 local --to_utc--> end      (не start + 7 дней!)
день:     day 00:00 local --to_utc--> start
          day+1 00:00 local --to_utc--> end
```

`week.week_bounds` сейчас делает `datetime.combine(monday, time.min)` и `+ timedelta(days=7)` — оба шага заменяются. Прибавление `timedelta` к UTC-значению сломало бы неделю, в которую попадает переход на летнее время.

*Альтернатива*: хранить ещё и локальную дату отдельной колонкой (`starts_on: Date`) и фильтровать по ней. Отвергнуто: денормализация, которую нужно синхронизировать при каждом переносе и правке, ради экономии одного `BETWEEN` по индексу `starts_at`.

### D4. `ScheduleEvent` остаётся плоским, но меняет смысл полей

```python
@dataclass(frozen=True)
class ScheduleEvent:
    starts_at: datetime      # aware UTC — источник истины
    ends_at: datetime        # aware UTC
    day: date                # ЛОКАЛЬНАЯ дата педагога
    start: time              # ЛОКАЛЬНОЕ время
    end: time                # ЛОКАЛЬНОЕ время
    ...
```

`day`/`start`/`end` заполняются один раз в `week_days.build_week_days`, где зона уже известна. `presentation.build_event_view`, `layout_events` и шаблон продолжают работать с `start`/`end` и не знают про зоны.

*Почему не «вычислять при рендере»*: `layout_events` сортирует и ищет пересечения по `start`/`end`; если сделать их методами, каждый вызов тащил бы зону через всю раскладку. Один расчёт на событие дешевле и оставляет `presentation` чистым.

*Что меняется в `presentation`*: `is_overdue`/`is_past` сравнивают `ends_at`/`starts_at` (aware UTC) с `now` (aware UTC) вместо сборки `datetime.combine(event.day, event.end)` — хелпер `_as_datetime` удаляется. Это устраняет целый класс ошибок: раньше «прошло» зависело от того, что `now` и время урока были в одном (наивном) кадре.

### D5. Генератор серий остаётся в настенном времени

`series_generator.generate_occurrences` принимает и возвращает **наивное локальное** время; это чистая функция без зон, её тесты не меняются по смыслу. `lesson_writer` конвертирует:

```
data["starts_at"] (local naive из формы)
   -> generate_occurrences(...) -> [local naive, ...]
   -> [to_utc(x, tutor) for x in ...] -> уроки
```

*Почему не перевести генератор на aware*: `starts_at.date()` и `weekday()` внутри генератора — это операции над локальной датой; на aware-UTC они дали бы сдвиг дня недели (серия «по четвергам» стала бы «по средам» у педагога в UTC+04). Держать генератор в настенном времени — значит сохранить его смысл: «уроки в 10:00 по местным часам каждую неделю».

*Следствие для DST*: каждая дата конвертируется отдельно, поэтому серия, пересекающая перевод часов, даёт разные UTC-значения при одинаковом настенном 10:00 — это и есть требуемое поведение.

### D6. Ввод: перевод в момент разбора формы

`lesson_form.parse_lesson_form` и `homework_form.parse_homework_form` получают `tutor` и сразу возвращают aware UTC. Дальше по цепочке (`lesson_writer`, `homework_writer`, `move`-вьюха) время уже в UTC — ни один сервис не переводит повторно.

Обратный путь — только в `presentation`/контексте формы: `_input_datetime(lesson.starts_at)` → `_input_datetime(to_local(...))`.

*Альтернатива*: конвертировать на границе вьюхи. Отвергнуто: разбор формы уже отдаёт словарь `data`, и если перевод оставить вьюхе, легко забыть один из четырёх путей (создание, создание серии, правка, перенос).

### D7. «Сейчас» и «сегодня» — только с сервера

- Вьюхи передают `now=now_local(tutor)` в `build_calendar_context` и `today=today_local(tutor)` в фильтры/панель недоступности.
- `#calendar-swap` получает `data-now="<ISO локального момента>"`; `calendar.js` читает его вместо `new Date()` (`todayIso`, `prefillMoment`). Атрибут обязателен — это контракт, закреплённый тестом разметки.
- `/time` (htmx-часы в кабинете) форматирует время в зоне вошедшего репетитора; без сессии — системная зона (эндпоинт не должен отдавать 303 в фрагмент).

### D8. Миграция: сдвиг на смещение зоны-источника

Одна ревизия Alembic, три шага:

1. **Источник смещения**: переменная окружения `MIGRATION_SOURCE_TZ`, иначе системная зона сервера. Значение пишется в лог миграции — иначе результат невоспроизводим и непроверяем.
2. **`lessons.starts_at`, `homework.due_at`**: каждое значение трактуется как настенное в зоне-источнике (`replace(tzinfo=zone)`), переводится в UTC и сохраняется. Перевод **по каждой строке**, а не единым смещением: строки из разных сезонов могут попадать по разные стороны перехода на летнее время.
3. **`tutors.timezone`**: всем строкам проставляется зона-источник.

Инвариант приёмки: **после миграции отображение не меняется ни на минуту**. Проверяется тестом: строка «22.10 10:15» до и после показывает 10:15 при той же зоне педагога.

*Почему не «оставить как есть и объявить UTC»*: это сдвинуло бы все существующие уроки на +04 и сломало бы расписание 66 уроков в рабочей базе.

*Downgrade*: обратный перевод UTC → зона-источник, `tutors.timezone` → `NULL`. Полный откат данных, а не только схемы.

*Альтернатива*: две миграции (данные и зона отдельно). Отвергнуто: между ними состояние «уроки уже UTC, зона ещё NULL» даёт неверный показ, а откат становится двухшаговым.

### D9. Регистрация получает зону сразу

`tutor/views/register.py` пишет `timezone=system_zone()` при создании карточки. Иначе новый репетитор снова окажется с `NULL`, и следующий change будет наследовать ту же дыру.

## Risks / Trade-offs

- **[SQLite теряет `tzinfo` — наивное значение может утечь в сравнение]** → Все чтения нормализуются `as_utc()`; `ScheduleEvent` держит aware-значения с момента сборки; тест на урок около полуночи и тест «прошло/не прошло» строятся на aware-значениях.
- **[182 упоминания `starts_at`/`due_at` в 8 файлах тестов]** → Фабрики и тесты переводятся на хелпер `local_dt(tutor, ...)`, который сразу даёт aware UTC; тесты, где время не важно, продолжают передавать наивное значение и получают его же в UTC-кадре через `to_utc`.
- **[Неверное предположение о зоне-источнике миграции]** → Зона печатается в лог; `MIGRATION_SOURCE_TZ` переопределяет; инвариант «отображение не изменилось» проверяется тестом на копии данных, а не на глаз.
- **[Смена зоны педагога «двигает» всё расписание]** → Это требуемое поведение (`tutor-timezone`: «смена зоны меняет только отображение»), но пользователю оно может быть неочевидно. Пока UI смены зоны нет, риск теоретический; при появлении профиля понадобится предупреждение в форме.
- **[DST-ловушка в генераторе серий]** → Генератор остаётся в настенном времени, конвертация по каждой дате; тест на серию через перевод часов.
- **[Несуществующий/двоящийся час при вводе]** → `zoneinfo` трактует несуществующее время по `fold=0` без ошибки; ввод не отклоняется. Это осознанный компромисс: отказ в создании урока «в 02:30 в ночь перевода» был бы хуже, чем час сдвига.
- **[Инвариант «ничего не изменилось» не покрывает бейдж зоны]** → Бейдж появится у всех — перечислено в proposal как намеренный эффект; тесты календаря обновляются вместе с ним.

## Migration Plan

1. Выкатить код и миграцию вместе: код, читающий aware-значения, на старой (наивной) базе покажет время как UTC, то есть со сдвигом. Простой на время миграции — приемлемо для self-hosted.
2. `uv run alembic upgrade head` — сдвиг данных и заполнение зоны; зона-источник видна в выводе.
3. Проверка: открыть список уроков и календарь, сверить два-три урока со старым скриншотом/записью.
4. Откат: `alembic downgrade -1` возвращает и данные, и `tutors.timezone`.
