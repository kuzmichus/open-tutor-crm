# Design

## Context

Каналов доставки в проекте нет. Хранение настроек — таблица `tutor_settings` (одна широкая строка на репетитора, change `tutor-profile-settings`); она заточена под фиксированный набор колонок и не годится для растущего списка параметров (токены трёх мессенджеров и будущие настройки). Внешних HTTP-клиентов в основных зависимостях нет; фронтенд проекта работает без сборщиков и CDN.

## Goals / Non-Goals

- Goals: единая точка отправки `send_message(messenger, recipient, text)`; статусы подключения репетитора; Telegram через Bot API; страница `/tutor/settings` с вкладкой «Мессенджеры»; расширение на MAX/VK без изменения вызывающего кода.
- Non-Goals: отправители MAX и VK (реестр готов, реализации — отдельные изменения); вебхуки и входящие сообщения; рассылки ученикам из UI; асинхронная очередь отправки; проверка токена запросом `getMe` при сохранении (страница не должна зависеть от сети).

## Decisions

### D1. Параметры репетитора — KV-таблица `tutor_params`
Колонки: `tutor_id` (FK, CASCADE) + `key` (String(100)) + `value` (Text), составной PK `(tutor_id, key)`. Одна строка на пару «репетитор + параметр»: новый параметр — новая строка, миграции на каждый параметр не нужны. Ключи мессенджеров — `<мессенджер>_token` (например `telegram_token`); имя ключа строит `token_key()` модуля messenger, вызывающий код литералов не пишет. Широкая `tutor_settings` остаётся для колонок с дефолтами и CHECK-инвариантами; KV — для секретов и опциональных параметров.

### D2. Реестр отправителей — Python-декоратор
`@register_sender("telegram")` над классом отправителя кладёт его в реестр модуля; `send_message` диспетчеризует по имени мессенджера. Новый мессенджер = новый файл с классом и декоратором, существующий код отправки не меняется. Закрытый список `MESSENGERS = ("telegram", "max", "vk")` с подписями — источник истины для страницы и для фильтрации «подключённых» (правило закрытых списков; DB-CHECK не нужен — в KV-таблице нет колонки мессенджера, ключи валидируются на уровне сервиса).

### D3. Сквозное поведение — классы-декораторы (GoF)
Базовый интерфейс `Sender.send(config, recipient, text)` (Protocol, ошибки — `SendError`). Обёртки:
- `LoggingSender` — пишет в logger результат (успех/ошибка, получатель в обезличенном виде);
- `RetrySender` — повторяет отправку при `SendError` фиксированное число попыток.

`send_message` собирает цепочку `LoggingSender(RetrySender(ConcreteSender()))`. Поведение наращивается обёртками без правки конкретных отправителей — это и есть декоратор поверх реестра из D2.

### D4. Telegram — Bot API на stdlib `urllib`
`POST https://api.telegram.org/bot<token>/sendMessage` с JSON `{chat_id, text}`; получатель — chat_id (число строкой или `@username` канала). `urllib.request` вместо httpx: ноль новых зависимостей, один запрос на отправку. Ответ `{ok: false}` и сетевые ошибки превращаются в `SendError` с описанием от Telegram.

### D5. «Подключён» = токен сохранён
`is_messenger_connected` / `connected_messengers` читают KV: непустой токен — подключён. Проверка сети (`getMe`) не выполняется ни при сохранении, ни при чтении статуса: страница настроек должна рендериться без доступа в сеть, а реальная валидность токена проявится при первой отправке (ошибка придёт списком от `send_message`).

### D6. Страница `/tutor/settings` — по образцу `/tutor/profile`
Серверные вкладки через `?tab=` (сейчас одна — «Мессенджеры»), форма без JS, POST при ошибке ре-рендерит вкладку, при успехе — 303 на `?tab=…&saved=1`. Пустой токен в форме означает отключение: параметр удаляется из KV, а не сохраняется пустой строкой — иначе «подключён» пришлось бы определять как «значение непустое» в каждом месте чтения. Формат токена валидируется regex (`id:секрет`), заодно принимается вставка ссылки `https://api.telegram.org/bot<token>` — токен извлекается.

### D7. Пункт сайдбара «Настройки» ведёт на `/tutor/settings`
`/tutor/profile` остаётся как есть (доступен из футера сайдбара); подсветка активного пункта на нём не меняется — правки профиля вне этого change'а.

## Risks / Trade-offs

- KV без CHECK на ключах: мусорный ключ возможен технически, но запись идёт только через сервисы с фиксированным набором ключей.
- `RetrySender` без задержки между попытками: сбои Bot API обычно мгновенные (сеть/токен), пауза усложнила бы тесты; при необходимости добавляется параметром.
- Синхронная отправка в вызывающем коде: таймаут `urllib` ограничен (10 c); очередь отправки — вне объёма.
- Две страницы настроек (`/tutor/settings` и `/tutor/profile`) сосуществуют: временная издержка решения «профиль не трогаем».
