# Design

## Context

См. proposal.md — Why. Факты из кодовой базы, которые определяют подход:

- `app/student/models/student.py` — заготовка: `id INTEGER PK`, `name`, `email` (unique, not null), `created_at`. В `tutor.db` таблица `students` пуста (0 строк), а эндпоинта создания ученика нет — значит пересборку таблицы можно делать начисто, без логики переноса данных.
- `app/student/views/index.py` — `GET /students` отдаёт `db.scalars(select(Student)).all()` **без проверки сессии**. Это единственная существующая точка доступа к ученикам и она публична.
- Авторизация уже есть: `SessionService.get_tutor_id_from_request(db, request)` (`app/tutor/services/sessions.py`) возвращает `tutor_id` или `None`. В кабинете (`app/tutor/views/home.py`) редирект на вход реализован именно так — повторяем этот приём, а не вводим новый.
- В `app/database.py` нет обработчика события `connect`, поэтому `PRAGMA foreign_keys` остаётся выключенным: объявленные FK в `tutor_sessions` и `tutor_password_reset_tokens` сейчас не проверяются. Нужно исправить до того, как появятся настоящие связи.
- В проекте нет ни одного `relationship()`. Связи существуют только как FK-колонки, запросы пишутся через явные `select()`/`join()`. Это стиль проекта, и его надо сохранить, иначе появятся два способа ходить по графу.
- `app/static/` содержит только `app.js`, `htmx.min.js` (v1.9.12), `lucide.min.js` и `styles.css`. Alpine.js отсутствует. `app/static/dist/app.css` — мёртвый Tailwind-артефакт, на который никто не ссылается (и который ссылается на несуществующий каталог `static/fonts/`).
- `styles.css` — нативный CSS с `@layer`, CSS Nesting и токенами. Уже есть `.btn`, `.btn--primary/--ghost/--brand/--destructive/--icon/--block`, `.card`, `.chip`, `.tabs`, `.tab`, `.field`, `.label`, `.input`, `.page-header` (колонка), `.main__container`, `.profile-grid`. Утилиты минимальны: `.flex`, `.items-center`, `.flex-wrap`, `.gap-2`, `.mt-4`, `.mt-5`, `.hidden`, `.truncate`, `.sr-only`.
- Тест `tests/test_css_styles.py` запрещает BEM-конкатенацию через `&__` (нативный CSS её выбрасывает) и проверяет баланс скобок — новые правила должны это соблюдать.
- `tests/conftest.py` содержит только `tutor_factory`; фабрики ученика нет.

## Goals / Non-Goals

**Goals:**

- Схема, в которой ученик принадлежит репетитору, взрослые контакты переиспользуются между учениками, а «кто платит» и «кому напоминать» выражаются на связи, а не копированием полей.
- Работающая проверка ссылочной целостности на уровне БД, а не только на бумаге.
- Закрытие публичного `/students` и скоуп по `tutor_id` на всех маршрутах модуля.
- Страница списка и карточка в стиле референса, но на реальных данных, с честными заглушками вместо несуществующих метрик.
- Соответствие AGENTS.md: один класс — один файл, по одному эндпоинту на файл вьюхи, миграция через Alembic, зелёные тесты.

**Non-Goals:**

- Модули уроков, оплат, задолженности и отчётов — их блоки остаются заглушками (см. спеку `student-management`).
- Импорт учеников из файла: кнопка «Импорт» в референсе не реализуется.
- Множественные педагоги и «ответственный менеджер»: ученик принадлежит одному репетитору, ролей в системе нет.
- Физическое удаление учеников — только архивирование.
- Отправка напоминаний: сохраняются только настройки, планировщика и доставки нет.
- Хранение истории изменений карточки и аудит.

## Decisions

### D1. Схема: `students` + `contacts` + `student_contacts`

```
tutors 1 --- N students            students.tutor_id      NOT NULL
tutors 1 --- N contacts            contacts.tutor_id      NOT NULL
students N --- N contacts          через student_contacts
students.payer_contact_id --> contacts.id   (nullable = платит сам)
```

`students`:

| Колонка | Тип | Правила |
|---|---|---|
| `id` | `String(36)` PK | uuid4, генерируется в Python |
| `tutor_id` | `String(36)` FK → `tutors.id` | NOT NULL, `ON DELETE CASCADE` |
| `first_name` | `String(100)` | NOT NULL |
| `last_name` | `String(100)` | nullable |
| `phone` | `String(32)` | nullable, не уникален |
| `email` | `String(255)` | nullable, **не** уникален, индекс для поиска |
| `kind` | `String(8)` | NOT NULL, `CHECK IN ('child','adult')` |
| `grade` | `Integer` | nullable, `CHECK BETWEEN 1 AND 11` |
| `school` | `String(255)` | nullable |
| `level` | `String(100)` | nullable, свободный текст |
| `notes` | `Text` | nullable |
| `status` | `String(10)` | NOT NULL, default `'new'`, `CHECK IN ('new','active','archived')` |
| `timezone` | `String(64)` | nullable |
| `remind_lesson` | `Boolean` | NOT NULL, default `false` |
| `remind_homework` | `Boolean` | NOT NULL, default `false` |
| `remind_cancel` | `Boolean` | NOT NULL, default `false` |
| `payer_contact_id` | `String(36)` FK → `contacts.id` | nullable, `ON DELETE SET NULL` |
| `created_at` | `DateTime(timezone=True)` | NOT NULL |
| `updated_at` | `DateTime(timezone=True)` | NOT NULL, обновляется при изменении |

`contacts`: `id` (uuid4), `tutor_id` (FK, NOT NULL), `full_name` (NOT NULL), `phone`, `email`, `timezone`, `created_at`.

`student_contacts`: `id` (uuid4), `student_id` (FK → `students.id`, NOT NULL), `contact_id` (FK → `contacts.id`, NOT NULL), `relation` (`String(50)`, nullable — свободный текст), `remind_lesson`/`remind_homework`/`remind_cancel` (Boolean, default false), плюс `UNIQUE(student_id, contact_id)`.

Почему напоминания на связи, а не на контакте: одна мама двух детей может получать напоминания о домашке по младшему и не получать по старшему — это выразимо только на паре «ученик — контакт».

Почему часовой пояс и на контакте, и у ученика: часовой пояс нужен для момента отправки сообщения, а получателем может быть и сам ученик (взрослый без контактов). Симметричный набор полей у `students` и `contacts` позволяет строить запрос получателей как UNION двух веток с одинаковыми колонками.

Почему «плательщик» — колонка `payer_contact_id`, а не флаг `is_payer` на связи: одна nullable-колонка заменяет флаг плюс частичный уникальный индекс, а «платит сам» выражается как `NULL`. Минус — целостность «плательщик должен быть привязан к этому ученику» обычным FK не выражается (см. D3).

### D2. Включение `PRAGMA foreign_keys = ON`

В `app/database.py` добавляется слушатель события подключения:

```python
@event.listens_for(Engine, "connect")
def _enable_sqlite_foreign_keys(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.close()
```

Альтернативы: `connect_args={"foreign_keys": True}` — не поддерживается драйвером `sqlite3`; pragma в каждом запросе — дорого и легко забыть. Слушатель на классе `Engine` покрывает и dev-базу, и in-memory базу в тестах.

Следствие: FK начинают **реально** работать, включая существующие таблицы сессий и ключей восстановления. Это не регрессия, а исправление, но тесты, которые сейчас опираются на возможность вставить сессию с несуществующим `tutor_id`, придётся проверить.

### D3. Проверка «плательщик привязан к ученику» — в сервисе, а не составным FK

Составной FK `(id, payer_contact_id) → student_contacts(student_id, contact_id)` выразил бы ограничение точно, но включил бы `students.id` в FK-граф и сделал каскадное удаление зависимым от порядка удаления строк в `student_contacts`. При только что включённой pragma это лишний источник тонких поломок.

Принято: проверка в сервисе сохранения карточки — `payer_contact_id` обязан входить в набор `contact_id` привязок этого ученика; иначе ошибка валидации. В интерфейсе выбор строится только из привязанных контактов, поэтому пользователь не может выбрать непривязанного. Покрывается тестом.

### D4. Миграция: пересборка `students` начисто + создание двух таблиц

`students` содержит 0 строк, а эндпоинта создания нет — значит логика переноса не нужна. Порядок в одной ревизии после `f7c3a1d92b6e`:

1. `contacts` — новая таблица + индексы по `tutor_id`, `phone`, `email`.
2. `student_contacts` — новая таблица + `UNIQUE(student_id, contact_id)` + индексы по `student_id`, `contact_id`.
3. `students` — `create_table('students_new', ...)`, перенос `id/name/email/created_at` из старой таблицы (если строки всё же есть: `name` → `first_name`, `kind` = `'child'` как безопасное значение по умолчанию, `status` = `'new'`, `tutor_id` — **проблема**, см. ниже), `drop_table('students')`, `rename_table`, индексы.

Проблема с `tutor_id` для гипотетических старых строк: заполнить его нечем, потому что у прежней таблицы владельца не было. Варианты: (а) падать, если строки есть; (б) подставлять единственного репетитора, если он ровно один; (в) удалять строки. Принято **(б) с откатом на (а)**: если строк нет — миграция проходит молча; если строки есть и репетитор ровно один — все привязываются к нему; иначе миграция останавливается с явной ошибкой, чтобы данные не «улетели» к случайному владельцу. В текущей базе ветка не выполняется, но код пишется, потому что база разработчика может отличаться.

`downgrade()` возвращает старую схему `students` (id INTEGER, name, email unique) и удаляет `student_contacts`, затем `contacts`. Данные контактов при откате теряются — фиксируется комментарием в миграции.

### D5. Проверка сессии и скоуп — зависимость FastAPI, а не копипаста

Новая зависимость в `app/student/services/access.py` (или рядом с вьюхами) возвращает `tutor_id` либо прерывает запрос редиректом. Все вьюхи модуля используют её и **никогда** не берут `tutor_id` из формы или query-параметра.

Ключевое правило: любой запрос по конкретному ученику строится как `select(Student).where(Student.id == id, Student.tutor_id == tutor_id)`. Отсутствие строки и «чужой ученик» дают одинаковый ответ (404) — спека требует не раскрывать существование чужой записи.

Альтернатива — отдельный middleware, проверяющий сессию для префикса `/students`. Отвергнута: middleware не даёт `tutor_id` в обработчик, и его пришлось бы доставать повторно, то есть сессия проверялась бы дважды.

### D7. Alpine.js: локальный файл, `defer`, обычная сборка

- `app/static/alpine.min.js` кладётся в репозиторий (AGENTS.md: без CDN). Подключается в `base.html` с `defer` после htmx.
- Alpine инициализирует узлы через MutationObserver, поэтому карточки и формы, вставленные htmx, получают `x-data` без ручной переинициализации.
- В `styles.css` обязательно `[x-cloak] { display: none !important; }` — иначе модалка мигнёт до инициализации.
- Обычная (не CSP) сборка использует `new Function`. CSP в проекте нет; ограничение фиксируется здесь, чтобы при появлении заголовка `Content-Security-Policy` не искать причину «молча не работает Alpine».
- Alpine отвечает **только** за клиентское состояние: открыта ли модалка, активный таб формы, сегмент «ребёнок/взрослый», раскрыта ли панель фильтров, вид сетка/список (с сохранением в `localStorage`). Никакой серверной логики в `x-data`.
- `app.js` остаётся как есть (сайдбар, тема, lucide) — его декларация «минимальный JS» не расширяется: новый интерактив идёт через Alpine.

Альтернатива — ванильный JS в `app.js` с ручной переинициализацией после каждого htmx-свопа. Отвергнута: это ровно тот код, который Alpine уже написал, и он быстро разъедется с разметкой.

### D8. Классы CSS: следуем существующей дизайн-системе, а не референсу

Референс написан на другой системе классов (`.btn-primary`, `.badge`, `.hide-sm`, `.grow`, `.span-2`, `.page-container`). Переименовывать существующее нельзя — на `.btn--primary` завязаны тесты (`tests/test_ui_polish.py`) и все страницы авторизации. Соответствие:

| Референс | Проект |
|---|---|
| `.btn-primary` | `.btn.btn--primary` |
| `.btn-outline` | `.btn.btn--ghost` + новый модификатор `.btn--outline` (рамка) |
| `.btn-sm` | `.btn--sm` |
| `.badge*` | `.chip` + `.chip--new` / `.chip--active` / `.chip--archived` |
| `.page-container` | `.main__container` (не дублируем) |
| `.page-header` (row) | `.page-header--row` (модификатор: `flex-direction: row`, `justify-content: space-between`) |
| `.hide-sm` | `.hide-sm` (новая утилита, `display:none` до 640px) |
| `.grow`, `.flex-1`, `.span-2`, `.justify-between` | `.grow`, `.flex-1`, `.span-2`, `.justify-between` (дописать) |
| `.students-grid`, `.student-card`, `.student-head`, `.student-contacts`, `.student-metrics`, `.student-actions` | те же имена, новые правила |
| `.modal-root`, `.modal-overlay`, `.modal-content` | те же имена, новые правила |

Новые правила пишутся в `@layer components` (компоненты) и `@layer utilities` (утилиты), с токенами из `:root` — никаких литеральных цветов из референса (`#e4e3df`, `#1f1f24`), только `var(--border)`, `var(--primary)` и т.д., иначе тёмная тема сломается. Брейкпоинты референса (1024px, 640px) совпадают с проектными.

Проверка на BEM-конкатенацию обязательна: `&__head` внутри `.student-card` браузер выбросит, тест `test_no_bem_concatenation_nesting` это поймает. Поэтому все селекторы плоские.

### D9. Ленивый поиск контакта

`GET /tutor/students/contacts/lookup?phone=...&email=...` возвращает HTML-фрагмент подсказки. Нормализация: телефон — только цифры; email — `strip().lower()`. Поиск ограничен `contacts.tutor_id == tutor_id`. Если найденный контакт уже привязан к ученику (передаётся `student_id`), подсказка не предлагает привязку, а сообщает «уже добавлен».

Сравнение телефонов по цифрам намеренно игнорирует формат `+7 555 555-55-55` / `8 555 555 55 55`. При сохранении номер приводится к единому виду `+7 555 555-55-55` (серверный `services/phone.py`, тот же алгоритм продублирован в `students.js` для форматирования по мере набора), а для сравнения всё равно берутся только цифры. Значения, не похожие на российский номер (больше 11 цифр, чужой код страны, посторонние символы вроде `доб. 12`), сохраняются как введены: шаблон не навязывается, чтобы не терять часть ввода.

Альтернатива — уникальный индекс на нормализованный телефон. Отвергнута: пользователь явно решил, что телефоны и почта не уникальны, и дубликаты в CRM легитимны (тёзки, общий номер у сиблингов).

### D10. Заглушки вместо фиктивных метрик

Блоки «Проведено», «0 ₽», дата следующего урока и кнопки «Уроки»/«Отчёт» из референса **не** отрисовываются с числами. Вместо них — серая плашка с текстом о том, что данные появятся позже. Причина: «0 ₽» читается как утверждение «долга нет», а это ложное утверждение при отсутствии модуля оплат. Кнопки без обработчиков не выводятся вовсе (не `hx-get` на несуществующий маршрут, не `href="#"`).

Кнопка «Импорт» из референса не выводится: импорта нет.

### D11. Тесты

- Переписать `tests/test_pages.py`: `/students` без входа → 303 на `/tutor/login`; со входом → 200 и только свои ученики.
- Добавить `student_factory` и `contact_factory` в `tests/conftest.py` по образцу `tutor_factory`.
- Новые файлы тестов: изоляция между репетиторами (список, карточка, поиск контактов), валидация формы (имя, класс 1–11, плательщик не привязан), архивирование и возврат, напоминания на связи, переиспользование контакта двумя учениками, каскадное удаление контакта, отсутствие нерабочих ссылок на странице (проверка, что в HTML нет `/tutor/students/{id}/lessons`).
- Тест `test_css_styles.py` расширяется проверкой, что классы из новых шаблонов описаны в `styles.css` (по образцу существующего параметризованного теста для `404.html` и `auth.html`).
- Тест миграции данных не пишется: in-memory `create_all` не проходит через Alembic. Перенос проверяется вручную по шагам Migration Plan.

## Risks / Trade-offs

- [Включение FK-прагмы может сломать существующие тесты, где вставляются строки с «висячими» FK] → прогнать полный набор сразу после включения pragma, до написания новых моделей; починить тестовые данные, а не отключать проверку.
- [`ON DELETE SET NULL` на `students.payer_contact_id` может обнулить плательщика незаметно для пользователя] → удаление контакта в UI сопровождается подтверждением, где перечислены ученики, у которых он был плательщиком; тест проверяет, что плательщик стал `NULL` (то есть «платит сам ученик»), а не остался битой ссылкой.
- [Свободный текст в `relation` и `level` допускает мусор и опечатки] → осознанный выбор пользователя; нормализация не вводится, чтобы не мешать («мама», «Мама», «мать» остаются разными).
- [Alpine обычной сборки несовместим со строгим CSP] → CSP в проекте нет; ограничение записано в D7, при появлении заголовка потребуется `@alpinejs/csp` и переписывание компонентов на `Alpine.data()`.
- [Отсутствие `relationship()` делает выборку контактов многословной] → стиль проекта сохраняется намеренно; сложные выборки инкапсулируются в сервисах, а не растекаются по шаблонам.
- [`student_contacts` без `relationship` требует явного `join` при каждой отрисовке карточки] → для списка учеников контакты подгружаются одним запросом с `join` и группировкой в Python, чтобы не получить N+1.
- [Референс предполагает три таба в форме («Общее», «Платежи», «Настройки»), а данных у нас на один] → форма делается одним экраном с секциями, без пустых табов; если секции станут длинными, табы добавляются позже без изменения схемы.
- [Кнопка «Удалённые» и фильтр `archived` могут восприниматься как удаление] → в интерфейсе используется слово «Архив», а действие называется «В архив» / «Вернуть из архива».

## Migration Plan

1. Бэкап dev-базы: `cp tutor.db tutor.db.bak` (если файл есть).
2. Включить `PRAGMA foreign_keys=ON` в `app/database.py`, прогнать `uv run pytest` — убедиться, что существующие тесты не сломались.
3. Применить миграцию: `uv run alembic upgrade head`. Проверить `PRAGMA foreign_key_check` — пустой результат.
4. Проверить обратимость: `uv run alembic downgrade -1` и `uv run alembic upgrade head`.
5. Ручная проверка в браузере: вход → `/tutor/students` → создание ребёнка с мамой и бабушкой → назначение плательщика → переиспользование мамы у второго ученика → архив и возврат.
6. Откат: `uv run alembic downgrade f7c3a1d92b6e` (таблицы контактов удаляются, данные контактов теряются) либо восстановление бэкапа.
