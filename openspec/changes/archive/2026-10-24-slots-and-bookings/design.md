# Design

## Context

См. `proposal.md` — Why. Состояние кода, формирующее подход:

- **Демо-слой полностью в браузере.** `calendar.js` держит `slotForm`, `booking`, `modal` и создаёт карточку через `renderCard({kind: "slot"})`; `_area.html` содержит разметку двух диалогов и `<template id="cal-event-template">`. Сетевых запросов нет вовсе — тест `test_calendar_slot_creation_static` это прямо закрепляет (`assert "fetch(" not in js`).
- **Календарь уже собирает события в один список.** `ScheduleDay.events: tuple[ScheduleEvent, ...]`, а `layout_events` раскладывает пересечения по колонкам. Это готовая точка входа для окон (design D8 предыдущего обсуждения: вариант «A»).
- **`ScheduleEvent` не имеет признака вида.** Есть `lesson_id`, и пустой id отличал демо-слот от урока — после удаления демо этого признака не хватает, нужен явный `kind`.
- **Недоступность уже в БД** (`tutor_unavailability`, `coverage_for_week`, `unavailability_warning`), и `unavailability_check` показывает, как модуль `lesson` зависит от `unavailability` односторонне.
- **XOR-инвариант урока.** `ck_lessons_target_xor`: ровно одна цель, `student_id` XOR `group_id`. Значит подтверждение брони обязано иметь ученика — создать его или найти.
- **У серии уроков запись атомарна** (`lesson_writer.create_series`: «либо все записи, либо ничего»). Пачка окон по требованиям наоборот частичная — это осознанное расхождение, его нельзя «выровнять» при рефакторинге.
- **Требуется предыдущий change.** `store-datetimes-in-utc` даёт UTC-хранение и `app/common/services/tutor_time.py`. Окна без него считать нельзя: пересечение окна с уроком бессмысленно, если урок наивный. Этот change — блокирующий предшественник.
- **У `Tutor` нет слага и публичного токена.** Есть только `uuid4`. Отдельной таблицы ссылок нет, и по решению пользователя не будет.
- **Rate limiting в проекте отсутствует** — ни middleware, ни счётчиков. Публичный POST станет первым неаутентифицированным маршрутом, создающим строки в БД.

## Goals / Non-Goals

**Goals:**

- Один источник истины для «окно занято» — вычисление пересечением, одинаково работающее для календаря и публичной страницы.
- Предпросмотр пачки, который физически не может разойтись с результатом.
- Публичный контур, не раскрывающий данные учеников и не требующий сессии.

**Non-Goals:**

- Страница «Брони» со списком заявок и фильтрами (отдельный change; действия живут в диалоге окна).
- Уведомления ученику (письмо/мессенджер) о подтверждении или отклонении.
- Оплата брони, предоплата, отмена брони учеником по ссылке.
- Повторяющиеся окна как отдельная сущность: пачка материализует окна, серии окон нет.
- Часовой пояс зрителя на публичной странице (показываем зону педагога и подпись).

## Decisions

### D1. Два новых доменных модуля: `app/slot/` и `app/booking/`

```
app/slot/                      app/booking/
├── models/slot.py             ├── models/booking.py
├── services/                  ├── services/
│   ├── access.py              │   ├── access.py
│   ├── slots.py    неделя     │   ├── bookings.py      выборки
│   ├── busy.py     занятость  │   ├── booking_form.py  разбор формы
│   ├── batch.py    пачка      │   ├── booking_writer.py заявка/статусы
│   ├── slot_form.py разбор    │   └── confirmation.py  ученик + урок
│   └── presentation.py        └── views/
├── views/                     └── templates/booking/
└── templates/slot/
```

*Почему два модуля, а не один `booking`*: у них разные владельцы доступа и разные публичные поверхности. Окно — сущность педагога с `tutor_id`; бронь — сущность окна без своего `tutor_id` (владелец выводится через окно, как владелец урока выводится из цели). Слить их значило бы либо дать брони лишнюю колонку, либо завести взаимные зависимости внутри одного модуля.

*Зависимость односторонняя*: `booking` → `slot` → `unavailability`. `slot` не знает про `booking`; календарь знает про оба.

### D2. Модель окон

```
slots
  id            String(36) uuid4
  tutor_id      FK tutors.id CASCADE, index, NOT NULL
  starts_at     DateTime(timezone=True) NOT NULL   -- UTC
  duration_min  Integer NOT NULL  CHECK IN LESSON_DURATIONS
  is_public     Boolean NOT NULL default True
  created_at / updated_at
  UNIQUE(tutor_id, starts_at)
```

`UNIQUE(tutor_id, starts_at)` — дешёвая защита от дубля «то же окно дважды», которую пачка может создать при неаккуратных параметрах. Полное пересечение (14:00 и 14:10) индекс не поймает — его проверяет сервис; уникальность ловит только точное совпадение и не заменяет проверку.

*Альтернатива*: `duration_min` свободным числом. Отвергнуто: требование «как у урока» и CHECK урока (`ck_lessons_duration`) означают, что окно 25 минут сделало бы невозможной запись ученика без округления.

### D3. Модель броней

```
bookings
  id          String(36) uuid4
  slot_id     FK slots.id CASCADE, index, NOT NULL
  name        String(200) NOT NULL
  contact     String(64)  NOT NULL
  status      String(10)  CHECK IN ('pending','confirmed','rejected','cancelled')
  student_id  FK students.id SET NULL   -- заполняется при подтверждении
  lesson_id   FK lessons.id  SET NULL   -- заполняется при подтверждении
  created_at  DateTime(timezone=True)
  decided_at  DateTime(timezone=True) | NULL
```

`SET NULL`, а не `CASCADE`, у `student_id`/`lesson_id`: удаление ученика или урока не должно уничтожать историю заявки. У `slot_id` — `CASCADE`: бронь без окна не имеет смысла.

**Одна активная бронь на окно** держится не только кодом, но и частичным уникальным индексом:

```
CREATE UNIQUE INDEX ux_bookings_active_slot
  ON bookings(slot_id) WHERE status IN ('pending','confirmed')
```

SQLite поддерживает частичные индексы — это тот же приём, что частичный `UNIQUE` вместо проверки в Python: гонка двух одновременных заявок не создаст две активные брони.

### D4. Занятость — вычисление, не колонка

```
busy_kinds(slot) =
  lesson   -> существует урок tutor'а, пересекающийся [slot.start, slot.start+dur)
  booking  -> есть активная бронь (pending | confirmed)
  past     -> slot.start + dur <= now(UTC)
  free     -> иначе
```

Приоритет подписи: `booking` > `lesson` > `past` > `free`. Обоснование: подтверждённая бронь — это договорённость с человеком, её нельзя «спрятать» за словом «прошло»; а урок в прошлом полезнее показывать как «занято уроком» тому, кто разбирается, почему время ушло.

Пересечение для урока считается как `lesson.starts_at < slot_end AND lesson.starts_at + duration > slot_start` — обычное пересечение полуинтервалов, без всякой математики по сетке.

*Почему не хранить*: урок появляется четырьмя путями (форма, серия, перетаскивание, подтверждение брони). Любое хранимое поле `is_busy` пришлось бы обновлять в каждом из них — и оно бы разошлось при первом же пропущенном вызове. Проверка на рендер недели — один `SELECT` уроков недели, который календарь **уже делает** для сетки, то есть дополнительных запросов нет.

### D5. `ScheduleEvent` получает `kind`, раскладка не меняется

```python
@dataclass(frozen=True)
class ScheduleEvent:
    kind: str            # "lesson" | "slot"
    starts_at / ends_at  # aware UTC (из предыдущего change)
    day / start / end    # локальные значения педагога
    slot_id: str = ""    # для kind="slot"
    slot_state: str = "" # free | pending | booking | lesson | past
    lesson_id: str = ""
    ...
```

`build_week_days` собирает уроки и окна в один `events`, поэтому `layout_events` и позиционирование карточек работают без изменений — пересечение окна с уроком раскладывается тем же кодом, что два урока.

*Альтернатива* (отвергнута): отдельный список `day.slots` со своей раскладкой. Тогда окно 14:00 и урок 14:00 нарисовались бы друг на друге — это визуальный баг, который пришлось бы лечить второй копией алгоритма.

### D6. Пачка: один расчёт, два входа

```
slot/services/batch.py
   plan(batch_params, existing)  -> BatchReport(create=[...], skip=[{when, reason}])
   apply(batch_params, db)       -> (created[], report)
   apply вызывает plan() и пишет результат  <- гарантия совпадения
```

Параметры (все приходят из формы, разбор — `slot_form.parse_batch_form`):

```
date_from, date_to, weekdays[], day_start, day_end,
duration_min (из LESSON_DURATIONS), gap_min, is_public
```

Генерация для одного дня:

```
cursor = day_start
while cursor + duration <= day_end:
    emit(cursor)
    cursor += duration + gap          # в настенном времени педагога
```

Шаг считается в настенном времени и только потом переводится в UTC — так пачка через переход на летнее время не «съезжает» (тот же принцип, что в `series_generator`).

Причины пропуска (`skip.reason`): `busy_lesson`, `busy_slot`, `unavailable_day`, `past`. Отчёт отдаёт шаблону человекочитаемые подписи через `presentation.py`.

**Лимит** `MAX_SLOT_BATCH = 200` проверяется на этапе генерации списка, до любых записей: превышение даёт ошибку формы, а не частично созданную пачку.

*Маршруты*: `GET /tutor/slots/plan` (htmx-предпросмотр, `hx-trigger="change, input changed delay:400ms"`) и `POST /tutor/slots/batch`. Оба рендерят один партиал отчёта.

*Почему не считать в JS*: число окон и список пропусков зависят от уроков и отметок недоступности в БД. Дублирование формулы в браузере гарантированно разойдётся — и именно на «занятое время пропустим» пользователь это заметит первым.

### D7. Публичная ссылка: кодирование без таблицы

```
/s/<tutor_id>?start=YYYY-MM-DD
```

`tutor_id` — `uuid4`, перебором не подбирается (122 бита). Неделя — обычный `?start=`, как у календаря: тот же параметр, та же нормализация к понедельнику, никакой новой семантики.

*Что это не даёт и почему принято*: ссылку нельзя отозвать отдельно от окон. Отзыв делается содержимым — снял публичность или удалил окна, страница пуста. Если позже понадобится «закрыть страницу целиком одним действием», добавляется `public_token` в `tutors` — отдельным change'ем, без переделки ссылок (старый формат можно оставить как алиас).

**Неизвестный `tutor_id`** → обычная 404-страница проекта, а не отдельный шаблон: существование чужого аккаунта не раскрывается (тот же принцип, что 404 вместо 403 в `get_owned_*`).

### D8. Публичная страница: что показывается и что скрывается

Выборка — один запрос на неделю с джойнами:

```
slots (public=True, tutor_id)
  LEFT JOIN bookings (active)      -> есть бронь => скрыть
  LEFT JOIN lessons (пересечение)  -> есть урок  => скрыть
  минус прошедшие (now UTC)
  минус дни из coverage_for_week   -> недоступный день
```

В разметку попадают только: дата, день недели, время начала и окончания, кнопка «Записаться». **Ни имён учеников, ни цен, ни заметок** — это отдельное требование спеки, и его проверяет тест на отсутствие подстрок.

Если неделя целиком недоступна — страница показывает причину вместо списка. Причина берётся из `coverage_for_week` (подпись «Отпуск»/«Больничный»/…).

Подпись о поясе — из `tutor_time.tutor_zone(tutor)`; серверный хелпер из предыдущего change'а даёт и fallback, поэтому пустая зона не ломает страницу.

### D9. Подтверждение брони: три исхода, один код

```
confirm(booking, chosen_student_id=None, kind=None)
  1. кандидаты = students(tutor).where(name == slot_name, phone == contact)
       не архивные; сравнение нормализованное (телефон без пробелов/дефисов)
  2. 0 кандидатов  -> создать ученика (нужен kind: child|adult)
     1 кандидат    -> использовать его
     >1 кандидатов -> требуется chosen_student_id (педагог выбирает)
  3. проверить пересечение времени ещё раз (пока бронь ждала, могли поставить урок)
  4. создать Lesson(starts_at=slot.starts_at, duration_min=slot.duration_min,
                    student_id=..., type="individual", status="planned")
  5. booking.status = confirmed, student_id, lesson_id, decided_at
```

Шаг 3 обязателен: между заявкой и подтверждением педагог мог создать урок руками. Без повторной проверки подтверждение создало бы двойную занятость — а `UNIQUE` на уроках нет.

**Сравнение телефонов** делается примитивно и предсказуемо: убрать всё, кроме цифр и ведущего `+`. Иначе «8 999…» и «+7 999…» не совпадут — но и «умное» сравнение российских номеров в этот change не входит: неверное склеивание двух разных людей хуже, чем лишний дубль, который педагог удалит.

### D10. Отмена и отклонение не трогают урок

```
reject(booking)  -> status=rejected, decided_at; окно снова свободно
cancel(booking)  -> status=cancelled, decided_at; урок и ученик остаются
```

Отмена не удаляет урок намеренно: урок мог быть уже проведён или изменён (перенесён, оценён). Педагог решает судьбу урока сам; окно при этом автоматически покажет «Занято уроком» — потому что занятость выводится (D4), а не хранится.

### D11. Удаление и перенос окна

- **Удаление** блокируется при активной брони (`pending`/`confirmed`) — требование пользователя. Проверка в сервисе, а не только в UI: кнопка может быть недоступна, но запрос всё равно придёт.
- **Перенос** меняет `starts_at`; бронь не трогается — она ссылается на окно по id, поэтому «едет» вместе с ним. Пересечение проверяется на новом времени; при конфликте перенос отклоняется.
- Перенос в недоступный день спрашивает подтверждение — тем же механизмом `ack_unavailable`, что и перенос урока (`lesson/views/move.py`), чтобы не изобретать второй способ подтверждения.

### D12. Ограничение частоты заявок

Публичный POST — единственный неаутентифицированный маршрут, создающий строки. Реализация без новых зависимостей: счётчик в SQLite по ключу «окно + грубый отпечаток клиента»:

```
booking_attempts(key, window_start, count)   -- ключ: sha256(slot_id + ip)
   окно: 10 минут, лимит 5 заявок
```

`booking_attempts` — отдельная таблица, чистится при каждом обращении (строки старше суток удаляются). Это не заменяет полноценный rate limiting, но закрывает сценарий «одна ссылка в чате и сотня заявок».

*Альтернатива* (отвергнута): honeypot-поле в форме. Ловит ботов, но не человека, который нажал пять раз. Обе меры не исключают друг друга — honeypot можно добавить позже без изменения модели.

*Альтернатива* (отвергнута): внешний сервис/Redis. Проект self-hosted на SQLite; лишняя зависимость ради счётчика неоправдана.

### D13. Удаление демо-слоя

Удаляется: `slotForm`, `_bookingSlot`, `booking`, `modal`, `openSlotDialog`, `createSlot`, `closeBooking`, `openBooking`, `confirmBooking`, ветка `kind === "slot"` в `renderCard`, `<template id="cal-event-template">` (если после удаления демо он больше не нужен — проверить при реализации), разметка двух диалогов, классы `.cal-event--slot`, `.cal-event--booked`, `.cal-event__book`, `.cal-event__state`, тесты 6-го раздела `tests/test_calendar.py`.

Токен `--cal-slot-accent` **сохраняется**: цвет окна остаётся фирменным, меняется только источник данных.

## Risks / Trade-offs

- **[Пересечение считается на каждый рендер недели]** → Уроки недели календарь уже выбирает одним запросом; окна добавляют второй. Пересечения считаются в Python по уже загруженным строкам, без N+1. При росте объёма — индекс `(tutor_id, starts_at)` на `slots`.
- **[Публичный POST без полноценной защиты]** → Лимит попыток (D12) + обязательная проверка, что окно публичное, свободное и не прошедшее. Осознанно не берём капчу: она ухудшает конверсию записи, а объём атаки на self-hosted несопоставим.
- **[Дубль ученика при несовпадении формата телефона]** → Принято как меньшее зло; педагог видит имя и контакт в диалоге и может выбрать существующего ученика вручную (исход «>1 кандидатов» уже требует выбора).
- **[Гонка двух заявок на одно окно]** → Частичный уникальный индекс `ux_bookings_active_slot` (D3) — БД откажет второй, сервис покажет «время уже занято».
- **[Подтверждение может создать урок на занятое время]** → Повторная проверка пересечения в шаге 3 (D9) до создания урока.
- **[Окно с бронью нельзя удалить, а бронь отменить негде, пока нет страницы «Брони»]** → Действия Подтвердить/Отклонить/Отменить живут в диалоге окна на календаре (D6 календарной дельты). Это осознанное промежуточное решение, страница «Брони» станет вторым входом.
- **[Часовой пояс зрителя не учитывается на публичной странице]** → Показываем зону педагога и подпись «Обратите внимание, время указано: …». Если ученик в другом поясе, он видит честное предупреждение, а не молчаливое расхождение.
- **[`UNIQUE(tutor_id, starts_at)` может помешать легитимному сценарию]** → Два окна в одну минуту у одного педагога смысла не имеют; конфликт возвращается как ошибка формы с понятным текстом.
- **[Пачка частичная, серия уроков атомарная]** → Расхождение осознанное: записано в design и в спеке («Одна опечатка не отменяет пачку»), чтобы при будущем рефакторинге его не «выровняли».

## Migration Plan

1. **Предусловие**: `store-datetimes-in-utc` уже применён (UTC-хранение, `tutor_time`, зона педагога).
2. Миграция Alembic: `slots`, `bookings`, `booking_attempts`, частичный уникальный индекс. Новые таблицы, перенос данных не требуется — демо-слоты жили только в DOM.
3. Деплой кода вместе с миграцией: старый `calendar.js` после удаления разметки не сломается, потому что новые шаблоны приходят с сервера.
4. Откат: `alembic downgrade -1` удаляет три таблицы. Данные окон и броней при откате теряются — это ожидаемо, они появились в этом change.
