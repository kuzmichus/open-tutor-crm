# Design

## D1. Страница читает данные; запись — только платёж

Страница `/tutor/finance` только читает `account_operations`; единственное действие записи —
создание платежа кнопкой «Доход». «Расход» — заглушка: кнопка неактивна (`disabled` +
подсказка «Раздел в разработке»), модели трат в проекте нет. Когда расходы появятся —
карточки «Расходы» и «Чистая прибыль» уже готовы показывать ненулевые значения.

## D2. Период — GET-параметр, границы в зоне педагога

`period = month | prev | 3m | all` (мусор → `month`). Границы — окно `[start, end)` в UTC,
посчитанное по настенному времени педагога через `local_day_bounds` (паттерн
`stats/services/periods.py`): месяц — первые сутки месяца и следующие за ним, «Последние
3 месяца» — текущий и два предыдущих. Подпись периода («Октябрь 2026», «Август — Октябрь
2026», «Всё время») собирается сервисом — шаблон бизнес-данные не форматирует.

## D3. Сводка: поток за период и состояние на сейчас

Карточки делятся на два рода, и это видно в подписях:

- **Поток за период** (фильтр по `occurred_at ∈ [start, end)`): «Доход» = оплаченные
  платежи (`kind='payment', status='paid'`), «Возвраты» = возвраты, «Чистый доход» =
  доход − возвраты, «Заработано (уроки)» = списания (`kind='lesson'`). Всё — один запрос
  `GROUP BY kind` с JOIN по `students.tutor_id`.
- **Состояние на сейчас** (без периода): «Долги учеников» и «Переплата» — суммы
  отрицательных и положительных балансов всех учеников репетитора. Баланс — производная
  (design D3 student-finance): один запрос операций с группировкой по ученику, сумма
  в Python той же формулой `signed_amount` — второй копии формулы не появляется.

«Расходы» — константа 0 ₽ и «Чистая прибыль» = чистый доход − расходы: карточки референса
сохранены, чтобы вёрстка не менялась при появлении расходов.

## D4. Блок «Заработано и получено»

Сравнение заработанного уроками и полученного от учеников за период. Разница
сопровождается подсказкой: получено больше — «ученики платят вперёд», меньше — «должны
за прошедшие занятия», поровну — «совпадают». Сравнение — про понимание, а не про новое
правило денег: числа уже посчитаны в D3.

## D5. Диалог «Доход» — тот же шаблон платежа, ученик выбирается

`finance/_payment_dialog.html` получает второй режим: `payment_student is none` — вместо
статичного имени поле выбора ученика (общий виджет `_person_picker.html`: список открывается
по клику, фильтруется по вводу) и скрытый `student_id`. Валидация — серверная: пустой
ученик → повторный диалог с ошибкой, чужой ученик → 404 (правило неразличимости).
Существующий режим из карточки ученика не меняется: там ученик известен и полем не передаётся
(design D11 student-finance).

Варианты выбора — активные и новые ученики (без «В архиве»): платёж архивному ученику —
редкий случай, его внесут из карточки ученика.

## D6. DOM обновляется с сервера

Успешное сохранение — пустой ответ + `HX-Trigger: payment-saved` (`dialog_closed`):
диалог закрывает подписка в шаблоне, а контейнер сводки `#finance-summary` перезапрашивает
себя (`hx-trigger="payment-saved from:body"`). Никаких пересчётов денег в браузере.
Без `HX-Request` POST отвечает 303 на `/tutor/finance` — форма работает и без JS.

## D7. Доступ и изоляция

`tutor_id` — только из сессии (`require_tutor_id` из `finance/services/access.py`). Все
выборки страницы идут через JOIN `students.tutor_id = tutor_id`; чужие данные не попадают
ни в сводку, ни в варианты выбора ученика. Пустой `student_id` в POST — ошибка валидации
(повторный диалог), чужой `student_id` — 404.
