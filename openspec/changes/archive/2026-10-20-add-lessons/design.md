# Design

## Context

Проект: FastAPI + SQLAlchemy 2.0 + HTMX + Jinja2, доменные модули (`app/student`, `app/group`, `app/calendar`) по правилам AGENTS.md: один класс — один файл, views по одному эндпоинту на файл с `router = APIRouter()`, шаблоны неймспейсятся подкаталогом, модели регистрируются в `app/models.py`. Уроков нет: `/tutor/lessons` — 404, календарь на демо-данных (в этом change не трогаем, см. proposal). Компонент селекта «Добавить ученика» с поиском и мини-формой уже существует (спека group-membership, `app/group/services/student_mini.py`) — его поведение переиспользуем для обеих сторон селекта.

## Goals / Non-Goals

**Goals:**
- Модели `Lesson`, `LessonSeries` + миграция Alembic, модуль `app/lesson/` по конвенциям проекта.
- Страница `/tutor/lessons` (список + модалки создания/редактирования) на HTMX.
- Материализованные серии: генерация уроков при создании, массовое редактирование (переключатель) и удаление серии.

**Non-Goals:**
- Интеграция с календарём (`app/calendar` остаётся на демо-данных).
- Поля ДЗ (вкладка — неактивная заглушка), предмет, место, оплата учителя, учитель.
- Продление серии и редактирование слотов уже существующей серии (модель это позволяет, UI — нет).
- Финансовый учёт: «(Оплачено)» — производная от статуса `completed` в презентации.

## Decisions

**D1. Хранение слотов серии — JSON-колонка.** `lesson_series.slots` (TEXT/JSON): список объектов `{weekday, start_time, end_time}`. Слоты нужны только для генерации и отображения панели расписания, не для запросов — отдельная таблица `lesson_series_slots` дала бы лишнюю модель и JOIN без выигрыша. Альтернатива (нормализованная таблица) отклонена как избыточная.

**D2. Материализация серии при создании.** Уроки генерируются один раз при сохранении формы (сервис `series_writer`): для каждого слота — даты от `starts_at.date()` через `interval_weeks`, пока `<= until_date` (включительно). Все уроки одной серии получают один `series_id` (UUID, без FK на родительскую запись не обойтись — FK на `lesson_series.id` + каскадное удаление). Пустой список слотов при включённом переключателе = валидационная ошибка («панель расписания пуста»).

**D3. Ровно одна цель урока — на уровне БД.** CHECK-ограничение в `lessons`: `(student_id IS NOT NULL) XOR (group_id IS NOT NULL)` — ровно одна FK заполнена. Сервис валидации дополнительно сверяет цель с типом (групповой → группа, остальные → ученик). Альтернатива (две nullable FK без CHECK) отклонена: нарушение инварианта невозможно было бы поймать тестом на уровне схемы.

**D4. Закрытый список длительности — CHECK + константа рядом с моделью.** Как в `student.py` (`STUDENT_KINDS`): кортеж `LESSON_DURATIONS` в файле модели — источник истины для CHECK-ограничения и для options селекта в форме.

**D5. Статус — строковый enum `planned`/`completed` с CHECK** (паттерн `STUDENT_STATUSES`). «(Оплачено)» выводится в `app/lesson/services/presentation.py` — в БД отдельного поля нет.

**D6. Views по одному эндпоинту, модалки — HTMX-фрагменты.** `app/lesson/views/`: `index.py` (страница), `create.py` (GET-фрагмент формы + POST), `update.py`, `delete.py`, `delete_series.py`, `lookup_student.py` / `lookup_group.py` (поиск для селекта), `create_student.py` / `create_group.py` (мини-формы). Модалки — частичные шаблоны, подменяемые через HTMX (паттерн `app/group/views/new_group.py`). Переключатель «Применить ко всей серии» — чекбокс той же формы; mass-update сервис принимает флаг.

**D7. Мини-формы переиспользуют правила существующих.** Мини-форма ученика — те же поля и валидация, что `app/group/services/student_mini.py` (Имя*, Фамилия, Телефон; статус «новый»). Мини-форма группы: Название* + Цена за урок — валидация аналогична созданию группы (`app/group/services/group_writer.py`), но без состава. Архивные/чужие записи в селект не попадают (как в group-membership).

**D8. Шаблоны и регистрация.** `app/lesson/templates/lesson/` (index.html, модалки, частички), каталог добавляется в `TEMPLATE_DIRS` в `app/templating.py`; роутер подключается в `main.py`; модели — регистраторы в `app/models.py`. Пункт сайдбара `/tutor/lessons` уже есть.

## Risks / Trade-offs

- [Генерация длинной серии] → серии ограничены разумной датой окончания; генерация — цикл с защитой от «бесконечной» серии (валидация until_date обязателен при повторе).
- [Массовое обновление общих полей трогает прошедшие уроки] → осознанное решение (spec: «включая прошедшие»); кнопка массового удаления — с подтверждением.
- [JSON-слоты не нормализованы] → принимается: слоты не участвуют в запросах; при будущем «продлении серии» JSON достаточно.
- [CHECK XOR в SQLite] → SQLite поддерживает CHECK; autogenerate Alembic сгенерирует ограничение, тесты схемы проверят нарушение.

## Migration Plan

`uv run alembic revision --autogenerate -m "add lessons"` → `alembic upgrade head`: таблицы `lesson_series`, `lessons`. Rollback — `alembic downgrade` (таблицы новые, каскады от `tutors` очищают данные штатно).

## Open Questions

- Нужен ли фильтр «На этой неделе» по границам недели (пн–вс) репетитора или достаточно ISO-недели от сегодня — уточнить при реализации UI, на поведение спеки не влияет.
