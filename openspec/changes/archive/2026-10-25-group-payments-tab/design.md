# Design

## Context

См. `proposal.md` — Why. Состояние кода, формирующее подход:

- **Модалка группы — одна `<form>` на пять вкладок.** `group/templates/group/_manage.html` оборачивает `.modal-body` и футер в единственную форму (`hx-post` на `/tutor/groups/{id}`), панели переключаются Alpine `x-show`. Всё, что попадает в панель вкладки, уходит в POST вместе с формой — поэтому платежная панель не может быть частью этой формы.
- **Панель платежей ученика уже решила эту задачу.** Вкладка «Платежи» карточки ученика — не форма: панель приходит своим GET-маршрутом `/tutor/students/{id}/payments/panel`, слот в форме ученика грузит её с `hx-trigger="load"`, панель перезапрашивает себя по `payment-saved` (design D11 `student-finance`). Вложенных `<form>` нет, POST карточки не затрагивается.
- **Владелец у группы есть напрямую** (`groups.tutor_id`), в отличие от операции счёта, у которой он выводится из ученика.
- **Списание связано с группой через урок.** `account_operations.lesson_id → lessons.group_id`: «списано за занятия группы» — это `kind='lesson'` по урокам группы. `occurred_at` списания равен началу урока (design D15 `student-finance`), поэтому период фильтруется по самому списанию.
- **Возврат с группой не связан вообще.** У возврата есть только `payment_id`, у платежа — только `student_id`; атрибутировать возврат конкретной группе схемы не позволяет. Связываемое с группой множество — только текущие участники.
- **Состав группы хранится только «сейчас»** (`group_members`, история членства отсутствует — design D7 `student-finance`): исключённый участник исчезает из строк, но его исторические списания за уроки группы остаются в его карточке.
- **Баланс — сумма со знаком** (`balance.signed_amount`), единственная формула модуля. Для списка участников баланс считается по всем операциям участников одним запросом, а не N запросами.
- **Границы периода** считаются в зоне педагога и переводятся в UTC (`local_day_bounds`), как в счёте за период: занятие вечером 30-го числа попадает в «Этот месяц» зоны педагога, а не UTC.
- **Чипы периода** (`.period-chips`, радио + подпись) уже есть в дизайн-системе для списка уроков; активное состояние рисует сервер, перерисовывая партиал.

## Goals / Non-Goals

**Goals:**

- Ответить на три вопроса по группе, не выходя из модалки: сколько списано за занятия группы, сколько возвращено, сколько участники должны сейчас.
- Один источник данных — `account_operations`; панель ничего не считает в шаблоне.
- Тот же паттерн «панель — не форма», что у вкладки «Платежи» карточки ученика: модалка группы не меняется как форма.
- Изоляция по репетитору на новом маршруте: чужая группа — 404.

**Non-Goals:**

- Внесение оплаты, возврат и пересчёт из модалки группы: действия остаются в карточке ученика (ссылка на неё — часть панели).
- Списания за индивидуальные уроки участников: сводка — про занятия группы.
- Учёт выбывших участников в строках и итогах: история выбывшего видна в его карточке.
- Пагинация, экспорт, детализация по занятиям (список занятий — будущая вкладка «Занятия»).

## Decisions

### D1. Панель — отдельный GET-маршрут `finance`, а не данные внутри `manage_context`

`GET /tutor/groups/{id}/payments` в модуле `finance` (`views/group_panel.py`), ответ — партиал `finance/_group_panel.html` с корнем `#group-payments-content`. Слот в `_manage.html` грузит его с `hx-trigger="load"` и `hx-swap="outerHTML"`; чипы периода перезапрашивают тот же маршрут, таргет — корень партиала.

Почему так:

- модалка группы — форма; встроенные данные пришлось бы пересчитывать на каждый POST (включая redraw с ошибкой валидации), а панель всё равно нельзя было бы редактировать из формы;
- паттерн уже проверен панелью ученика: ленивая загрузка, перерисовка сервером, нет вложенных форм и JS-пересчётов;
- модуль `group` не получает зависимость от `finance`: наоборот, `finance` уже импортирует модели `group` (`charges.py`, `recalculate.py`) и сервисы (`panel.py` импортирует `student.services.presentation`).

Маршрут в пространстве `/tutor/groups`, но владелец — проверка `group`: `get_owned_group` ри-экспортируется в `finance/services/access.py` (правило AGENTS.md о ри-экспортах), вьюха не импортирует чужой модуль напрямую.

### D2. Объёмы данных: всё — по текущим участникам

- **«Списано за занятия группы»** — сумма `kind='lesson'` по урокам этой группы (`lesson_id → lessons.group_id`) у **текущих** участников, за период.
- **«Возвращено»** — сумма `kind='refund'` **текущих** участников за период.
- **«Долг участников сейчас»** — Σ max(0, −баланс) текущих участников; от периода не зависит (в подписи — «сейчас»).
- **Строка участника** — «Баланс» и «Долг» по всему счёту ученика, «Списано: X ₽ (N занятий)» — списания за уроки этой группы в периоде; N — число списаний.

Почему не «списания группы вообще» (включая выбывших): итог должен складываться из видимых строк — иначе при исключённом участнике сумма карточек не сходилась бы с итогом без объяснений. Выбывший участник продолжает держать свои списания в своей карточке (design D7 `student-finance`), там они и читаются.

Почему «Возвращено» считается по участникам, а не по группе: схема не связывает возврат с группой (только `payment_id → student_id`). Единственный корректный объём — возвраты участников; расширенное поле `comment` возврата остаётся местом, где педагог может пояснить связь.

### D3. Период: закрытый список из трёх значений

`all` («За всё время», по умолчанию), `this_month` («Этот месяц»), `last_month` («Прошлый месяц»). Неизвестное значение query — «За всё время» (нормализация на сервере, как `?tab=` у карточки ученика). Границы месяцев — в зоне педагога: `local_day_bounds` первого дня месяца и последнего дня; «За всё время» — фильтра нет вовсе (не «от нуля до бесконечности», а отсутствие условия).

### D4. Один запрос на каждую выборку, без N+1

- списания: один `SELECT` c `JOIN lessons` и `GROUP BY student_id` (сумма + количество) — фильтр по `lesson_id IN (уроки группы)` выражен join'ом на `lessons.group_id`;
- балансы: один `SELECT` операций всех участников (`student_id IN (...)`), знаки расставляет `signed_amount` в Python — та же формула, что у баланса карточки;
- возвраты: один `SELECT ... SUM`.

Пустой состав — короткое замыкание: запросы не выполняются, сводки нули, вместо списка — пояснение «В группе пока нет учеников.».

### D5. Число занятий — плюрализация в `finance/services/presentation.py`

`(1 занятие / 2 занятия / 5 занятий)` — чистая функция `lessons_count_label(count)`, регистрируется в общем Jinja-окружении рядом с `money`. Шаблон не склоняет сам; правило склонения одно на проект. При N = 0 подпись не выводится: «0 занятий» при пустом периоде читалось бы как данные, а не как их отсутствие.

### D6. Референс и подписи

Тексты берутся с референса макета: заголовки сводок — «Списано за занятия группы», «Возвращено», «Долг участников сейчас»; строка — «Баланс: …», «Списано: … (N занятий)», «Долг: …»; подпись внизу: «Баланс и долг — по всем занятиям ученика, списания — только за занятия этой группы. Оплату вносят в карточке ученика (нажмите на имя — «Платежи»).» Имя участника — ссылка на `/tutor/students/{id}?tab=payments` (обычный переход, не модалка: модалки групп поверх уже открыта, второй слой карточки ученика из неё не предусмотрен). Отрицательный баланс и ненулевой долг выделяются `--danger`-модификаторами (цвет `--destructive`), как минусовые суммы панели ученика.

## Risks / Trade-offs

- **Итоги не включают выбывших участников** (D2) — осознанно ради сходимости итога и строк; полная «выручка группы» видна в карточках учеников. Если позже понадобится именно выручка группы, это отдельный показатель со своим заголовком.
- **Панель устаревает, пока модалка открыта**: платежи/списания, сделанные в другом окне, не подтянутся до перезагрузки модалки. Событие `payment-saved` приходит только после действий в диалогах ученика, которых из модалки группы сделать нельзя; слушать его «на всякий случай» — лишняя связь. Осознанный компромисс.
- **Баланс «не пересчитан»** (у проведённых уроков нет списаний) в сводке группы не детектируется — баннер живёт в карточке ученика, где и находится кнопка ремонта. Дублировать баннер в группу — второй источник истины о расхождении.
