# Design

## Context

Календарь (`/tutor/calendar`) — SSR + Alpine, данные демо: занятия позиционируются в сетке, единая модалка «Новый урок» (решение D6 предыдущего change), карточки создаются единым рендерером `renderCard` и живут только в DOM до листания недели. Мотивация — в proposal.md; требования — в `specs/slot-booking/spec.md`. Ключевое ограничение: пользователь выбрал демо-режим без БД — сервер вообще не участвует.

## Goals / Non-Goals

**Goals:**
- Кнопка «Добавить слот» + диалог создания слота + карточка «свободен/занят» в существующей сетке.
- Диалог записи (имя + телефон/Telegram) с отметкой занятости на карточке.
- Всё в DOM, ноль серверных запросов, тесты зелёные.

**Non-Goals:**
- БД-модель слота, публичная страница `/slot/<токен>`, реальная запись и любые серверные маршруты (см. proposal — вне объёма).
- Слоты в мобильной FAB, режим «День», перетаскивание слотов.
- Персистентность слотов между листаниями недели (как и у демо-уроков).

## Decisions

**D1. Единая модалка урока/слота через режим, отдельная модалка записи.**
Существующее состояние модалки расширяется полем `mode: "lesson" | "slot"`. В режиме «слот» окно переименовывается в «Новый слот», скрывает выбор ученика, показывает редактируемые поля даты и времени и кнопку «Создать». Кнопка «Добавить»/FAB/клик по четверти — режим `lesson` (поведение не меняется), «Добавить слот» — режим `slot`. Диалог записи — отдельный блок разметки (два поля, своя кнопка), т.к. он семантически иной и не должен конкурировать с формой создания.
*Альтернативы:* три независимых модалки — дублирование разметки и стилей; один модалка-переключатель с редактируемым временем и для уроков — меняет существующий поток «клик по четверти» без пользы.

**D2. Выбор времени слота — редактируемые `input[type=date]` и `input[type=time]` с шагом 900 с.**
Кнопка тулбара не имеет контекста кликнутой четверти, в отличие от урока, где время берётся из слота. Поэтому в режиме «слот» статичная строка `дата · время` заменяется на два input'а, префилл — та же логика `openForm()` (сегодня/первая видимая дата, ближайшая будущая четверть). При сохранении время нормализуется к границе четверти часа (повторное использование `snapToQuarter`).
*Альтернатива:* «pick-mode» (после нажатия кнопки кликнуть четверту) — скрытый преходящий режим, хуже обнаруживается и тестируется.

**D3. Карточка слота — переиспользование `renderCard` с полем `kind`.**
Карточка получает класс `cal-event cal-event--slot` (свободен) или `cal-event cal-event--slot cal-event--booked` (занят) — бесплатно переиспользуются позиционирование, наложение, hover и стили сетки. Внутри: строка состояния («Свободен · запись по ссылке» / «Занят: \<имя\>»), интервал времени и, только для свободного, кнопка «Записаться». Явно в обработчике перетаскивания добавлено исключение `.cal-event--slot` — слоты не перетаскиваются (вне объёма, см. proposal); заодно это гарантирует, что клик по кнопке записи никогда не интерпретируется как жест.
*Альтернатива:* отдельный рендерер слотов — дублирование позиционирования и логики наложения.

**D4. Данные записи — атрибуты DOM-узла.**
При подтверждении на карточку пишутся `data-booked-by` (имя) и `data-contact` (телефон/Telegram), контакт показывается в `title` занятой карточки — репетитору есть как связаться, и данные остаются локальными. Повторная запись исключена структурно: кнопка «Записаться» в DOM не добавляется для `--booked`, а обработчик открытия диалога записи принимает только свободные карточки.
*Альтернатива:* показывать контакт отдельной строкой — удорожает карточку; хранить в localStorage — ненужная сложность и скрытые данные.

**D5. Разметка диалогов и кнопки — статическая в `_area.html` (`x-show` + `x-cloak`).**
Все три элемента (кнопка тулбара, диалог «Новый слот», диалог записи) присутствуют в SSR-разметке, как текущая модалка, — это позволяет покрыть их обычными SSR-тестами без запуска JS. Карточка слота создаётся только на клиенте (по требованию DOM-only); тесты на неё — статические проверки JS/CSS, как у заглушек в прошлом change.

**D6. Жизненный цикл без состояния в Alpine.**
Слот добавляется напрямую в DOM-сетку и не заводит массива-состояния: HTMX-листание подменяет `#calendar-swap` и карточки исчезают сами — ровно как демо-уроки (требование «DOM-only жизненный цикл»). Диалог записи ведёт ссылку на конкретный DOM-узел карточки (`_bookingSlot`), а не индекс в массиве.

## Risks / Trade-offs

- [Клик по «Записаться» тонет в drag/клике карточки] → слоты исключены из жеста перетаскивания (D3), у кнопки обычный `@click.stop`.
- [Нормализация времени: `input[type=time]` может дать «10:07»] → при сохранении применяется `snapToQuarter`, длительность обрезается по границе 23:00.
- [Слот «наезжает» на демо-урок] → по требованию спеки создание не блокируется; позиционирование переиспользует существующую логику наложения (карточки видны обе).
- [Пользователь может перепутать два диалога] → разные заголовки («Новый слот» / «Запись на слот»), у слота свой пунктирный стиль и подпись состояния.
- [HTMX-листание «съедает» созданные слоты и отметки] → это задокументированное поведение спеки, а не дефект; тест явно это фиксирует.

## Migration Plan

Не требуется: клиентский демо-режим, миграций и конфигурации нет, откат — revert коммитов.

## Open Questions

Нет: объём (демо без БД), поля формы (имя + телефон/Telegram) и поведение ссылки (диалог записи вместо страницы) подтверждены пользователем.
