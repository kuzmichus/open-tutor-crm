# Design

## Context

См. `proposal.md` — Why. Состояние кода, формирующее подход:

- **Модалка «Карточка ученика» — одна `<form>` на три вкладки.** `student/templates/student/_form.html` оборачивает `.modal-body` и общий `.modal-actions` в единственную форму (`hx-post` на `/tutor/students/{id}`), панели вкладок переключаются `x-show`. Пока «Платежи» были заглушкой, это было безопасно.
- **Вложенные `<form>` в проекте запрещены не по вкусу, а по факту.** В `slot/templates/slot/_dialog.html` и `lesson/templates/lesson/_form.html` оставлены комментарии, что браузер выбрасывает внутренний `<form>`, и кнопка отправляет чужую форму (проверено в браузере). Панель ДЗ (`homework/_panel.html`) — отдельная форма с `hx-target` на саму себя и `hx-swap="outerHTML"`; это готовый образец «второй формы внутри модалки».
- **`#modal` — единственный контейнер.** `student/index.html` и `student/card.html` содержат `<div id="modal"></div>`; каждая модалка вешает `@keydown.escape.window="close()"`.
- **Списание не существует ни в каком виде.** «(Оплачено)» в `lesson/services/presentation.py` — производная от `status == "completed"`; в design `add-lessons` это записано как Non-Goal «финансовый учёт».
- **Урок пишется четырьмя путями с разными транзакциями.** `lesson_writer.create_single_lesson` и `create_series` коммитят сами; `lesson_writer.update_lesson` не коммитит (коммит делает `views/update.py`, вместе с `mass_update.apply_to_series`); `lesson_remover.delete_lesson`/`delete_series` коммитят сами.
- **Групповой урок не имеет цены.** `lesson.price` у группового всегда `NULL` (поле скрыто и `:disabled` в форме), а цена участника лежит в `GroupMember.price_override`, общая — в `Group.price_per_lesson`. Форма счёта периода на референсе показывает групповые занятия с ценой, значит цена участника уже есть в модели.
- **Состав группы хранится только «сейчас».** `group_writer` при исключении участника делает `db.delete(member)` — истории членства нет.
- **Время** — UTC в БД (`DateTime(timezone=True)`), показ и ввод через `app/common/services/tutor_time.py` (`to_local`/`to_utc`); SQLite теряет tzinfo, поэтому чтения нормализуются `as_utc`.
- **Деньги** — `Integer` рубли в `Lesson.price`, `Group.price_per_lesson`, `GroupMember.price_override`. Форматтер «1 200 ₽» уже существует дважды (`group/services/presentation.py`, `lesson/services/presentation.py`).
- **Панель платежей будет длинной.** История на много строк требует одного источника с одной сортировкой; мерж двух источников в Python на каждый рендер — плохая основа для страницы, которую открывают ради проверки денег.

## Goals / Non-Goals

**Goals:**

- Один источник истины для баланса: единая таблица операций, баланс — сумма со знаком, без денормализованной колонки.
- Списание за урок живёт рядом с уроком, но переживает удаление ученика из группы и удаление урока.
- Пересчёт, который можно запускать сколько угодно раз без побочных эффектов, и который не переписывает историю.
- Вкладка «Платежи», которая не участвует в POST карточки ученика ни при каком сценарии.

**Non-Goals:**

- Посещаемость групповых занятий (в v1 «считаем, что были все»).
- Отправка счёта в мессенджеры и на email.
- Пагинация истории, экспорт, корректировки вручную, копейки.
- Пересмотр «(Оплачено)» в списке уроков: остаётся производной от статуса, несоответствие фиксируется как известное.
- Data-миграция существующих уроков: историю догоняет кнопка «Пересчитать».

## Decisions

### D1. Новый доменный модуль `app/finance/`

```
app/finance/
├── models/account_operation.py
├── services/
│   ├── access.py           get_owned_operation (JOIN students)
│   ├── operations.py       выборки: платежи, история, суммы
│   ├── payment_form.py     разбор и валидация формы платежа
│   ├── payment_writer.py   создание и правка платежа
│   ├── refunds.py          возврат, остаток к возврату
│   ├── charges.py          sync_lesson_charge (списание из урока)
│   ├── balance.py          баланс ученика
│   ├── recalculate.py      идемпотентный ремонт + детектор расхождения
│   ├── invoice.py          занятия периода и текст сообщения
│   └── presentation.py     «1 200 ₽», подписи видов и статусов, знак суммы
├── views/                  по одному эндпоинту на файл
└── templates/finance/      _panel.html, _payment_dialog.html,
                            _refund_dialog.html, _invoice_dialog.html
```

*Почему отдельный модуль, а не расширение `student`*: у счёта своя модель, свои сервисы и своя поверхность (панель + три диалога), а `student` уже держит карточку, контакты, плательщика и напоминания. Правило AGENTS.md «один класс — один файл» и структура по доменам требуют отдельного модуля для сущности, у которой своё поведение.

*Зависимость односторонняя*: `finance` → `student`, `finance` → `lesson`, `finance` → `group`. Обратной зависимости нет; единственная точка, где `lesson` знает про `finance`, — вызов `sync_lesson_charge` в путях записи урока (D6).

### D2. Одна таблица операций вместо двух

```
account_operations
  id           String(36)  PK, uuid4
  student_id   FK students.id CASCADE, index, NOT NULL
  kind         String(8)   CHECK IN ('payment','refund','lesson')
  amount       Integer     NOT NULL, CHECK (amount > 0)
  occurred_at  DateTime(timezone=True) NOT NULL, index   -- UTC
  status       String(10)  CHECK IN ('paid','pending','cancelled') | NULL
  method       String(8)   CHECK IN ('transfer','card','online')   | NULL
  comment      Text        | NULL
  lesson_id    FK lessons.id CASCADE      | NULL, index
  payment_id   FK account_operations.id SET NULL | NULL
  created_at / updated_at
```

Частичный уникальный индекс вместо `UNIQUE(...)` в таблице — SQLite их поддерживает, как уже сделано для `ux_bookings_active_slot`:

```
CREATE UNIQUE INDEX ux_account_operations_lesson_student
  ON account_operations(lesson_id, student_id) WHERE kind = 'lesson';
```

`tutor_id` в строке нет: владелец выводится из ученика, как у `Booking` — через `Slot`. Изоляция — `get_owned_operation` одним `SELECT` с `JOIN students` по `id` операции и `tutor_id`; чужая и несуществующая неразличимы (404).

*Альтернатива — две таблицы (`payments` и `lesson_charges`)*. Отвергнута: история на референсе — один список с одной сортировкой и одной нумерацией; две таблицы заставили бы либо мержить их в Python на каждый рендер, либо вводить денормализованную копию.

*Альтернатива — `balance` колонкой у ученика*. Отвергнута: её пришлось бы обновлять в каждом из четырёх путей записи урока плюс в платежах и возвратах, и первая же пропущенная ветка сделала бы число неверным без следа.

### D3. Знак выводится из вида, сумма всегда положительная

```
баланс = SUM( +amount  WHERE kind='payment' AND status='paid'
            - amount   WHERE kind='refund'
            - amount   WHERE kind='lesson' )
```

`amount > 0` держится CHECK-ограничением. Хранить знак в сумме было бы соблазнительно, но тогда `kind` и знак могут противоречить друг другу (положительный «возврат»), и починить это можно только ещё одним CHECK. Одна формула на весь модуль — в `balance.py`; шаблон не суммирует ничего сам.

### D4. Статус платежа — отдельная ось от вида операции

`status` и `method` имеют смысл только при `kind='payment'`, у остальных видов они `NULL`. Это не «мягкий XOR» на уровне БД: CHECK на пару колонок был бы громоздким, а инвариант простой и проверяется в writer'ах — форма платежа всегда пишет оба поля, остальные виды их не трогают.

Следствия, которые держит сервис, а не только форма:

- «Ожидает» и «Отменено» не входят в баланс, но видны в списке платежей;
- смена статуса на «Оплачено» — это просто изменение строки, баланс пересчитывается сам (он производный);
- отмена платежа запрещена, если по нему есть возвраты (`SELECT 1 FROM account_operations WHERE payment_id = ... AND kind='refund'`).

### D5. Возврат — отдельная операция со ссылкой на платёж

```
refund: kind='refund', payment_id -> платёж, amount, occurred_at, comment
доступно к возврату = payment.amount − SUM(refund.amount WHERE payment_id = payment.id)
```

`UNIQUE(payment_id)` **не** ставится: референс прямо содержит поле «Сумма возврата» и подсказку «Полный возврат», то есть возврат бывает частичным и многократным.

Возврат не меняет статус платежа: платёж остаётся «Оплачено», а в истории рядом появляются строки со знаком минус. Это и есть смысл подсказки «Статус «Отменён» при внесении платежа НЕ оформляет возврат» — три статуса и кнопка «Возврат» не взаимозаменяемы.

`payment_id` объявлен `SET NULL`, а не `CASCADE`: удаление платежа в v1 не предусмотрено, но история возврата не должна исчезать от чужой ошибки в БД.

Ограничение «не ниже нуля» у баланса отсутствует осознанно: возврат 2 400 при балансе 300 даёт −2 100, потому что репетитор возвращает деньги, уже потраченные на уроки.

### D6. Списание — идемпотентная функция от урока

```
sync_lesson_charge(db, lesson) -> None      # без коммита
  цели = []  если lesson.status != 'completed' -> ничего не списываем
         иначе если lesson.group_id -> участники группы
         иначе если lesson.student_id -> [ученик]
  для каждой цели с определимой ценой:
      upsert строки (lesson_id, student_id): amount = цена
  удалить строки по lesson_id, которых больше нет в целях
```

Цена цели: `lesson.price` для индивидуального; `price_override ?? group.price_per_lesson` для участника группы. Если цена не определима — строки нет (не «0 ₽», а именно отсутствие строки).

Вызывается из всех путей записи урока:

| Путь | Точка вызова | Коммит |
|---|---|---|
| `create_single_lesson` | после `db.add(lesson)`, до `commit` | свой |
| `create_series` | для каждого урока серии, до `commit` | свой |
| `views/update.py` | после `update_lesson` + `apply_to_series`, до `db.commit()` | вызывающего |
| `delete_lesson` / `delete_series` | **не нужен**: `lesson_id` каскаден | — |

*Почему не сигналы ORM (events)*: `Session` в проекте настраивается один раз в `database.py`, а неявная подписка на `after_flush` спрятала бы финансовое поведение от читателя сервиса урока. Явный вызов в четырёх местах виден в диффе и не сработает там, где не надо (например, в тестах, создающих уроки фабрикой напрямую).

*Почему upsert, а не «удалить и создать»*: удаление и создание меняло бы `id` строки, а на него ссылаются возвраты (`payment_id` не касается, но принцип тот же) и, главное, `occurred_at` — история должна сохранять исходную дату списания при правке цены.

**Осознанное следствие**: правка цены урока пересчитывает списание (спека `lesson-management` это обещает), а изменение цены группы задним числом не переписывает прошлые списания — их создаёт только `sync_lesson_charge` по конкретному уроку. Пересчёт (D7) тоже не переписывает суммы.

### D7. Пересчёт — ремонт, а не пересчёт истории

```
recalculate(db, tutor_id, student=None) -> int   # сколько строк добавлено
  для каждого completed-урока репетитора (опционально — одного ученика):
      для каждой цели с ценой:
          если строки (lesson_id, student_id) нет — создать
          если есть — НЕ трогать
  для каждого урока, который больше не completed — удалить его строки
```

Кнопка «Пересчитать баланс» вызывает его для одного ученика; детектор расхождения (D8) — `COUNT` по тому же критерию.

Почему не «удалить всё и построить заново»: rebuild не может восстановить членство в группе на дату урока (`group_members` хранит только текущий состав, исключённый участник удаляется физически). Полный rebuild молча стёр бы исторические списания вышедших участников. Поэтому правило «добавляем недостающее, существующее не трогаем» — не оптимизация, а требование корректности.

### D8. Баннер вместо data-миграции

```
has_missing_charges(db, tutor_id, student_id) -> bool
  EXISTS(lesson: status='completed', цель с ценой, нет строки (lesson_id, student_id))
```

Если `True` — панель показывает баннер «Баланс не пересчитан» с кнопкой. Это закрывает главный практический случай: таблица только что появилась, а проведённые уроки уже есть, и без пересчёта первый открывший увидел бы минус по всем урокам, которые когда-либо провёл.

*Альтернатива — data-миграция с backfill*. Отвергнута: AGENTS.md требует создавать миграции через autogenerate, а ручной шаг с бизнес-логикой внутри миграции пришлось бы дублировать и поддерживать. Кнопка работает и для будущих расхождений (ручная правка БД, старые данные после восстановления из бэкапа), а миграция — нет.

### D9. Модалка: три соседние формы вместо одной

```
.modal-content
  .modal-header
  .tabs.modal-tabs
  .tab-shell                      (flex:1, min-height:0)
    form.tab-form  x-show="tab==='general'"   .modal-body + .modal-actions[Отмена|Сохранить]
    div.tab-form   x-show="tab==='payments'"  .modal-body + .modal-actions[Закрыть]
    form.tab-form  x-show="tab==='settings'"  .modal-body + .modal-actions[Отмена|Сохранить]
```

Три элемента — **соседи**, а не вложенные друг в друга, поэтому запрет на вложенные `<form>` не нарушается. Каждый `.tab-form` — `display:flex; flex-direction:column; min-height:0`, а `.modal-body` внутри него получает `overflow-y:auto`: кнопки вкладки остаются на виду, как сейчас у `.modal-content`.

*Почему не серверная подмена вкладки (`hx-get ?tab=payments`)*: несохранённые правки в «Общем» пропадали бы при каждом клике на «Платежи». `x-show` оставляет панели в DOM, и значение поля доживает до сохранения.

*Почему не вынести «Платежи» на страницу*: пользователь выбрал модалку с таббаром, и это согласуется с референсом; страница получает только сводку (D12).

*Следствие для валидации*: `revealInvalidField` в `students.js` ищет `:invalid` в `event.target` — это по-прежнему своя форма, и `closest("[data-tab-panel]")` переключает `tab` на её панель. Правка не нужна.

### D10. Второй слой модалок: `#modal-payment`

```
z-50  #modal          .modal-root         «Карточка ученика»
z-60  #modal-payment  .modal-root--stack  «Новый платёж» / «Оформить возврат» / «Счёт за период»
```

Контейнер добавляется соседом `<div id="modal">` в `student/index.html` и `student/card.html`. Каждый диалог — своя форма с `hx-target` на свой контейнер и `hx-swap="outerHTML"`: при ошибке валидации возвращается тот же фрагмент с ошибками, форма карточки не затрагивается вовсе.

*Escape*: нижний слой проверяет, не занят ли верхний —

```
@keydown.escape.window="if (!stackedOpen()) close()"
```

где `stackedOpen()` из `payments.js` смотрит, есть ли дети у `#modal-payment`. Правило «закрывается только верхний слой» без общей машинерии модалок.

*Альтернатива — открывать платёж в том же `#modal`* (замена содержимого). Отвергнута: несохранённые правки в «Общем» исчезали бы, а состояние вкладки пришлось бы тащить в query-параметр.

### D11. Вкладка «Платежи» — панель без формы

Каждый элемент — самостоятельный запрос; вкладка не содержит ни `<form>`, ни скрытых полей.

| Элемент | Метод | Путь | Ответ |
|---|---|---|---|
| Внести оплату | GET | `/tutor/students/{sid}/payments/new` | диалог в `#modal-payment` |
| Сохранить платёж | POST | `/tutor/students/{sid}/payments` | диалог закрыт + `HX-Trigger: payment-saved` |
| Изменить | GET | `/tutor/payments/{pid}/edit` | тот же диалог с данными |
| Сохранить правку | POST | `/tutor/payments/{pid}` | закрыт + `payment-saved` |
| Возврат | GET | `/tutor/payments/{pid}/refund/new` | диалог возврата |
| Оформить возврат | POST | `/tutor/payments/{pid}/refund` | закрыт + `payment-saved` |
| Пересчитать баланс | POST | `/tutor/students/{sid}/balance/recalculate` | перерисованная панель |
| Счёт за период | GET | `/tutor/students/{sid}/invoice?from=&to=&balance=1` | диалог счёта |

`payment-saved` → панель перезапрашивает себя (`hx-get` + `hx-trigger="payment-saved from:body"`), как `student-saved` в сетке учеников. Ничего нового в паттерне нет.

Один шаблон диалога на создание и правку (`payment is None` → пустая форма), как `slot/_dialog.html`.

Поле «Ученик» — статичный текст, не селект: диалог открывается из карточки конкретного ученика, а перенос платежа другому ученику — отдельный сценарий, которого нет в требованиях.

### D12. Страница карточки ученика

Блок «Уроки и оплаты» заменяется на сводку: текущий баланс, последние операции и действие «Платежи» (`hx-get="/tutor/students/{id}/edit?tab=payments"` → `#modal`). `form_context` получает `initial_tab` из query-параметра, `student/_form.html` — `x-data="studentForm(..., '{{ initial_tab }}')"`. Это одна строка в контексте и одна в шаблоне.

### D13. Счёт за период

- Период по умолчанию — следующий календарный месяц (первое и последнее число).
- Список занятий: уроки периода с определимой ценой (D6), независимо от статуса. Для будущего периода это «запланированные», для прошедшего — то, что было.
- Тумблер «Учесть остатки на балансе» — арифметика на сервере: `К оплате = Стоимость занятий − Баланс`.
- Текст сообщения собирается на сервере и кладётся в `data-invoice-text`; копирование — `navigator.clipboard` + тост `.cal-toast` (класс уже есть в дизайн-системе).
- «Отправить ученику» — `disabled`, без адреса и без маршрута (требование `student-management` «Нет нерабочих ссылок»).

### D14. Представление: один форматтер денег на модуль

`finance/services/presentation.py` заводит `money(value)` → «1 200 ₽» и `signed_money(operation)` → «+2 000 ₽» / «−1 200 ₽» (типографский минус U+2212, как на референсе). Третья копия форматтера в проекте уже была бы, но `group` и `lesson` уже содержат свои; дублировать их в `finance` — значит получить три реализации одного правила. Решение: `finance` использует свой форматтер, а вынос общего в `app/common/` — отдельная задача (не в этом change, чтобы не расширять область).

### D15. Время операции

`occurred_at` — одно сортируемое поле:

- платёж и возврат: дата из формы + текущее локальное время в момент сохранения (референс показывает «22 окт. 2026, 01:31» при выбранной дате);
- списание: `lesson.starts_at` (время урока) — так история читается как хронология занятий.

Хранится в UTC, показывается через `to_local(value, tutor)`; формат `%d.%m.%Y, %H:%M`.

## Risks / Trade-offs

- **Списание расходится с уроком при новом пути записи** → `sync_lesson_charge` вызывается явно в каждом известном пути (D6), а расхождение ловится баннером (D8) и лечится кнопкой. Пропущенный пятый путь не испортит данные молча: пользователь увидит баннер.
- **Групповые списания не отражают посещаемость** → «считаем, что были все» записано в спеку и в README; при появлении посещаемости списание станет функцией от отметок, а `sync_lesson_charge` — её единственная точка изменения.
- **Выход участника из группы удаляет `group_members`** → пересчёт не удаляет существующие строки (D7), поэтому исторические списания выживают; но восстановить списание вышедшего участника после ручного удаления строки нельзя — принимается, это ремонт, а не реконструкция.
- **`x-show` держит все вкладки в DOM** → память и разметка растут; для трёх вкладок с формой это несущественно, зато несохранённые правки не теряются.
- **Второй слой модалок добавляет `z-index`-дисциплину** → два контейнера и правило «Escape закрывает только верхний» (D10); регрессия возможна только при появлении третьего слоя, которого в планах нет.
- **Правка цены проведённого урока пересчитывает списание, а изменение цены группы — нет** → асимметрия осознанная (D6): цена группы — настройка на будущее, а не документ прошлого. Зафиксировано в спеке.
- **`occurred_at` платежа содержит «время ввода», а не реальное время перевода** → для сортировки этого достаточно; отдельная колонка «время платежа» не нужна, пока нет сценария, где она важна.
- **«(Оплачено)» в списке уроков остаётся производной от статуса** → после появления платежей надпись может быть неправдой. В v1 не трогаем, чтобы не расширять область; фиксируется в README как известное ограничение.

## Migration Plan

1. `uv run alembic revision --autogenerate -m "add account operations"` — таблица `account_operations`, FK, CHECK'и и частичный уникальный индекс (autogenerate не создаёт частичные индексы — индекс дописывается в миграцию вручную, как `ux_bookings_active_slot` в миграции броней).
2. `uv run alembic upgrade head` — данные не переносятся: backfill заменён кнопкой «Пересчитать» (D8).
3. Откат — `alembic downgrade -1`: таблица удаляется целиком, уроки и платежи не затрагиваются, потому что ни одна существующая таблица не меняется.
4. После деплоя первое открытие вкладки «Платежи» показывает баннер; нажатие «Пересчитать» создаёт списания по прошлым урокам.
