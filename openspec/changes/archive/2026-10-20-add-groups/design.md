# Design

## Context

См. proposal.md — Why. Ключевые вводные из кодовой базы:

- `/tutor/groups` объявлен в `sidebar.html` как обычный пункт меню, но роута нет → 404. Регистрация модуля идёт по канону AGENTS.md: `app/models.py` (импорт-регистратор), `main.py` (`include_router`), `app/templating.py` (`TEMPLATE_DIRS`).
- Доступ по сессии — `require_tutor_id` / `LoginRequired` из `app/common/access.py` (переиспользуется календарем и студентами, модуль group берёт его оттуда же).
- Паттерн «модалка с вкладками» уже отработан в `app/student/templates/student/_form.html`: Alpine `x-data`, `x-show` на панелях (все поля в DOM и уходят в POST), футер `.modal-actions` вне скролла.
- Паттерн «селект с поиском» — `combobox()` в `app/static/combobox.js` + `data-options` с JSON (часовые зоны у ученика). Список выбора человека (ученика/контакта) — общий виджет `createPersonPicker` в `app/static/picker.js` + макрос `_person_picker.html`.
- Связи в проекте объявлены как FK-колонки без `relationship()`; выборки — одним запросом с `join` и группировкой в Python (`app/student/services/students.py`). `PRAGMA foreign_keys=ON` уже включён.
- Модели занятий, расписания и платежей нет — календарь работает на демо-данных. Вкладки «Расписание», «Занятия», «Оплаты» поэтому — заглушки.

## Goals / Non-Goals

**Goals:**

- Группы как полноценная сущность БД с изоляцией по `tutor_id`, живущая рядом с учениками.
- Интерфейс, повторяющий референс: список карточек, модалка «Новая группа», модалка «Группа A» с пятью вкладками.
- Состав группы как отдельный набор данных (дата вступления, индивидуальная цена) — задел под будущие расписание и оплаты.
- Тестируемость в pytest через SSR-текст: состав, счётчики, валидация лимита/дублей, изоляция.

**Non-Goals:**

- Модели занятий, серий расписания и платежей: вкладки «Расписание», «Занятия», «Оплаты» остаются заглушками.
- Отражение групп в карточке ученика и в календаре (отдельные change).
- Импорт/экспорт групп, шаблоны групп, авто-генерация расписания.

## Decisions

### D1. Новый доменный модуль `app/group/`

```
app/group/
├── __init__.py
├── models/
│   ├── group.py          # Group
│   └── group_member.py   # GroupMember
├── services/
│   ├── groups.py         # выборки списка и карточек, lookup учеников
│   ├── members.py        # лимит, дубли, дата вступления
│   ├── student_mini.py   # создание ученика из формы группы (D9)
│   ├── group_form.py     # разбор формы (создание/настройки), валидация
│   ├── group_writer.py   # создание, обновление, удаление
│   └── presentation.py   # форматирование цены, подписи дат
├── views/
│   ├── index.py            # GET  /tutor/groups
│   ├── list_partial.py     # GET  /tutor/groups/list (HTMX-партиал сетки)
│   ├── new_group.py        # GET  /tutor/groups/new
│   ├── create_group.py     # POST /tutor/groups
│   ├── create_student.py   # POST /tutor/groups/students (мини-форма, D9)
│   ├── edit_group.py       # GET  /tutor/groups/{id}/edit
│   ├── update_group.py     # POST /tutor/groups/{id}
│   ├── update_notes.py     # POST /tutor/groups/{id}/notes
│   ├── delete_group.py     # POST /tutor/groups/{id}/delete
│   └── __init__.py         # сборщик router
└── templates/group/
    ├── index.html, _grid.html, _card.html
    ├── _new_group.html     # модалка создания
    └── _manage.html        # модалка управления (5 вкладок)
```

- **Альтернатива:** группы внутри модуля student — отвергнута: группа не разновидность ученика, у неё свой жизненный цикл и свои будущие разделы (расписание, оплаты), плюс AGENTS.md требует отдельного модуля на домен.

### D2. Модели

`Group`: `id` (uuid4, String(36)), `tutor_id` (FK `tutors.id` ON DELETE CASCADE, индекс), `name` (String(100), NOT NULL), `description` (Text, NULL), `price_per_lesson` (Integer, NULL — рубли, «цена с человека за урок»), `meeting_url` (String(500), NULL), `notes` (Text, NULL), `created_at`, `updated_at`.

`GroupMember`: `id`, `group_id` (FK `groups.id` ON DELETE CASCADE, индекс), `student_id` (FK `students.id` ON DELETE CASCADE, индекс), `joined_at` (DateTime(timezone=True), NOT NULL, по умолчанию «сейчас»), `price_override` (Integer, NULL), `created_at`; `UNIQUE(group_id, student_id)`.

- `price_override IS NULL` трактуется как «оплата по общей цене группы» — правило фиксируется в спеке `group-membership`.
- Проверки на сервере: `MAX_MEMBERS = 10` (константа рядом с моделями), лимит и дубль проверяются и в форме, и в writer'е — защита не только от интерфейса.
- **Альтернатива:** хранить состав как JSON-массив id на группе — отвергнута: нужна индивидуальная дата и цена на участника, индексированные FK и каскадное удаление.

### D3. Модалка управления — Alpine-переключение вкладок, все панели в DOM

Вкладки рендерятся одним шаблоном `_manage.html`, панели переключаются `x-show` (паттерн `_form.html` студента). «Общее» и «Настройки» — рабочие панели; «Расписание», «Занятия», «Оплаты» — `.tab-panel__empty` с пояснением (как «Платежи» у ученика).

- **Альтернатива:** серверные партиалы вкладок (`GET /tutor/groups/{id}/tab/{tab}`) — отвергнута: выигрыша нет (данных немного, заглушки статичны), а это лишний маршрут и состояние загрузки.
- Футер модалки общий: «Удалить» (красная), «Отмена», «Сохранить». «Сохранить» сабмитит форму вкладки «Настройки»; заметки на вкладке «Общее» сохраняются отдельным HTMX-POST `/tutor/groups/{id}/notes` с подменой панели.

### D4. Форма состава: именованные поля по id участника

Строка участника в форме: имя, поле даты `member_joined_<id>` (date), поле цены `member_price_<id>` (number) и кнопка «Убрать», которая вычёркивает строку и кладёт id в Alpine-массив `removed`. При сабмите уходят `members[]` (id оставшихся), их даты/цены и скрытое поле `removed_members=id1,id2` — writer исключает перечисленных и добавляет новых.

- Валидация: не более `MAX_MEMBERS` после применения добавлений/исключений; дубли отклоняются (уже состоящий в группе не предлагается и не принимается сервером).
- **Альтернатива:** чекбокс «в группе» у каждого кандидата — отвергнут: раздувает форму и расходится с референсом (комбобокс + список выбранных).

### D5. Выбор учеников — общий список выбора с JSON-опциями

`GET /tutor/groups/new` и `/edit` отдают модалку с `data-options` (JSON: id, имя, класс/статус) — только активные/новые ученики репетитора, уже состоящие в группе исключены. Клиентская часть — общий виджет `createPersonPicker` (`app/static/picker.js`) поверх Alpine; правила группы (кто предлагается, что делает выбор) — в `app/static/groups.js`.

- **Поле общее с формой ученика:** то же поле «Добавить контакт» в форме ученика рисуется тем же макросом `_person_picker.html` и управляется той же фабрикой. Иначе два похожих поля разъезжаются по поведению и вёрстке.
- **Список открывается сразу** по клику/фокусу, не дожидаясь ввода; ввод фильтрует уже открытый список. Раньше список показывался только при непустом запросе — по клику «Добавить ученика» ничего не происходило.
- **Альтернатива:** HTMX-поиск по мере ввода (`/tutor/groups/students?q=`) — отвергнут: у одного репетитора десятки учеников, весь список умещается в JSON один раз.
- **Альтернатива:** отдельная реализация для группы — отвергнута: дублирует уже существующий список выбора контактов и расходится с ним в поведении.

### D6. Клиентская валидация — дублирует серверную, не заменяет

Лимит 10 и запрет дублей блокируются в Alpine (быстрая обратная связь) и проверяются заново на сервере при сохранении: форма может быть отправлена криво или устаревшими данными.

### D7. Удаление — двухшаговое подтверждение без системного диалога

«Удалить» в футере модалки и в меню «...» карточки переводит кнопку в состояние «Точно удалить?» (второй клик = POST `/tutor/groups/{id}/delete`); ответ подменяет сетку списка через `hx-target` и закрывает модалку. Членство уходит каскадом (FK + включённый `PRAGMA foreign_keys`), ученики не трогаются.

- **Альтернатива:** `window.confirm()` — отвергнут: системный диалог выбивается из стиля и не тестируется в SSR.

### D8. Стили — в общем `app/static/styles.css`

Классы `.groups-grid`, `.group-card`, элементы модалки переиспользуют существующие `.modal-*`, `.tabs`, `.btn`, `.chip`. Компонентов в дизайн-системе достаточно, новых CSS-файлов не заводим (прецедент — календарь).

### D9. «Добавить ученика» из списка выбора — мини-форма вместо селекта

Список выбора участников дополняется разделителем и пунктом «Добавить ученика», который подменяет поле выбора мини-формой: «Имя *», «Фамилия», «Телефон» и кнопки «Создать»/«Отменить». Точки входа две — модалка создания и вкладка «Настройки» (один и тот же компонент).

- **Вложенный `<form>` запрещён:** модалка группы — это `<form hx-post=...>`, а мини-форма лежит внутри её блока состава. Поэтому мини-форма — `div` с полями и кнопкой «Создать», несущей собственный `hx-post` и `hx-include` (HTMX читает значения полей без элемента `form`); нативная проверка `required` на кнопке не работает — обязательность имени проверяется Alpine (`@click` с предотвращением отправки при пустом имени) и заново на сервере.
- **Отдельный эндпоинт** `POST /tutor/groups/students` (модуль group, не student): возвращает фрагмент строки участника для формы + обновлённый JSON опций для списка выбора. Существующий `POST /tutor/students` возвращает модалку ученика и целится в `#modal` — переиспользовать его нельзя без ломания контракта страницы учеников.
- **Автодобавление в состав:** созданный ученик сразу получает строку в форме состава с датой вступления «сегодня» и пустой индивидуальной ценой; в группу он попадает только после «Сохранить» формы, как и остальные участники. Поле выбора группы в мини-форме отсутствует — группа берётся из контекста (id в URL эндпоинта).
- **Значения по умолчанию:** статус «Новый», тип «Ребёнок», остальные поля карточки — пустые; полное редактирование доступно на странице учеников.
- **Телефон** нормализуется и валидируется существующим `app/student/services/phone.py` (переиспользуется, не дублируется); невалидный телефон — ошибка в мини-форме, ученик не создаётся.
- **Альтернатива:** `POST /tutor/students` с особым заголовком/параметром, возвращающим другой фрагмент — отвергнута: один маршрут с двумя разными ответами хуже тестируется и путает владельца кода; к тому же контекст группы (id группы в URL) естественнее живёт в модуле group.

## Risks / Trade-offs

- [**Лимит 10 зашит в два места (клиент и сервер)**] → константа `MAX_MEMBERS` в моделях + константа в JS читается из `data-max-members` шаблона — единственный источник истины на сервере.
- [**Цена Integer (рубли) не хранит копейки)**] → осознанно: вся витрина считает рублями («1 200 ₽»); при появлении платежей с копейками поле меняется миграцией.
- [**Заглушки вкладок выглядят как «сломанная функция»)**] → каждая заглушка несёт пояснение «раздел появится позже» и не содержит активных кнопок, ведущих в 404 (правило из спеки календаря про кнопки-заглушки).
- [**Участники, удалённые в форме, но не отправленные)**] → изменение применяется только по «Сохранить»: «Убрать» меняет только DOM, сабмит несёт финальный список.
- [**Чужая группа по id в URL)**] → 404-подобный ответ «как будто нет» (паттерн изоляции студентов), тест покрывает.
- [**Создание ученика дублирует логику страницы учеников)**] → мини-форма опирается на те же `phone.py` и правила модели Student, но живёт отдельным вьюхом (D9); тест проверяет, что созданный ученик виден и на странице учеников.
- [**`required` не работает на кнопке вне `<form>`)**] → обязательность имени проверяется дважды: клиент (Alpine) и сервер (валидация формы группы); тест покрывает пустое имя.

## Migration Plan

`uv run alembic revision --autogenerate -m "add groups"` → создаёт `groups` и `group_members`; применение — `alembic upgrade head` (таблиц новые, переносить нечего). Откат — `alembic downgrade head` (удаление двух новых таблиц, на данные не влияет). Деплой обычный: `uv run pytest` → `upgrade head` → рестарт.

## Open Questions

- Цветовая метка карточки группы (у ученика есть цвет акцента) — подбирается при реализации, спеку не меняет.
- Показывать ли группы в карточке ученика — отдельный change, точка интеграции: состав уже лежит в `group_members.student_id`.
