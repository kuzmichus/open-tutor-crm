# Design

## D1. Метаданные в БД, байты — в хранилище

Таблица `files` хранит только метаданные: id, владельца, бэкенд, ключ объекта,
исходное имя, тип содержимого, размер и время создания. Байты лежат вне БД: в
каталоге `FILES_LOCAL_ROOT` или в S3-бакете. Причина — SQLite: файл в BLOB
раздувает базу, ломает её резервное копирование и не даёт отдать файл потоком.

Колонка `backend` фиксирует, куда именно лёг объект. Она нужна, чтобы смена
`FILES_BACKEND` не делала старые файлы нечитаемыми: файл ищется в том хранилище,
которое записано в строке, а не в текущем значении env.

## D2. Абстракция хранилища — один интерфейс, две реализации

`Storage` — ABC с методами `save(key, data, content_type)`, `open(key)`,
`delete(key)`, `exists(key)` и `download_url(key, filename, content_type)`.

- `LocalStorage` трактует ключ как относительный путь внутри корня и **обязан**
  проверить, что итоговый путь не выходит за корень (`..`, абсолютные ключи):
  иначе имя файла из формы стало бы записью в произвольное место диска. Запись
  идёт через временный файл с `os.replace`, чтобы оборванная загрузка не
  оставила половину файла под итоговым именем. `download_url` возвращает `None`:
  локальный файл отдаёт приложение, а не веб-сервер, — иначе проверку сессии
  пришлось бы дублировать в nginx.
- `S3Storage` работает через `boto3` и отдаёт presigned URL на
  `get_object` с `ExpiresIn=FILES_PRESIGN_TTL_SECONDS` и
  `ResponseContentDisposition`/`ResponseContentType`: браузер скачивает файл под
  исходным именем, а не открывает его встроенным просмотрщиком.

Конструктор `S3Storage` принимает фабрику клиента: тесты подставляют заглушку и
не ходят в сеть (правило CI «тесты не ходят в сеть»).

## D3. Единственное место, знающее про env, — фабрика

`get_storage()` под `functools.lru_cache` собирает бэкенд по
`settings.files_backend`. Сервисы получают хранилище функцией, а не настройками:
смена env не растекается по коду, а тесты сбрасывают кэш
`get_storage.cache_clear()`.

## D4. Ключ объекта формируется сервером

`build_key(tutor_id, filename)` → `"{tutor_id}/{uuid4().hex}{ext}"`. Имя
пользователя в ключ не попадает: ключ — не пользовательские данные, а адрес
объекта; исходное имя живёт в метаданных и уходит в `Content-Disposition`.
Расширение сохраняется, чтобы объект в бакете оставался опознаваемым.

## D5. Валидация до чтения тела

`validate_upload(filename, content_type, size)` проверяет расширение по
allowlist из `FILES_ALLOWED_EXTENSIONS`, размер по `FILES_MAX_SIZE_MB` и
непустое имя. Тело читается чанками с жёстким обрывом при превышении лимита:
`UploadFile` нельзя читать целиком — 20 МБ × N файлов в одном запросе съедят
воркер.

Порядок при сохранении ДЗ: сначала валидация ДЗ, затем запись ДЗ с `flush`
(нужен `homework.id`), затем файлы. Ошибка файла откатывает транзакцию и удаляет
уже записанные объекты — «половины» не остаётся.

## D6. Доступ к скачиванию — по актору, а не по ссылке

`resolve_downloadable_file(db, file_id, request)` определяет актора по трём
независимым сессиям (репетитор, ученик, родитель) и разрешает:

- репетитору-владельцу файла (`files.tutor_id`);
- ученику — если файл привязан к ДЗ урока, где он цель или участник группы;
- родителю — если файл привязан к ДЗ урока его ребёнка (привязка
  `StudentContact`).

Остальным — 404, как у несуществующего файла: существование чужой записи не
раскрывается. Presigned URL живёт после отзыва доступа до истечения TTL, поэтому
TTL по умолчанию короткий (900 с), а бакет приватный.

## D7. Отдача файла защищена от stored XSS

Пользовательский файл отдаётся только как вложение: `Content-Disposition:
attachment` и `X-Content-Type-Options: nosniff`, `Cache-Control: private,
no-store`. Иначе загруженный SVG или HTML открылся бы в контексте домена
приложения и получил доступ к сессионной cookie.

## D8. Связь с ДЗ — отдельная таблица с порядком

`homework_files` (homework_id, file_id, position, UNIQUE по паре) повторяет
паттерн `homework_answer_links`: порядок в SELECT не гарантирован, а список
файлов читается в осмысленной последовательности. Один файл может быть привязан
к нескольким ДЗ, поэтому файл и связь — разные таблицы.

## D9. Синхронный boto3 в async-вьюхе

`boto3` синхронный: вызовы хранилища в async-вьюхе уходят в
`starlette.concurrency.run_in_threadpool`, иначе один медленный запрос к S3
блокирует event loop и все остальные соединения воркера.

## Risks

- **Осиротевшие объекты**: падение между записью объекта и коммитом БД оставляет
  файл без строки. Уборка — отдельное cron-задание (`files.cleanup_orphans`), вне
  этой итерации.
- **Несколько воркеров uvicorn** должны видеть общий `FILES_LOCAL_ROOT` (том
  `/data` в Docker), иначе файл «пропадает» при балансировке.
- **Presigned URL** действует до истечения TTL даже после отзыва доступа к ДЗ;
  митигация — короткий TTL и приватный бакет.
- **Смена бэкенда** не переносит старые файлы: строка помнит свой бэкенд, но
  объект остаётся там, где был. Миграция данных — вне объёма.
- **Обратная совместимость**: схема только добавляет таблицы, дефолт
  `FILES_BACKEND=local`, поэтому существующие установки работают без S3. Откат —
  `alembic downgrade -1` и удаление каталога загрузок.
