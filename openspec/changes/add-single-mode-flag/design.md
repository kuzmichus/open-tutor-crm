# Design

## Context

Аутентификация репетитора живёт в модуле `tutor`:

- `app/tutor/views/register.py` — `GET /tutor/register` (форма) и
  `POST /tutor/register` (создание `Tutor`, редирект на
  `/tutor/login?registered=1`);
- `app/tutor/views/login.py` — `GET /tutor/login` (форма) и
  `POST /tutor/login` (проверка пароля и сессия);
- `app/tutor/views/remember_password.py` — восстановление пароля;
- шаблоны `tutor/login.html` и `tutor/remember_password.html` содержат ссылку
  «Нет аккаунта? Зарегистрироваться».

Конфигурация — `app/config.py`, класс `Settings` на pydantic-settings: поля
читаются из переменных окружения и `.env` (`SettingsConfigDict(env_file=".env")`),
глобальный объект `settings` создаётся при импорте. В проекте уже есть булевы
флаги (`messenger_tls_verify`, `google_calendar_sync`) — новый флаг оформляется
так же.

Без сессии `require_tutor_id` (`app/common/access.py`) поднимает `LoginRequired`
с редиректом на `/tutor/login`, поэтому корень `/` → `/tutor/` → `/tutor/login`
уже работает; достаточно добавить редирект на регистрацию в сам обработчик
входа.

## Goals / Non-Goals

**Goals:**

- Флаг `SINGLE_MODE` в конфигурации, по умолчанию `false` — мульти-режим,
  текущее поведение сохраняется.
- Сингл-режим: после появления первого репетитора `GET` и `POST`
  `/tutor/register` отвечают 404.
- Сингл-режим на первом запуске (репетиторов нет): `GET /tutor/login`
  перенаправляет на `/tutor/register`.
- Ссылки на регистрацию не показываются, когда она закрыта.

**Non-Goals:**

- Ограничение «ровно один репетитор» на уровне схемы БД (уникальный индекс,
  триггер) и защита от гонки двух первых регистраций.
- Управление режимом из интерфейса и его смена без перезапуска.
- Ограничение регистрации учеников и родителей по приглашениям.

## Decisions

**D1. Режим — булев флаг `SINGLE_MODE`, а не enum `CRM_MODE=single|multi`.**
Режимов ровно два, и один из них — текущее поведение. Булев флаг с дефолтом
`false` означает, что существующие установки ничего не настраивают и получают
прежнюю CRM; enum потребовал бы либо дефолта `multi`, либо обязательного
значения в каждом окружении. Имя `SINGLE_MODE` читается как ответ на вопрос
«включать ли сингл-режим?».

**D2. `settings.single_mode` читается в момент запроса, а не при импорте.**
Сервис `app/tutor/services/registration_mode.py` обращается к глобальному
`settings` внутри функций. Это позволяет тестам подменять значение через
`monkeypatch.setattr(settings, "single_mode", True)` — так же, как уже
подменяются `files_backend` и `files_max_size_mb` в тестах загрузки файлов.
Для владельца сервера поведение прежнее: настройки читаются при старте,
изменение `SINGLE_MODE` требует перезапуска приложения.

**D3. «Первый запуск» = в таблице `tutors` нет ни одной строки.**
Отдельного признака «инициализировано» нет и он не нужен: единственный
репетитор — и есть результат первого запуска. Проверка — `SELECT tutors.id
LIMIT 1` (`has_tutors`), без `COUNT(*)`: нужен только факт наличия строки.
Состояние не хранится, поэтому откат (удаление репетитора) снова открывает
регистрацию — это соответствует смыслу «персональная установка без аккаунта».

**D4. Закрытая регистрация отвечает 404, а не 403 и не редиректом.**
Страница не должна существовать для того, кто её не должен видеть: 404 не
раскрывает, что регистрация вообще есть и почему закрыта. Проверка стоит в
обоих обработчиках — `GET` и `POST`: иначе форму можно отправить напрямую,
минуя страницу. 404 поднимается `HTTPException(status_code=404)`, и его
отрисовывает существующий обработчик `not_found` (`main.py`), поэтому
пользователь видит обычную страницу 404 с подписью версии.

**D5. Редирект на регистрацию — только `GET /tutor/login` и только в
сингл-режиме на первом запуске.**
`POST /tutor/login` остаётся проверкой пароля: на первом запуске входить
некому, но редирект вместо формы ошибки на POST сломал бы семантику «форма
вернула сообщение». В мульти-режиме пустая база — нормальное состояние
(администратор заводит аккаунты через регистрацию), поэтому редиректа нет.

**D6. Ссылки на регистрацию скрываются при закрытой регистрации.**
Требование ограничивается ответом 404, но ссылка «Нет аккаунта?
Зарегистрироваться» на страницах входа и восстановления пароля вела бы в 404 —
это выглядит как поломка. Вьюхи передают в шаблоны `show_register =
registration_open(db)`, шаблоны оборачивают ссылку в `{% if show_register %}`.
На первом запуске сингл-режима ссылка видна (регистрация открыта).

**D7. Состояние входа и сессии не меняются.**
Сингл-режим не ограничивает уже открытые сессии и не завершает их: если
репетитор вошёл, его работа продолжается. Флаг влияет только на доступность
страницы регистрации и на первый вход.

## Risks / Trade-offs

- **Гонка первых регистраций.** Два одновременных POST на пустой базе в
  сингл-режиме могут создать двух репетиторов: проверка «есть ли строки» и
  `INSERT` не атомарны. Сценарий требует одновременного доступа к свежей
  установке; закрывается уникальным индексом в будущей задаче, если станет
  актуальным (см. Non-Goals).
- **Зависимость от перезапуска.** `SINGLE_MODE` читается при старте: смена
  режима «на лету» не подхватывается. Это общее свойство конфигурации проекта
  (`GOOGLE_*`, `FILES_*`), отдельного механизма не вводим.
- **404 вместо отдельной страницы «регистрация закрыта».** Владелец, забывший
  про флаг, увидит 404 на `/tutor/register`; подсказка живёт в README и
  CHANGELOG, а не в интерфейсе — страница не должна объяснять посторонним,
  что здесь была регистрация.
- **Откат.** Выставить `SINGLE_MODE=false` и перезапустить приложение —
  регистрация снова открыта. Схема БД не меняется, миграций для отката нет.
