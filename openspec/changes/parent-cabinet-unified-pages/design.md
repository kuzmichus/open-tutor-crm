# Design: Единые страницы кабинета родителя

## Context

Кабинет родителя (`app/cabinet`) повторяет каркас CRM: сайдбар, `.main`,
htmx. Сейчас навигация строится секциями по детям (`parent/_sidebar.html`),
страницы ребёнка — `/parent/students/{id}` и `/parent/students/{id}/homework`,
финансы — одна страница с блоками по детям. Недельная сетка «только чтение»
уже реализована для кабинета ученика: `cabinet/services/calendar.py` поверх
общего `build_calendar_context`, партиал `cabinet/_lessons_calendar.html`,
листание недель htmx-свопами. Плашки-предупреждения репетитора: включаемый
`app/templates/_notice_banner.html`, партиалы `/tutor/notices/*`, Alpine-фабрика
`noticeGroup` (`app/static/notices.js`), спека `cabinet-notices`.

Решения владельца из exploration: пункт меню «Уроки»; `/parent` — редирект;
задолженность = отрицательный баланс; плашка срока учитывает «Задано» и
«Не выполнено» и закрывается с запоминанием; цвет карточек сетки — цвет
ребёнка; звёздочка — «★ N».

## Goals / Non-Goals

**Goals:**

- Плоская навигация и общие страницы на всех детей вместо страниц ребёнка.
- Сетка недели всех детей с переиспользованием каркаса календаря.
- Вкладки по детям на «Домашних заданиях» и «Финансах» без потери
  изоляции по контакту.
- Алерты «нехватка на сегодня» и «задолженность» на всех страницах
  кабинета родителя.

**Non-Goals:**

- Действия родителя (ответы на ДЗ, платежи) — кабинет остаётся read-only.
- Своя часовая зона родителя как отдельная настройка — сетка показывает
  пояс первого ребёнка (решение владельца, D9), а не свой выбор.
- Пагинация ДЗ, экспорт, изменения финансов.
- Обобщение партиала сетки на оба кабинета (см. риски).

## Decisions

### D1. Плоский сайдбар

`parent/_sidebar.html` теряет цикл по детям и пары «раздел + ребёнок»:
четыре пункта, активность — только по разделу. Дети в архиве не влияют на
меню (они и так учитываются на общих страницах — иначе разошлись бы с
«Финансами», где их история остаётся).

### D2. Редиректы вместо удаления путей

`/parent` → `/parent/lessons`; `/parent/students/{id}` → `/parent/lessons`;
`/parent/students/{id}/homework` → `/parent/homework?child={id}` — 303 через
`RedirectResponse`. Ссылки родителям уже разосланы (мессенджер, закладки),
поэтому пути сохраняются. Проверка привязки в редиректах не нужна: страница
данных не отдаёт. Файлы вьюх `parent_index.py`, `parent_student_lessons.py`,
`parent_student_homework.py` переписываются в редиректы с теми же путями —
имена файлов сохраняются.

### D3. Многодетная сетка недели — зеркальный сервис

Новый `cabinet/services/parent_calendar.py` по образцу
`student_calendar_context`: те же `week_bounds`/`now_local`/
`build_calendar_context`, но выборка — два SELECT с
`Lesson.student_id.in_(дети)` / `GroupMember.student_id.in_(дети)`.
Карточка: подпись «Имя ребёнка» / «Имя · Группа», цвет — `Student.color`
ребёнка (для групповых тоже: ось родителя — «который из детей»). Прошедшие
уроки остаются серыми ( existing-логика), звезда — исключение: «★ N»
золотым токеном поверх серой карточки, чтобы оценку было видно.

Рейтинг берётся из уже выбранных строк (`Lesson.rating` в SELECT) —
дополнительного запроса нет. ДЗ — тот же массовый `homework_by_lesson` на
всю неделю.

Партиал `parent/_lessons_calendar.html` — копия ученического с `hx-get` на
`/parent/lessons?start=…` и звёздочкой в карточке. Осознанное дублирование:
URL листания и состав бейджей различаются; обобщение (параметр base_url в
один партиал) отложено до третьего потребителя.

Звёздочка — текст «★ N» (как `format_rating`), не lucide-иконка: пересборка
`icons.js` не требуется.

### D4. Табы — серверные, через `?child=<id>`

Активная вкладка — параметр адреса, дефолт — первый ребёнок в порядке
`children()`. Валидация — существующий `get_child(db, child_id, contact_id)`:
чужой/несуществующий — 404 (требование изоляции сохраняется). Серверные
вкладки работают без JS и не требуют Alpine-состояния; контент вкладок
всё равно собирается на сервере.

Альтернатива (Alpine-переключение с рендером всех вкладок) отклонена:
данные по детям в одном ответе тяжелее и путают изоляцию.

### D5. Плашка срока ДЗ

Считается на сервере при рендере `/parent/homework`: по всем видимым
заданиям всех детей — статусы «Задано»/«Не выполнено», `due_at` сравнивается
с «сегодня» в зоне репетитора (`today_local`). Плашка — один блок над
вкладками, вне notice-stack (другой источник данных и другое закрытие).
Закрытие — Alpine-компонент с ключом в localStorage, включающим состав
предупреждения (id заданий + день): закрытое сегодня не прячет завтрашнее,
по аналогии с close-keys репетиторских плашек.

### D6. Родительские алерты — зеркало репетиторского каркаса

Включаемый `parent/_notice_banner.html` с теми же классами
(`notice-stack`, `notice-summary`) и той же фабрикой `noticeGroup`
(она не привязана к id контейнера): подключается на все четыре страницы
родителя. Два htmx-партиала: `/parent/notices/balance` (нехватка) и
`/parent/notices/debt` (задолженность), `hx-trigger="load"` — в кабинете
родителя нет сохраняющих событий, `from:body`-триггеры не нужны.

Сервисы в `app/cabinet/services/`:

- нехватка — переиспользует `digest_lessons(db, tutor, day)` и фильтрует
  цели по id детей контакта: формула цен
  (`price_override ?? group.price_per_lesson`) и «уже прошедшие по времени,
  но не отмеченные» остаются в одном месте, дубликата выборки нет;
- задолженность — `balance()` по каждому ребёнку, отрицательные в плашку.

Импорт `cabinet → lesson/finance` согласуется с существующим направлением
(`cabinet/services/calendar.py` уже тянет `calendar`, `child_finance.py` —
`finance`).

### D7. Финансы: тот же сервис, другой шаблон

`finance_overview` не меняется: возвращает блоки по детям + итог. Шаблон
`parent/finance.html` переходит на табы: общая плашка итога, затем блок
активного ребёнка. Ограничение выборки активным ребёнком — в шаблоне по
`active_child`, без нового сервиса.

### D8. Порядок роутов

`/parent/lessons`, `/parent/homework`, `/parent/notices/*` регистрируются в
`views/__init__.py` до редиректов `/parent/students/{student_id}` (правило
AGENTS.md 3: статические пути до параметрических).

### D9. Зона отображения сетки — первый ребёнок (решение владельца,
уточнение 2026-11-16 в ходе применения)

Время сетки «Уроков» — в часовом поясе первого ребёнка в порядке
навигации (`Student.timezone` с его карточки), как у ученика; пустое или
неизвестное имя пояса — зона педагога (правило `_student_zone`
напоминаний), а не системная зона сервера. Окно недели, «сейчас»,
колонки дней, бейдж пояса и плашка «Ближайшее занятие» используют одну
зону (`display_zone_owner`), иначе бейдж противоречил бы колонкам.
Рабочие границы сетки — настройки педагога (часы работы, не зона).
Хелперы `tutor_time` принимают любой объект с `.timezone`, поэтому
носителем зоны служит сам ребёнок либо карточка педагога — без нового
типа-обёртки.

## Risks / Trade-offs

- [Дублирование партиала сетки между кабинетами ученика и родителя] →
  осознанная копия: URL и бейджи различаются; обобщение при третьем
  потребителе.
- [`noticeGroup` фактически обкатан на репетиторском контейнере] → фабрика
  не зависит от id; при реализации проверить локальное хранилище ключей
  закрытия, у родителя ключи со своими id.
- [Плашка срока и notice-stack на одной странице] → разные блоки с разным
  закрытием; путаницы нет, но проверить визуально на узком экране.
- [ digest_lessons фильтруется по детям на Python] → уроков у репетитора за
  день десятки, фильтр дешёвый; N+1 не возникает.
- [Редирект маскирует опечатку в id ребёнка] → приемлемо: данных по пути
  не отдаётся, пользователь попадает на корректную страницу.

## Migration Plan

Миграций БД нет. Деплой — обычный; откат — git revert (старые URL после
отката снова отдают страницы ребёнка, новые продолжают работать).
