# Open Tutor CRM

**Открытая CRM для репетиторов: ученики, группы, уроки и расписание — на вашем собственном сервере.**

Один репетитор — один аккаунт — только его данные. Self-hosted: база и файлы лежат у вас
(SQLite по умолчанию, PostgreSQL — сменой `DATABASE_URL`), никаких подписок и облаков.
Рендеринг серверный на Jinja2 + HTMX + Alpine.js — без Node.js и сборки фронтенда; все
ассеты отдаются локально, без CDN. История версий — в [CHANGELOG.md](CHANGELOG.md).

## Возможности

- **Главная** — дашборд «сегодня»: уроки дня, активные ученики, доход и проведённые часы за месяц.
- **Календарь** — недельная сетка по четвертям часа: уроки, окна для записи, отпуска и выходные, навигация по неделям.
- **Ученики** — карточки с контактами, статусом и долгом; переиспользуемые контакты взрослых с ролью и напоминаниями.
- **Группы** — до 10 участников, цена за урок с человека, вкладки занятий и оплат группы.
- **Уроки** — индивидуальные, групповые, пробные и отработки; серии с массовым изменением; отметка проведёнными пачкой; длительность нового урока и окна для записи по умолчанию берётся из профиля (вкладка «Календарь»).
- **Домашние задания** — вкладка урока: задание, срок сдачи, статус, ответ ученика и проверка; к заданию прикрепляются файлы — они лежат в локальном каталоге или в S3-бакете (см. [«Хранение файлов»](#хранение-файлов)).
- **Брони и публичная запись** — ученик записывается по ссылке без входа, заявка подтверждается в календаре и становится уроком.
- **Финансы** — сводка за период с проведёнными часами и средней стоимостью часа, часами подготовки по коэффициенту профиля и реальной стоимостью часа с советом по ставке, упущенная чистая прибыль простоя (свободные окна × реальная ставка), доходы по типам занятий, все операции, аналитика и прогноз на месяц; для самозанятых — расчётный налог НПД по физлицам и юрлицам с прогрессом годового лимита дохода; счёт ученика: платежи, списания, возвраты, счёт за период.
- **Задачи** — канбан по этапам и список по срокам: приоритет, срок, привязка к ученикам.
- **Статистика** — загрузка в астрономических часах и учёт внеурочной занятости: подготовка к урокам и проверка ДЗ по коэффициенту профиля, «Загрузка ресурса» по общей занятости с цветом по часам в неделю (комфорт до 35 ч, высокая 35–45 ч, риск больше 45 ч), баланс «уроки vs подготовка», предупреждение о риске выгорания, карта загрузки, LTV, Retention Rate, «риск потери», конверсия из пробного, выгрузка CSV.
- **Рассылки** — сегменты учеников, шаблоны с подстановками и журнал всех сообщений бота.
- **Мессенджеры** — Telegram и MAX: токен бота, каналы уведомлений и приглашения учеников по диплинку, без ручного ввода chat_id.
- **Google Календарь** — подключение аккаунта одной кнопкой в профиле: занятия создаются, правятся при переносе и удаляются вместе с уроком (см. [«Как подключить Google Календарь»](#как-подключить-google-календарь)).
- **Кабинеты** — ученик (`/student`) видит неделю своих занятий в календаре (только чтение, со значками ДЗ) и сдаёт ДЗ, родитель (`/parent`) — детей, их занятия, ДЗ и финансы; входы независимы от сессии репетитора.
- **Оформление** — светлая и тёмная темы: выбор запоминается и не мигает при переходах.

Данные каждого репетитора изолированы: запись другого аккаунта неотличима от несуществующей.

## Быстрый старт (Docker Compose)

Нужен только Docker. Сохраните как `docker-compose.yaml`, запустите `docker compose up -d`, откройте <http://localhost:8000> → регистрация → главная с дашбордом. Живость: `GET /health` → `{"status": "ok"}`.

```yaml
services:
  migrate:                      # одноразовая миграция до старта приложения
    image: kuzmichus/open-tutor-crm:latest
    command: alembic upgrade head
    volumes: [open_tutor_data:/data]
    restart: "no"

  app:
    image: kuzmichus/open-tutor-crm:latest
    depends_on:
      migrate:
        condition: service_completed_successfully
    ports: ["8000:8000"]
    volumes: [open_tutor_data:/data]
    restart: unless-stopped

volumes:
  open_tutor_data:
```

Для стабильности зафиксируйте версию вместо `latest` (релизы публикуются с тегами `X.Y.Z`, `X.Y`, `sha-*`). Образ собирается для `linux/amd64` — на ARM-хосте соберите его локально (см. ниже). База живёт на томе `open_tutor_data` (`/data` в контейнере).

Cron — из crontab хоста раз в минуту (compose расписаний не умеет):

```bash
* * * * * cd /путь/к/каталогу/compose && docker compose run --rm app python cron.py
```

## Запуск на своём сервере

### Docker без compose

```bash
docker run --rm -v open_tutor_data:/data kuzmichus/open-tutor-crm:latest alembic upgrade head

docker run -d --name open-tutor-crm \
  -p 8000:8000 \
  -v open_tutor_data:/data \
  kuzmichus/open-tutor-crm:latest
```

Миграции — одноразовым контейнером **до** первого старта приложения: приложение схему само не создаёт, без миграций оно упадёт на первом же запросе с «no such table».

### Сборка образа локально

```bash
docker build -t open-tutor-crm .
```

Дальше те же команды с `open-tutor-crm` вместо `kuzmichus/open-tutor-crm:latest`; процесс
не под root, живость проверяет встроенный healthcheck (`GET /health`).

### Релизы образа

Публикация — только вручную: workflow `.github/workflows/release.yml` запускается на
Actions → **Release** → «Run workflow» с полем `version`, которое обязано совпадать с
версией в `pyproject.toml`. Каждый выпуск получает четыре тега: `X.Y.Z`, `X.Y`,
`latest` и `sha-<7 знаков>`; последним шагом создаётся релиз GitHub с тегом `v<version>`
(при ошибке реестра не появится ни релиза, ни тега). Секреты `DOCKERHUB_USERNAME` и
`DOCKERHUB_TOKEN` нужны только этому workflow — `ci.yml` запускается из форков без них.

Кроме релизов есть ночной образ: workflow `.github/workflows/nightly.yml` запускается
по расписанию каждый день (03:17 МСК) и публикует текущий HEAD `main` под тегом
`night` — но только если все проверки (тот же `ci.yml`) зелёные, поэтому красный
`main` тег не обновляет. Ночной канал — не релиз: git-теги и релизы GitHub не
создаются, `latest` не двигается, тег `night` один и перезаписывается каждой
успешной ночью. Запустить вручную можно на Actions → **Nightly** → «Run workflow».

### Без Docker: uv + systemd

Нужен только [uv](https://docs.astral.sh/uv/) — Python 3.14 он подтянет сам.

```bash
sudo git clone https://github.com/kuzmichus/open-tutor-crm.git /opt/open-tutor-crm
cd /opt/open-tutor-crm
sudo uv sync --no-dev
sudo uv run alembic upgrade head
sudo chown -R www-data:www-data /opt/open-tutor-crm   # SQLite пишет журнал рядом с базой
```

`/etc/systemd/system/open-tutor-crm.service`:

```ini
[Unit]
Description=Open Tutor CRM
After=network.target

[Service]
Type=exec
User=www-data
WorkingDirectory=/opt/open-tutor-crm
ExecStart=/opt/open-tutor-crm/.venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000 --workers 4
Restart=on-failure
Environment=DATABASE_URL=sqlite:////opt/open-tutor-crm/tutor.db

[Install]
WantedBy=multi-user.target
```

Запустите: `sudo systemctl daemon-reload && sudo systemctl enable --now open-tutor-crm`.
Наружу отдавайте через nginx или Caddy с HTTPS — сессионная cookie ездит в браузере.

Cron — раз в минуту. Задания: автозавершение уроков, не отмеченных 24 часа после окончания (списание — как при ручной отметке), дневная сводка уроков в мессенджеры, рассылка «День рождения» и сверка Google Календаря.

- **Дневная сводка** — в время из профиля (вкладка «Уведомления», поле «Время отправки») во все привязанные каналы: время, ученик или группа и пометка, если на счету не хватает денег на урок.
- **День рождения** — в то же время, если включён переключатель «День рождения» на вкладке «Уведомления»: во все привязанные каналы уходит список учеников с днём рождения сегодня, с исполняющимся возрастом. Пустой список сообщения не даёт. Дата рождения 29 февраля в невисокосные годы в рассылку не попадает.
- **Сверка Google Календаря** — приводит события окна «вчера — 90 дней вперёд» к состоянию базы: создаёт пропущенные (сохранение урока не прошло из-за сети), правит изменившиеся и удаляет события занятий, которых в базе уже нет. Работает только у репетиторов с подключённым календарём.

Задания идемпотентны и живут в своих транзакциях: одна отправка на локальные сутки педагога.

```bash
* * * * * cd /opt/open-tutor-crm && /opt/open-tutor-crm/.venv/bin/uv run python cron.py
```

## Конфигурация

Параметры читаются из переменных окружения или файла `.env` в корне проекта.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./tutor.db` | строка подключения SQLAlchemy; в образе — `sqlite:////data/tutor.db` |
| `APP_NAME` | `Open Tutor CRM` | название приложения |
| `SINGLE_MODE` | `false` | режим работы CRM: `false` — мульти, регистрация репетиторов открыта всегда; `true` — сингл, страница регистрации живёт только до создания первого аккаунта |
| `MESSENGER_TLS_VERIFY` | `true` | проверка TLS-сертификатов Bot API мессенджеров; `false` — на машинах без корня Минцифры (сертификат `platform-api2.max.ru`) |
| `GOOGLE_CLIENT_ID` | — | OAuth-клиент Google для интеграции с Календарём; пусто — интеграция выключена |
| `GOOGLE_CLIENT_SECRET` | — | секрет того же OAuth-клиента |
| `GOOGLE_REDIRECT_URI` | из запроса | внешний адрес callback; за прокси задайте явно `https://ваш-домен/tutor/profile/google/callback` |
| `GOOGLE_CALENDAR_SYNC` | `true` | `false` — синхронизация занятий с Google выключена, подключение остаётся |
| `MIGRATION_SOURCE_TZ` | системная зона сервера | зона-источник перевода старых записей в UTC; читается только `alembic upgrade`, например `MIGRATION_SOURCE_TZ=Europe/Berlin uv run alembic upgrade head` |
| `FILES_BACKEND` | `local` | куда складывать загруженные файлы: `local` — каталог на сервере, `s3` — S3-совместимый бакет |
| `FILES_LOCAL_ROOT` | `./files` | каталог локального хранилища; в образе — `/data/files` (на томе рядом с базой) |
| `FILES_MAX_SIZE_MB` | `20` | предел размера одного файла, МБ |
| `FILES_ALLOWED_EXTENSIONS` | документы, таблицы, презентации, картинки, архивы | разрешённые расширения через запятую, без точки |
| `FILES_PRESIGN_TTL_SECONDS` | `900` | срок жизни временной ссылки на скачивание (только S3), секунды |
| `S3_BUCKET` | — | имя бакета; обязательно при `FILES_BACKEND=s3` |
| `S3_REGION` | `us-east-1` | регион бакета |
| `S3_ENDPOINT_URL` | — | адрес S3-совместимого хранилища (MinIO, Selectel); пусто — AWS |
| `S3_ACCESS_KEY_ID` | — | ключ доступа; обязателен при `FILES_BACKEND=s3` |
| `S3_SECRET_ACCESS_KEY` | — | секретный ключ; обязателен при `FILES_BACKEND=s3` |
| `S3_PREFIX` | `uploads/` | префикс ключей объектов в бакете |
| `LANDING_ROOT` | `./landing` | каталог лендинга на диске: черновик, опубликованная страница и картинки редактора; в образе — `/data/landing` |
| `SMTP_HOST` | — | адрес SMTP-сервера; пусто — почта выключена, письма не отправляются |
| `SMTP_PORT` | `587` | порт SMTP-сервера |
| `SMTP_USERNAME` | — | логин на SMTP-сервере; пусто — без авторизации |
| `SMTP_PASSWORD` | — | пароль к `SMTP_USERNAME` |
| `SMTP_FROM` | `SMTP_USERNAME` | адрес отправителя в письмах |
| `SMTP_STARTTLS` | `true` | шифрование через STARTTLS (обычно порт 587) |
| `SMTP_USE_SSL` | `false` | TLS с самого начала соединения (обычно порт 465); взаимоисключающе с `SMTP_STARTTLS` |
| `SMTP_TIMEOUT` | `15` | таймаут соединения с SMTP-сервером, секунды |
| `APP_BASE_URL` | из запроса | внешний адрес приложения для ссылок в письмах; за прокси задайте явно `https://ваш-домен` |

Время хранится в UTC, вводится и показывается в зоне репетитора (IANA-имя из его карточки); при пустом поле — зона сервера. SQLite держит кабинет одного-двух репетиторов; для большего смените `DATABASE_URL` на PostgreSQL, добавьте драйвер (`uv add "psycopg[binary]"`) и прогоните миграции — код моделей не меняется.

### Режим работы: сингл и мульти

`SINGLE_MODE` определяет, сколько репетиторов может быть в установке:

- `false` (по умолчанию) — **мульти-режим**: страница регистрации `/tutor/register` открыта всегда, аккаунтов может быть сколько угодно.
- `true` — **сингл-режим** для персональной установки: страница регистрации работает только на первом запуске, пока в базе нет ни одного репетитора. В этом состоянии `GET /tutor/login` перенаправляет на регистрацию — чтобы владелец сразу создал свой аккаунт. После первой регистрации страница `/tutor/register` отвечает 404 и на GET, и на POST, а ссылки «Нет аккаунта? Зарегистрироваться» на страницах входа и восстановления пароля исчезают.

```bash
SINGLE_MODE=true uv run uvicorn main:app --host 0.0.0.0 --port 8000
```

Режим читается при старте приложения: после смены переменной перезапустите сервис. Схема БД не меняется — «первый запуск» определяется по отсутствию строк в таблице `tutors`, поэтому удаление репетитора снова открывает регистрацию. Ограничение на уровне БД не ставится: одновременные первые регистрации в сингл-режиме теоретически могут создать два аккаунта, для персональной установки это не сценарий.

## Как подключить Google Календарь

Интеграция синхронизирует **занятия**: новое занятие появляется в календаре, перенос меняет время события, удаление занятия (и серии, и группы) удаляет событие. Окна для записи, недоступность и задачи в Google не попадают. События пишутся в основной календарь подключённого аккаунта, во временной зоне репетитора из вкладки «Календарь»; участники не приглашаются, письма не рассылаются.

OAuth-клиент создаёт **владелец сервера** один раз на весь сервис, репетитор только нажимает кнопку в профиле — client_id и secret в интерфейсе не вводятся. Каждый репетитор подключает свой аккаунт Google: подключения и токены изолированы по владельцу.

### 1. OAuth-клиент в Google Cloud Console

1. Откройте [Google Cloud Console](https://console.cloud.google.com/), создайте проект (или выберите существующий) и в **APIs & Services → Library** включите **Google Calendar API**. Без неё подключение пройдёт, а первая же запись события упадёт с ошибкой `accessNotConfigured`.
2. **APIs & Services → OAuth consent screen**: тип *External* (для аккаунтов Google Workspace своего домена — *Internal*). Заполните название приложения, почту поддержки и контакты разработчика. В новом интерфейсе Google это страницы **Google Auth Platform → Branding / Audience / Clients**.
3. На той же странице в **Data access → Add or remove scopes** добавьте `https://www.googleapis.com/auth/calendar.events`, `openid` и `email` — это ровно те права, которые запрашивает приложение. Пока приложение в статусе *Testing*, подключиться смогут только аккаунты из списка **Test users** (до 100 штук) — добавьте туда каждого репетитора. Учтите: в статусе *Testing* Google выдаёт refresh-токен на 7 дней, после чего интеграция попросит подключиться заново; для постоянной работы нажмите **Publish app** — для `calendar.events` (чувствительный scope) Google попросит верификацию.
4. **Credentials → Create credentials → OAuth client ID** → тип **Web application**. В **Authorized redirect URIs** добавьте адрес ровно в том виде, в каком он попадёт в запрос: `https://ваш-домен/tutor/profile/google/callback`. Схема, домен, порт и путь должны совпадать побайтово — иначе Google ответит `redirect_uri_mismatch`. Google принимает `https`, а `http` — только для `localhost` при локальной разработке; наружу приложение должно быть опубликовано через HTTPS-прокси.
5. Скопируйте **Client ID** и **Client secret** — они понадобятся на следующем шаге.

### 2. Переменные окружения сервера

```bash
GOOGLE_CLIENT_ID=xxxx.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=xxxx
GOOGLE_REDIRECT_URI=https://ваш-домен/tutor/profile/google/callback
```

Куда их положить:

- **git-установка (uv + systemd)** — в `.env` в корне проекта (файл в `.gitignore`) или в `Environment=`/`EnvironmentFile=` systemd-юнита;
- **Docker** — в `environment:` сервиса `app` в `docker-compose.yaml` (или подключите `env_file: .env`); сервису `migrate` эти переменные не нужны. При `docker run` — флаги `-e`.

`GOOGLE_REDIRECT_URI` можно не задавать: тогда адрес собирается из запроса (`http://localhost:8000/tutor/profile/google/callback` при локальном запуске). За прокси и в контейнере так делать нельзя — приложение увидит внутренний хост и `http`, и Google отклонит обмен кода.

Дополнительно: `GOOGLE_CALENDAR_SYNC=false` оставляет подключение, но запрещает запросы к Google. После изменения переменных **перезапустите приложение** — настройки читаются при старте.

### 3. Подключение аккаунта

Откройте **Профиль → Календарь → «Подключить Google»** и дайте доступ. Возврат происходит на ту же вкладку: карточка показывает «Календарь подключён» и email аккаунта. Будущие занятия (`starts_at >= сейчас`) выгружаются сразу, дальше события создаются, правятся и удаляются вместе с занятиями.

Проверка: создайте занятие на завтра — событие «Занятие — имя ученика» появится в Google в течение нескольких секунд; перенесите занятие — время события изменится; удалите — событие исчезнет. Ошибки синхронизации видны в карточке интеграции и в логе приложения (`gcalendar`): `docker compose logs app` или `journalctl -u open-tutor-crm`.

Для надёжности держите запущенным cron (см. [«Запуск на своём сервере»](#запуск-на-своём-сервере)): сверка `gcalendar.reconcile` догоняет события, которые не создались из-за сетевого сбоя, обновляет изменившиеся и удаляет осиротевшие.

### Если что-то пошло не так

| Что видно | Причина | Что делать |
|---|---|---|
| «Интеграция не настроена», кнопка неактивна | `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` пусты или приложение не перезапущено | задать переменные и перезапустить |
| Google: `redirect_uri_mismatch` | адрес в Console не совпадает с `GOOGLE_REDIRECT_URI` (или с адресом из запроса) | сверить адреса побайтово; за прокси задать `GOOGLE_REDIRECT_URI` явно |
| «Доступ к Google Календарю не предоставлен» | в окне согласия нажали «Отмена» или аккаунта нет в **Test users** | добавить аккаунт в тестовые и повторить |
| «Ссылка подключения устарела или уже использована» | callback открыт повторно или ссылка устарела | начать подключение заново из профиля |
| «Не удалось завершить подключение Google Календаря» | неверный `GOOGLE_CLIENT_SECRET`, истёк код, сетевая ошибка | проверить secret и лог `gcalendar`, повторить |
| «Доступ к Google Календарю отозван — подключите его заново» | доступ отозван в аккаунте Google или истёк refresh-токен (статус *Testing* — 7 дней) | подключить заново; для постоянной работы опубликовать приложение |
| Календарь подключён, событий нет | `GOOGLE_CALENDAR_SYNC=false`, занятия только в прошлом или не запущен cron при сетевых сбоях | включить синхронизацию, настроить cron |
| События задвоились | базу восстановили из бэкапа, не отключив интеграцию | удалить лишние события и подключить календарь заново |

### Отключение и ограничения

Кнопка «Отключить» забывает подключение и удаляет связи с событиями, но **сами события в календаре Google остаются** — это расписание репетитора, стирать его без явной просьбы нельзя.

Событие окрашивается в ближайший к цвету ученика или группы цвет — так же, как карточка в календаре CRM. Палитра событий Google уже палитры CRM (11 цветов против 16), поэтому оттенок может отличаться, а у некоторых учеников и групп он совпадёт. Если цвет у цели не задан, событие получает цвет по умолчанию. Смена цвета ученика или группы перекрашивает уже созданные события при следующей синхронизации, а сверка в cron догоняет цвет у событий, созданных до появления раскраски.

Синхронизация односторонняя: правки события в Google не возвращаются в CRM. Если Google недоступен или доступ отозван, занятия в CRM продолжают сохраняться: ошибка видна в карточке интеграции, а сверка в cron догоняет пропущенное. Перед восстановлением базы из резервной копии отключите интеграцию: без строк соответствий сверка создаст события заново и в календаре появятся дубли.

## Хранение файлов

К домашнему заданию прикрепляются файлы: в панели «ДЗ» можно выбрать несколько сразу. Хранилище выбирается переменной `FILES_BACKEND` — код загрузки и скачивания один и тот же, меняется только бэкенд:

- **`local`** (по умолчанию) — объекты лежат в каталоге `FILES_LOCAL_ROOT`, отдаёт их само приложение через `GET /files/{id}` после проверки доступа. Ничего дополнительно настраивать не нужно; каталог создаётся при первом сохранении.
- **`s3`** — объекты лежат в бакете, а `GET /files/{id}` проверяет доступ и отвечает редиректом на временную ссылку (presigned URL) со сроком жизни `FILES_PRESIGN_TTL_SECONDS`. Так файлы можно держать вне сервера приложения; ссылка перестаёт работать после истечения срока, а ключи объектов в интерфейс не попадают.

Файл, прикреплённый к ДЗ, доступен репетитору-владельцу, ученику этого урока (в том числе участнику группы) и родителю, привязанному к ученику. Остальным — 404: чужой файл неотличим от несуществующего.

Имя файла в хранилище генерируется сервером (`<id репетитора>/<uuid><расширение>`), исходное имя хранится только в метаданных — одинаковые `домашка.pdf` у разных учеников не перезаписывают друг друга, а имя из формы не может вывести запись за пределы каталога. Бэкенд запоминается у каждого файла: после смены `FILES_BACKEND` старые файлы продолжают скачиваться из прежнего хранилища.

Что учесть при эксплуатации:

- **Резервная копия.** При `local` каталог файлов — такие же данные, как база: в образе он лежит на томе `/data` рядом с `tutor.db`, в git-установке — в `FILES_LOCAL_ROOT`. Копируйте его вместе с базой, иначе после восстановления базы из бэкапа файлы будут отдавать 404.
- **Ограничение размера на прокси.** Приложение проверяет `FILES_MAX_SIZE_MB` само, но nginx по умолчанию режет тело запроса на 1 МБ — поднимите лимит: `client_max_body_size 25m;` (Caddy ограничения не ставит).
- **Права на каталог.** Процесс приложения должен писать в `FILES_LOCAL_ROOT`; в systemd-установке каталог создаётся под тем же пользователем, что и сервис (`www-data`).

## Лендинг

В сингл-режиме (`SINGLE_MODE=true`) на `/` публикуется лендинг репетитора — одна страница, которую владелец правит визуально в редакторе. Лендинг один на установку и хранится на диске в каталоге `LANDING_ROOT`, отдельно от загрузок `FILES_*` и без записей в базе:

```
landing/                    LANDING_ROOT
  draft.html                черновик (пишет редактор, показывает предпросмотр)
  index.html                опубликованная страница → GET /
  index.prev.html           бэкап прошлой публикации
  assets/<uuid>.<ext>       картинки из редактора, публично /landing-assets/...
```

- **Публикация.** Пока `index.html` нет, `GET /` отвечает прежним 303 на `/tutor/`. После публикации корень отдаёт файл как есть — без серверного рендера и подстановки данных, — с `Cache-Control: no-cache`: свежая публикация видна сразу. Предыдущая версия сохраняется в `index.prev.html` (хранится ровно одна); отмена публикации удаляет `index.html`, не трогая бэкап и черновик.
- **Картинки.** Ассеты отдаются с `/landing-assets/<uuid>.<ext>` публично, с долгим кэшем `public, max-age=31536000, immutable`. Имя генерирует сервер (`uuid4` и расширение), поэтому одинаковые имена из редактора не перезаписывают друг друга, а обход каталога через URL невозможен. Принимаются только картинки: png, jpg/jpeg, gif, webp, svg.
- **Asset Manager.** В редакторе картинки загружаются через Asset Manager (`POST /tutor/landing/assets`): кнопка загрузки принимает только картинки из белого списка, общий лимит — `FILES_MAX_SIZE_MB`, у растров проверяются магические байты (файл `photo.png` с текстом внутри будет отклонён). SVG принимается по расширению осознанно: модель доверия та же, что у правки HTML. Ранее загруженные картинки показываются в окне ассетов по абсолютным ссылкам `/landing-assets/…`, поэтому `/` и предпросмотр показывают одно и то же. Удаление ассета (`DELETE /tutor/landing/assets/<имя>`) после подтверждения убирает файл с диска; ссылка на удалённую картинку отдаёт 404 — это ожидаемо, о нём предупреждает текст подтверждения.
- **Входы.** Кнопки входа на опубликованной странице сами меняются у вошедших: ученик и родитель видят «В кабинет» (→ `/student` и `/parent`), репетитор — «кабинет» (→ `/tutor/`). Страница при этом остаётся статическим файлом: скрипт `landing-auth.js` запрашивает публичный `GET /auth/status`, который отвечает булевыми статусами трёх независимых сессий с `Cache-Control: no-store`. Аноним, сбой запроса или протухшая сессия оставляют обычные ссылки на страницы входа; скрипт не трогает разметку вне `[data-auth]`.
- **Безопасность.** `<script>` на опубликованной странице разрешён: HTML правит владелец установки. Загружать через редактор можно только картинки, пользовательское имя файла в путь не попадает.
- **Управление.** Страница `/tutor/landing` (пункт «Лендинг» в сайдбаре, только в сингл-режиме) показывает состояние страницы — «опубликован», «черновик» или «пусто». С неё доступны предпросмотр черновика (`/tutor/landing/preview`), публикация, снятие с публикации и возврат шаблона из профиля. Первый черновик создаётся кнопкой «Создать черновик»: шаблон по умолчанию подставляет имя, предмет, «О себе», опыт, ставку и телефон, а CTA «Записаться на занятие» ведёт на публичную страницу записи `/s/<tutor_id>`. Обычное открытие страницы управления черновик не перезаписывает — «Вернуть шаблон» требует подтверждения и применяется только явно. В шаблоне уже стоят точки входа: «Вход для ученика» и «Вход для родителя» в шапке, ненавязчивая ссылка «вход» в подвале.
- **Редактор.** Полноэкранный визуальный редактор `/tutor/landing/editor` (кнопка «Редактировать» на странице управления) открывает черновик в GrapesJS: верхняя панель «Сохранить / Предпросмотр / Назад к управлению», канвас на весь вьюпорт. Интерфейс переведён на русский собственной локалью `app/static/dist/grapesjs/i18n-ru.js` (включая подписи свойств диспетчера стилей); незаведённые ключи уходят в английский. GrapesJS 0.23.9 (BSD-3-Clause) лежит локально в `app/static/dist/grapesjs/` — CDN не используется, версия и контрольные суммы зафиксированы в README рядом. В редактор попадают только тело черновика без `<script>` и первый `<style>`; сокращения с `var()` перед загрузкой разворачиваются в эквивалентные длинные свойства, иначе CSSOM GrapesJS терял бы `background: var(--accent)` и рамки. «Сохранить» отправляет `editor.getHtml()` / `editor.getCss()` на `POST /tutor/landing/draft`, сервер собирает полный документ заново, сохраняет прежний `<title>` и идемпотентно гарантирует тег `/static/landing-auth.js` перед `</body>`. Скрипты в редактируемом теле не сохраняются — это осознанное ограничение: тег подмены входов возвращается автоматически.
- **Блоки.** Панель «Блоки» в редакторе наполняется сервисом `app/landing/services/blocks.py` по разметке из `app/landing/templates/blocks/`: категория «Блоки лендинга» — готовые секции шапки, обложки с CTA, «О себе», «Стоимости», «Контактов» и подвала в дизайне шаблона; «Базовые» — заголовок, текст, изображение, кнопка и разделитель; «Макет» — две и три колонки. Блок вставляется кликом (`blockManager.appendOnClick`). Секции используют классы и CSS-переменные шаблона по умолчанию, поэтому вставка не добавляет новых правил CSS, а CTA ведёт на публичную страницу записи текущего репетитора (`/s/<tutor_id>`). Подписи блоков и категорий — в русской локали.
- **Вставка изображений.** Блок «Изображение» после вставки сразу открывает Asset Manager: можно выбрать ранее загруженную картинку или загрузить новую. Выбранный файл попадает в `src` компонента абсолютной ссылкой `/landing-assets/…`, поэтому картинка видна в канвасе, предпросмотре и на `/` после публикации. Двойной клик по любой картинке в канвасе открывает Asset Manager для замены.
- **Резервная копия.** Каталог `LANDING_ROOT` — такие же данные, как база и загрузки: в образе он лежит на томе `/data` (`/data/landing`), в git-установке — в `./landing`. Копируйте его вместе с `tutor.db`.

## Отправка почты (SMTP)

Почта нужна для восстановления пароля: письмо со ссылкой сброса уходит на email репетитора. Почтовый сервер задаёт владелец установки, в интерфейсе ничего не настраивается.

Почта включается переменной `SMTP_HOST`. Ссылка восстановления уходит только письмом и никогда не показывается на странице: иначе любой, кто знает чужой email, мог бы сбросить пароль, открыв форму. Пока `SMTP_HOST` пуст, восстановление недоступно — страница сообщает об этом, а ссылка пишется в лог приложения (`WARNING` от логгера `mail`), откуда её может взять владелец сервера. Минимальный набор для обычного почтового провайдера (порт 587, STARTTLS):

```bash
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=robot@example.com
SMTP_PASSWORD=пароль-или-токен-приложения
SMTP_FROM=robot@example.com          # необязательно: по умолчанию SMTP_USERNAME
APP_BASE_URL=https://crm.example.com # чтобы ссылка в письме вела на внешний адрес
```

- **Порт 465 вместо 587.** Некоторые провайдеры принимают подключения сразу по TLS: задайте `SMTP_USE_SSL=true` и `SMTP_STARTTLS=false` (одновременно оба способа включить нельзя — приложение не стартует).
- **Без авторизации.** Для локального релея (`SMTP_HOST=localhost`, порт 25) оставьте `SMTP_USERNAME` и `SMTP_PASSWORD` пустыми, но задайте `SMTP_FROM`.
- **Неполная конфигурация.** Если `SMTP_HOST` задан, но отправителя нет, приложение не стартует и называет недостающие переменные — так же, как при неполной настройке S3.
- **Внешний адрес.** За прокси `APP_BASE_URL` обязателен: иначе ссылка в письме может указывать на внутренний хост или `http://`. Значение — без завершающего слэша.
- **Спам-фильтры.** Письма с нового домена чаще попадают в спам: настройте у провайдера SPF и DKIM для домена из `SMTP_FROM`.

Проверка вручную: откройте `/tutor/remember-password`, введите email зарегистрированного репетитора — при настроенном SMTP письмо придёт на этот адрес, а страница покажет «Если аккаунт с таким email существует, письмо со ссылкой для сброса пароля отправлено». Ссылка на странице не показывается. Перейдя по ссылке из письма, задайте новый пароль дважды — при несовпадении полей форма покажет ошибку. Ссылка действует 24 часа и срабатывает один раз.

## Обновление

Перед обновлением сделайте резервную копию базы:

```bash
cp tutor.db tutor.db.bak                                    # git-установка
docker run --rm -v open_tutor_data:/data -v "$PWD:/backup" \
  python:3.14-slim cp /data/tutor.db /backup/tutor.db.bak   # docker-установка

# git-путь
git pull && uv sync --no-dev && uv run alembic upgrade head

docker compose pull && docker compose run --rm migrate && docker compose up -d
```

## Разработка

```bash
uv sync                                   # dev-зависимости
uv run uvicorn main:app --reload          # dev-сервер на :8000
uv run pytest -n auto                     # тесты
uv run alembic upgrade head               # схема БД

```

Схему базы создаёт только Alembic — перед первым запуском dev-сервера выполните `uv run alembic upgrade head` (иначе приложение упадёт на первом же запросе с «no such table»). Правила разработки — в [AGENTS.md](AGENTS.md), спецификации поведения — в `openspec/specs/`.

### Иконка сайта

Набор favicon в `app/static/favicons/` (ICO, PNG, SVG, `apple-touch-icon`,
maskable-иконка и `site.webmanifest`) собирается из одного исходника
`scripts/vendor/favicon-source.png` скриптом `scripts/build_favicons.py`:

```bash
uv run --with pillow python scripts/build_favicons.py   # пересобрать весь набор
```

Исходник — 200×200, поэтому 512 px получается апскейлом: если появится PNG
размером 512 или больше, достаточно заменить `favicon-source.png` и повторить
команду. Pillow нужен только для пересборки, в зависимостях проекта его нет.
Ссылки на набор прописаны в `app/templates/base.html` и наследуются всеми
страницами; `/favicon.ico` отдаёт маршрут `app/common/views/favicon.py`.

платежи с должниками и предоплатами, домашние задания, задачи и расходы.

```bash
uv run python scripts/seed_demo.py        # пересоздать демо-данные
uv run python scripts/smoke_demo.py       # проверить, что все страницы рендерятся
```

Скрипт **разрушающий**: данные репетитора `demo@example.com` удаляются и создаются
заново (остальные аккаунты в базе не затрагиваются). Вход после прогона —
`demo@example.com` / `12345678`. Списания за проведённые уроки считаются доменным
сервисом `sync_lesson_charge`, поэтому балансы в демо-базе совпадают с тем, что
показывает приложение.

Issues и pull request'ы приветствуются: прочитайте [AGENTS.md](AGENTS.md), добавьте тесты
на новое поведение и убедитесь, что `uv run pytest -n auto` зелёный.

(`.github/workflows/ci.yml`): тесты, `uv lock --check`, `alembic check`
(модель без миграции валит PR), линт `ruff check --select E9,F63,F7,F82`
и сборка образа с смоук-проверкой `GET /health`. Тот же набор идёт перед
публикацией релиза — красные тесты не уезжают в образ.
